# Today and Chat

The two everyday tabs: Today's feed (backend composition and the page), and Chat (the URL as source of truth, the work rail, the turn model, the transcript, the composer, drafts and the queue), plus the chat state in `ChatContext` and how a new build reaches tabs left open.

## The three tabs

- The dock and header are three tabs, three questions: **Today** (what does he need from me, what happened), **Chat**, **Edward** (what he knows, watches, does; the route stays `/settings` so old links work — [settings.md](settings.md)). The pure nav config is `frontend/components/layout/navItems.ts`.

## Today

- **Today** (`backend/services/today_service.py`, `GET /api/today`): `compose_today()` is pure and pinned in `tests/test_today_service.py`. Each need carries a `rank`, in this order: an overdue *timed* pet dose → an escalated message thread (24 h), a calendar event about to start, a send held for approval → fresh open loops (not snoozed, priority ≥ .5, fewest nudges first, at most 3) → Edward's notes that need the owner → one-shot events in the next 24 h (recurring housekeeping never) → finished workers (24 h) → a timed dose due within 45 min. The digest collapses recurring fires to one row. Each need ships its actions (method, url, body), so the page only runs them (`runTodayAction`). One source failing degrades the feed, never breaks it.
- **Fields the UI relies on** (2026-09-26):
  - an approval need carries `send: {channel, recipient, text, subject?}` (`detail` stays the one-line summary), and `POST /api/approvals/{id}` returns `delivered` from the send tool's own reply: the UI says "Sent" only when it is true;
  - a dose's "Log given" body carries `for_care_day` (and the first household member as `given_by` — [hub.md](hub.md)), and `POST /api/hub/care/{item_id}/log` answers 409 when it is not today's care day (the hub's own taps send none);
  - goals carry `set_on` / `set_by`, and their progress no longer includes the "Goal set" line;
  - the message-count row reads "Read N messages · M for you";
  - `GET /api/events` items carry `event_type` (null for the owner's plain reminders) and parsed `event_metadata`;
  - `GET /api/settings/models` adds `mind_model`, `mind_effort`, `mind_efforts`, `pulse_model`, `pulse_effort`, `chat_model`, `chat_effort` (efforts as the request will send them);
  - `GET /api/consolidation/connections?with_content=true` carries `memory_a_content` / `memory_b_content`;
  - the /screen calendar carries `all_day`.
- **Escalated messages collapse to one need per thread** (the conversation, else the chat identifier), carried by the newest message with the count in the detail: a busy group chat used to put the same name on Today five times (`test_escalated_messages_from_one_thread_collapse_into_one_need`).

### Today as a briefing: the feed

(The UX pass of 2026-09-25/26, from an audit of a live day; `today_service`'s docstring has the list.)

- **Needs never flood**: notes sharing a title are one card with a `count` (seven identical "Which is right?" cards once landed within 41 s); at most `MAX_NOTE_NEEDS` (4) note cards and `MAX_HEARTBEAT_NEEDS` (5) threads, the rest in `overflow` ("and 3 more" opens `GET /api/notes`).
- **Every note and message card has a mutating Done**: `POST /api/notes/{id}/dismiss {also}` expires the card's notes now (the rows stay, so the next pack still reads the day's notes); `POST /api/today/heartbeat/{event_id}/done {also}` stamps the card's events `notified_at` with the batch `owner:done` (the mark the mind puts on what it considered, so the next wake's "Waiting on you" drops them too), and only the ids the card carried: a message that arrived after Today loaded stays a new card.
- A contradiction note carries a `choice` (both memories; each answer resolves the flag through `POST /api/consolidation/flags/{id}/resolve {keep}`).
- A calendar row is a `calendar` need ("Dentist in 25 min", gone an hour after it began), never "someone needs a reply"; an escalated email is "<sender> emailed you: <subject>".
- **"What I did"** is one window (`did_since`: local midnight or 18 h back, whichever is earlier), every row with its `at`. Edward's plumbing (`PLUMBING_EVENT_TYPES`: the pulse, widget refresh, mind wakes, ticks, the sweep and the retired surplus tick — pinned against `scheduler_service.event_route`) never appears, and the mind's wakes are one folded row ("Woke 6 times · acted on 2").
- `presence` (what he is listening to, his last and next wake) replaced the heartbeat's 80-key `status`, which keeps only the two fields the page read.
- One clock format, "7:34 pm" (`_clock`; `lib/edwardMood.formatClock` on the page).
- Tests: `tests/test_today_service.py`, `test_today_io.py`, `test_care_day_guard.py`.

### Today as a briefing: the page

(`components/today/`)

- `TodayHero`: the date, the live Edward beside his greeting, and one quiet line only the signals support (`heroModel.ts`). About 800 ms after the owner resolves a need it asks the greeting `?fresh=1`, so it stops naming what was just done.
- Needs are whole-card targets (`NeedCard`: a stretched link under the title, the owner's primary action neutral, the tone a small chip). A held send quotes who and what; a contradiction is answered by tapping the memory that is right.
- Receipts with Undo: a Done waits out its Undo before it is sent; "Sent" only when the server says `delivered`.
- "What I did" is bucketed by part of the day (`bucketDid`: This morning / afternoon / evening, Earlier today, Last night, Tonight, Yesterday; newest first), his chosen acts in his colour linking to their journal entry. Then the owner's threads. Two panes at lg (the hero and For you on the left; What I did and conversations on the right, sticky).
- **Instant paint** (`useTodayFeed`, pure `todayFeedState.ts`): the last feed from module memory, then sessionStorage `edward:today:v1` (≤ 24 h, with its scroll position), revalidated quietly, polled every minute while visible, a failed load retried from 2 s to 1 min. A change on screen bumps a generation, and a load started before it is dropped (a refresh in flight used to put a logged dose back). A feed painted from the cache or left through a long sleep is `confirmed: false` until the network answers, and an action on it is checked against a fresh feed first. One action per card: a double tap does nothing. Pull to refresh on touch (`pullToRefresh.ts`).
- **Keyboard** (desktop): j / k move between the cards that need the owner, e runs the focused card's primary action, x is its Done. The focused card is read from the DOM's focus at the keypress (`focusedCardIndex`): a remembered index, after a click elsewhere or a reflow, turned into a stray dose log or a sent message. **No key ever acts on a held send** (`todayKeys.keyAction` returns null for approvals): a send goes out from the owner's number, so it is always a deliberate tap.
- Tests: `todayModel.test.ts`, `todayFeedState.test.ts`, `todayHero.test.ts`, `todayKeys.test.ts`, `todayPull.test.ts`, `todayView.test.tsx`, `useTodayFeed.test.tsx`.

## Chat

- **Conversation visibility**: `EDWARD_OWN_SOURCES` (`scheduled_event`, `heartbeat`, `edward_thought`) are hidden from default listings unless the owner engaged (more than 2 messages) or Edward reached out (`notified_user`). `is_conversation_visible()` is the pure predicate; `_visible_filter()` the SQL. The sidebar shows **Yours / Edward's** (`components/chat/sidebarGroups.ts`), fetched per group via `GET /api/conversations?group=yours|edwards`. Edward's group is paged **per source** on the server (thoughts would otherwise crowd everything off the first page) and pinned to include `edward-surfaces`; the sidebar sections it as Surfaces / Threads / Workers / Scheduled / Thoughts (thoughts folded). Thought conversations are titled from the narrative's first sentence (`thought_conversation_service.thought_title`).
- **The chat URL is the source of truth** (`/chat?c=<id>`): sidebar taps and the dock's New push a URL, the page reconciles URL against state on every navigation (`lib/chatRoute.ts::decideChatRoute`), and a brand-new chat `replaceState`s its id into the URL when the first stream event assigns one, so back and forward return to the conversation that was on screen. **Never call `loadConversation` from a click handler; push the URL.** Message threads order by latest message (`last_activity_at`), not `updated_at`, which retitles and nudges bump.
- **Timestamps**: the conversations API emits Z-suffixed UTC; `lib/time.ts::parseIso` treats any naive ISO as UTC. **Never `new Date(iso)` directly.**
- **iMessage thread titles** carry the contact name (`imessage_conversation_service.title_for_chat` / `retitled_for`); callers pass `contact_name` for 1:1 inbound senders only. `scripts/backfill_imessage_titles.py` is the one-off for older rows.
- **The work rail** (`components/chat/WorkRail.tsx`, pure `lib/workRail.ts`, labels `lib/toolLabels.ts`; rebuilt 2026-09-26): one timeline above the answer, in arrival order (`buildTimeline`: memory search, each reasoning step by its **heading**, tools, code with output, plans, helpers and Codex sessions).
  - Live: a 16 px Edward mirrors the turn (a nod per tool that went well, a wince per failure), the latest reasoning heading is the status (each fades in once; nothing loops in the transcript), and the seconds count.
  - When the answer starts the timeline folds, before there is text to read, so the answer being read is never yanked up (it used to fold at done). At done the header becomes the receipt at the same height: "Thought for 14s · texted Parker · searched memory · opened 2 pages", outward acts in emerald; a tap reopens it.
  - `toolLabels.ts` says what he did ("Opened example.com", "Searched “kayak weather”", "Texted Parker") from the tool and the stream's `args_summary`: one exact-name table for every backend tool (`toolLabels.test.ts` reads `graph/tools.py` and `services/toolset/*.py` and fails on a tool without a label; the toolset's action tools read `"{action}: {detail}"`), keyword rules for MCP tools, else the name in words.
  - A turn reloaded from history renders through exactly the same path, from its stored `trace` ([tool-loop.md](tool-loop.md)).
  - The preference is per device (`edward:workDisplay`: collapse | open | tap), set in the Mind room ("In chat").
  - **Showing the thinking, the tool use and the reasoning is a product requirement; do not hide it behind a debug flag.**
  - Assistant turns render without a bubble or avatar; the owner's bubble is neutral (emerald is Edward's).
  - Tests: `workRail.test.ts`, `workRailView.test.tsx`, `toolLabels.test.ts`.
- **The turn model** (`lib/turnModel.ts`, pure; `ChatContext` folds every SSE event through `reduceTurn`): one answer to "what is Edward doing on this turn": `recalling → thinking → working → writing`, ending `done | stopped | error`, driven only by stream events, never by whether the answer text is empty (that made the rail flap between tool rounds). A stream that closes without `done` (a hidden tab, a dropped connection) is `cut`: the server may still be finishing, and the thread reloads when visible. `ChatContext` exposes `streamingMessageId`; a bubble is live iff `message.id === streamingMessageId` (`workRail.isLiveMessage`), and `MessageBubble` is memoised so only that bubble re-renders per token. Presence reads the same turn. Tests: `turnModel.test.ts`, `streamSegments.test.ts`, `chatTurn.test.tsx`, `streamErrorRecovery.test.ts`.
- **The transcript** (`ChatWindow`, pure `lib/scrollStick.ts`; 2026-09-26): while a turn streams, a ResizeObserver keeps the newest line in view by writing `scrollTop` (no smooth scroll per token); opening a thread or sending lands at the bottom. **Only the reader lets go**: wheel, touch, a scrolling key or the scrollbar mark intent; a layout clamp is not intent (the composer re-measuring used to read as "scrolled up" and drop the live turn behind the pill), and tapping a disclosure in the transcript lets go without a pin so it opens under the finger. Then new text raises "New reply ↓".
  - A reading column (`max-w-3xl`) shared with the composer; a thread still loading is a skeleton conversation.
  - Under a finished answer: Copy · Retry (the owner's own question, never a pack or a trigger — `lib/answerText.ts::retryQuestion`) · Read aloud (`speakableText` → `POST /api/voice/synthesize`, cancellable). App links stay in the app, off-app links open a new tab with ↗, and `/api/files/<id>/download` downloads (`classifyLink`).
  - A new chat is `ChatEmptyState`: Edward as the hero (the day's first wave, `listen` while the owner types), his greeting streamed in, his status as a caption when there is something to say, a few ways in from Today (`lib/chatSuggestions.ts`: each fills the composer through `?prompt=`, never sends) and Resume.
  - Tests: `scrollStick.test.ts`, `messageBubble.test.tsx`, `answerText.test.ts`, `chatEmptyState.test.tsx`, `chatSuggestions.test.ts`.
- **Drafts, deletes, the list**: what the owner types stays with its thread (`lib/drafts.ts`: sessionStorage `edward:draft:<conversation id | __new__>`, ≤ 20K characters, every storage call guarded). Deleting a conversation is optimistic with Undo (`lib/pendingDeletes.ts`, a module store that outlives the drawer): the row leaves at once, the API call waits out the 6 s Undo window, and Undo means nothing is ever sent. Pending deletes commit on `pagehide` **and** `visibilitychange → hidden`, because iOS suspends and then kills a backgrounded PWA without ever sending `pagehide`; the commit starts before subscribers hear, so the row never flashes back. The sidebar and drawer list conversations as links (swipe or hover to delete) and read only `useChatList()` (below). Tests: `drafts.test.ts`, `pendingDeletes.test.ts`, `deleteStaysGone.test.tsx`, `undoableDelete.test.ts`, `sidebarRows.test.ts`, `chatContextSplit.test.tsx`.
- **Attachments stay with their thread** (2026-09-27): switching threads used to `setFiles([])` and drop them silently. `lib/draftFiles.ts` keeps them in memory per conversation (`readDraftFiles` / `writeDraftFiles` / `rekeyDraftFiles` when a new chat gets its id). Deleting a thread forgets them and refuses later writes for that id (`forgetDraftFiles`, called by `ChatSidebar` after a successful DELETE; a refused DELETE keeps them, since the thread comes back); sign-out empties them. Kept attachments in any thread hold a new build's reload (`hasDraftFiles`). Still open: a thread deleted from another device keeps holding reloads in this tab. Tests: `inputBarDrafts.test.tsx`, `draftFilesDeletedThread.test.tsx`.
- **The prefill carries a nonce**: `InputBar` accepts `prefill` as a string or `{text, nonce}`, and `/chat` passes `{text: prompt, nonce: Date.now()}`, so the same "Try it" twice refills the composer (React skipped the re-render when the page set the same string again). Test: `chatPagePrefill.test.tsx`.
- **Rename on the phone** (2026-09-27): on touch, swiping a row shows Rename beside Delete; a full swipe still deletes (65 % of the measured row, never within 24 px of the open position, never more than one button past it: 200 px on a 306 px iPhone row instead of 264). Tests: `sidebarRows.test.ts`, `sidebarTouchRename.test.tsx`.
- **"Reached out" is only for what reached someone** (2026-09-27): the sidebar's Actions chip and `ThoughtEntryHeader` read `thought.reached` (true when a message was delivered to a person or a push reached the owner) and nothing else; `outward` is also true for `leave_note` and a held send. A null or missing `reached` (an entry written before the field) is unknown and shows no chip, never a fallback to `outward`. `ThoughtMeta.reached?: boolean | null`; the conversations API returns it (`ThoughtResponse.reached`). Tests: `sidebarGroups.test.ts`, `thoughtEntryHeader.test.tsx`, backend `test_thought_journal_wake.py`.
- **The composer** (`components/chat/InputBar.tsx`, pure `lib/composerAction.ts`): one primary slot on the right: an empty box → the waveform ("talk live"), anything typed or attached → send. While streaming, typed text **queues** and Stop moves beside it (`showsSeparateStop`; Enter never stops). The mic button always records a memo ([voice.md](voice.md)). No "+" menu; the paperclip is inline on every size.
- **The queue while a turn runs** (2026-09-24): queued messages show as chips with × above the composer (`lib/composerQueue.ts`); the ChatProvider's drain effect (`nextOnDone`) sends the next one in the same conversation when the turn ends (done or error), one at a time, holding while history loads, in voice mode, or while a hidden-tab stream is recovered.
  - **Stop means stop** (2026-09-26): a stopped turn with messages queued pauses the queue (`queuePaused`) until the owner taps the chip's "Send now" (`resumeQueue`).
  - The queue is per conversation, in memory, and mirrored with the composer's kept attachments (`lib/draftFiles.ts`) into the tab's stash (`lib/tabStash.ts`: IndexedDB keyed by a per-tab id in sessionStorage, a day at most, cleared by sign-out). **Why**: after a deploy, Next 14.1 answers any navigation that fetches the server with a full page load (a build-id mismatch), whatever `AppBuildReload` holds (pre-deploy review, 2026-09-27). The next load puts attachments back with their thread, and the queue back **paused**.
  - Tests: `__tests__/tabStash.test.tsx`, `__tests__/composerQueue.test.ts`, `__tests__/composerAction.test.ts`.
- **The dock**: Today / Chat / Edward only ([design-and-presence.md](design-and-presence.md#the-shell)). The Chat tab tapped while on `/chat` starts a new chat (`navItems.chatTabAction` / `dockTapAction`); a separate "New" button was redundant.
- **The greeting** (`routers/chat.py`): stale-while-revalidate. Within 60 s the cached line; past that the cached line *plus* one background refresh; past 30 min a synchronous rebuild. Opening the app never waits on the ~2 s greeting model call. `?fresh=1` (2026-09-26; Today asks after the owner resolves a need, so the hero stops saying "Biscuit's meds are waiting" after they were logged) rebuilds a line older than 20 s, at most one forced rebuild per 20 s, and a failed rebuild keeps the line it had (`_greeting_wants_rebuild`; `tests/test_greeting_cache.py`).
- **The phone stays awake mid-turn** (2026-09-07): `/chat` calls `useWakeLock(isLoading)` (`lib/useWakeLock.ts`; the policy is `lib/wakeLockPolicy.ts::shouldHoldWakeLock` = working ∧ visible). The iPhone PWA used to sleep while Edward was still running tools.
- **Phone focus mode**: while the composer on `/chat` has focus, the presence bar and dock fold away (`lib/chrome.ts::shouldHideChrome`, `lib/useComposing.ts`; blur is debounced so tapping Send doesn't flash them back), and `--shell-inset-bottom` then carries the home indicator for the composer.

## Frontend chat state

- React Context holds the chat state: conversation selection, message history, the one active stream, voice mode, the composer queue.
- Split by who re-renders (2026-09-26): `useChat()` is everything; `useChatList()` is the memoised list slice (conversations, search, paging and stable actions; no messages, no turn) for the sidebar, drawer, dock and header, so a streamed token never re-renders 30–50 rows; `useChatPresence()` is what Edward's presence reads (the turn, the voice phase); `useComposerQueue()` is safe outside a provider. `streamingMessageId` names the one live bubble (above). Test: `__tests__/chatContextSplit.test.tsx`.

## New builds reach open tabs

(`frontend/lib/buildReload.ts`, `components/layout/AppBuildReload.tsx`, `app/build-id/route.ts`; 2026-09-27)

**Why**: nothing told an open tab that a new build existed. After the 2026-09-26 deploy, the /screen tab in the owner's Chrome kept the old bundle: 36,694 `GET /api/display/signals` the next day at the old 2 s cadence from two pollers, and almost no calls to the new code's `/api/mind/now`. The display fixes never reached the monitor; a kiosk and a PWA left open do the same.

- `next.config.js` makes one build id (the commit sha and UTC build time, `<12-hex sha|nogit>-<YYYYMMDDTHHMMSS>`, or `EDWARD_BUILD_ID` if the deploy sets it), used for `generateBuildId` and baked in as `NEXT_PUBLIC_BUILD_ID`; it equals `.next/BUILD_ID`. `GET /build-id` (a Next route outside `/api`, which `next.config.js` rewrites to the backend) answers `{"build_id": …}` with `Cache-Control: no-store`, force-dynamic, and is NetworkOnly in the service worker.
- `useBuildReload(surface)` checks every 3 min (the first after 20 s), when the tab becomes visible, on a back/forward-cache restore and when the network returns; never while hidden.
  - **Display and hub routes** (the `(display)` layout) reload when nobody has touched the screen for 30 s.
  - **App routes** (`AppBuildReload` inside `ChatProvider`) reload only when no chat turn is running, live voice is off, nothing is queued in the composer in any thread, no thread keeps attachments, the composer is not holding (it holds while it has text, files or a voice memo recording), and there has been no tap, key or wheel input for 2 minutes (a page scrolling itself is not input).
- **On every surface the page's own work holds** (`pageHoldsWork`): a focused text field with text, any writable textarea with text (focus can drop when the PWA backgrounds), a playing video or audio element, an iframe with a `src` (an embedded player; the /screen srcdoc tiles don't count, so an embed left up on /screen keeps that tab on the old build until it is cleared).
- **Any component can hold** with `useBuildReloadHold(active)`: the composer, an open microphone (`useMicStream`, so every live-voice view including `/hub/ask`), a voice memo being recorded, the /screen compose bar while typing or streaming, the hub's "Screen off" (a reload would light the panel back up for the night), a Hub Photos upload in progress, a goal's progress line or status change in flight, a half-written wish.
- A reload that left the old bundle running (a stale cache) is not retried for 10 minutes (`RETRY_GUARD_MS`). React only: this sits in the display, hub and Today first loads, so it must never pull framer-motion or the chat into them (`buildReloadWiring.test.tsx`).
- Tests: `__tests__/buildReload.test.ts`, `buildReloadWiring.test.tsx` (drives a real turn and real voice mode), `pwaCaching.test.ts`.
