# Authentication and the PWA

Single-user password auth, the first password's one-time setup code, rate limits, session renewal, the household photo door, and the PWA's rules for auth, caching and the service worker.

## Backend auth

(`backend/services/auth_service.py`, `backend/routers/auth.py`)
- Single-user password auth with JWT tokens and an HttpOnly cookie session (`edward_token`): bcrypt password hashing, 30-day JWT expiration, HS256.
- The password is chosen once, at first-time setup on `/login` (`POST /api/auth/setup`), and stored as `settings.password_hash`; `POST /api/auth/change-password` changes it. There is no default password.
- **The first password needs the one-time setup code** (2026-10-12; `backend/services/setup_code.py`). While no password exists, the backend keeps a random code (`XXXX-XXXX-XXXX`, from an alphabet without 0/O/1/I/L, about 59 bits) in backend/.setup_code: created with `O_CREAT|O_EXCL|O_NOFOLLOW` at mode 0600, readable by the backend's user alone, and git-ignored. It is made at startup (`services/setup_code.py::ensure_for_startup`, in the lifespan right after `init_db`, best effort) and on demand by `GET /api/auth/status` and `POST /api/auth/setup`. A file that is not a regular 0600 file owned by that user and holding a well-formed code (world-readable, a symlink, garbage) is replaced, never trusted. The log says only where it is, at every start while there is no password ("No password is set yet. First-time setup code: cat backend/.setup_code (<absolute path>)", a warning in `/tmp/edward-backend.log`), never the code: the `/tmp` logs are world-readable. The code is deleted after a successful setup, and at startup once a password exists; a lost password row gets a new one. The owner reads it on the Mac (cat backend/.setup_code, from the checkout) and types it into the setup form; case, dashes and spaces don't matter, and the comparison is constant-time (`services/setup_code.py::matches`). Edward's own shell and editor can neither read nor replace the file ([computer.md](computer.md#the-rails)).
- **`POST /api/auth/setup` checks, in this order** (`routers/auth.py::setup_password`; body `{password, setup_code}`):
  1. 415 unless `Content-Type: application/json`. A form post or a typeless `fetch` body is a "simple" cross-site request that needs no preflight, and FastAPI parses a body that has no Content-Type as JSON.
  2. 403 (`SETUP_LOCAL_ONLY`: "The first password can only be set on the Mac Edward runs on. Open http://localhost:3000 there.") when an `Origin` header is present and is not `http(s)://localhost`, `127.0.0.1` or `[::1]`, on any port.
  3. 403, the same words, unless `client_ip.is_local_client` says the original client was this Mac: a loopback peer, no `CF-Connecting-IP`, every `X-Forwarded-For` / `X-Real-IP` / `Forwarded` entry loopback, and, through Next's proxy, a loopback host in `X-Forwarded-Host` (`http://my-mac.local:3000` from a phone is not local).
  4. 429 with `Retry-After` after 10 wrong codes from one client in 15 minutes. This is a store of its own: the attempt is reserved before the first await, a missing code doesn't count, and setup never touches the login limiter.
  5. 422 for a malformed body ("Send a password and the setup code.").
  6. 400 "A password is already set. Sign in with it."
  7. 503 when the code file can't be written.
  8. 403 "That setup code doesn't match. On the Mac Edward runs on: cat backend/.setup_code", for a missing or a wrong code.
  9. 400 for a password under 8 characters.

  The write runs under a lock (one per event loop), so a double submit with the right code sets the password once and the second answers 400. Then the code is deleted and the session cookie set. `GET /api/auth/status` carries `setup_code_required` (true only while no password exists), the login page's setup form asks for the code (below), and `setup.sh`, `restart.sh` and `scripts/install-launchagents.sh` print where it is ([ops-health-backups.md](ops-health-backups.md#first-time-setup)). A Mac with no screen: `ssh -L 3000:localhost:3000 you@my-mac.local`, open `http://localhost:3000` on your own computer, and read the code over ssh. Tests: `tests/test_public_auth_hardening.py`.
- **Why the code** (2026-10-12 review). Whoever sets the password owns the install, a shell on the host included; the backend and `next start` listen on every interface; and the LaunchAgents start Edward before the owner has chosen a password. The first fix was the header check (steps 2 and 3) alone, and it could be beaten. Next's `/api` proxy copies the client's own `Host` into `X-Forwarded-Host` and adds no `X-Forwarded-For`, so `curl -H 'Host: localhost:3000' http://my-mac.local:3000/api/auth/setup` from any device on the LAN passed as local. And before setup, any web page open in a browser on the Mac could post a typeless `fetch` to `http://localhost:3000/api/auth/setup` without a preflight. The JSON, Origin and local-client checks stay as a second line: an honest phone or hub browser at `http://my-mac.local:3000` gets the 403 above, so it is told where to go. But a hand-made request can forge every header, so the proof is the code, which takes a read on the Mac.
- **Before a password is set, the API is closed**: `AuthMiddleware` 401s every non-public `/api` route with "Edward has no password yet. Set one on the Mac Edward runs on: open http://localhost:3000 there." (`NOT_SET_UP`); only `/health`, `/`, `/api/auth/status`, `/api/auth/setup` and the public routes below answer. It used to let everything through until setup, so a LAN device could run turns or flip skills on a fresh install. A valid session cookie is still honoured (only the signing key can mint one), and the live-voice socket always needs one. Tests: `tests/test_public_auth_hardening.py`, `tests/test_voice_ws_router.py`.
- **Password attempts are rate-limited** (`routers/auth.py`), each in a 15-minute sliding window and a store of its own:
  - **Logins** (the owner's `/login` and the photo door's): 5 failures per client, and **100 failures across all clients** close new logins (owner and photo door) for everyone until the oldest age out; signed-in sessions are not affected. At most 10,000 clients are tracked (the least recently failed are forgotten first).
  - **`/change-password`**: 5 failures per signed-in session (keyed by a hash of its token), with no ceiling across clients, so a guessing attack on the login never stops the owner changing the password. It used to share the login's store and ceiling.
  - **Wrong setup codes**: 10 per client (above).
  - **An attempt is reserved before the first await** (2026-10-12 review): it is recorded under its key at once and counts against every limit while the password is checked; a success clears the key, and a failure keeps the reservation as its record. Checking first and recording after the database and bcrypt let a parallel burst of guesses pass every limit at once. bcrypt (cost 12, about a quarter of a second a call) runs in `asyncio.to_thread` in login, setup, change-password and the photo door, so a burst no longer freezes every turn, stream and the scheduler. A 429 now really carries `Retry-After`: it used to be set on the injected `Response`, which is thrown away when the route raises.

  The client is `client_ip.client_ip` (`backend/services/client_ip.py`): the peer itself unless it is loopback; behind a loopback peer (Next's `/api` rewrite, a tunnel on this Mac) `CF-Connecting-IP`, else the right-most `X-Forwarded-For` entry that is not loopback (each proxy appends, so the left-most entries are whatever the client wrote), else the peer. The old key was the left-most `X-Forwarded-For` entry, which any client chooses. Uvicorn's own proxy-header handling (trusting 127.0.0.1 by default) may already have rewritten the client; that counts as local only while `FORWARDED_ALLOW_IPS` is unset or loopback, so leave it so. A LAN device that goes through Next's proxy controls every header Next passes on, so it can rotate its per-client key; that is what the ceiling is for. **Known limits, not fixed**: Next adds no `X-Forwarded-For`, so every client that comes through it without proxy headers of its own (the owner at `http://localhost:3000` and a phone or hub on the LAN alike) has the same key, `127.0.0.1`, and 5 wrong passwords from the LAN close the login for all of them for 15 minutes (10 wrong setup codes likewise pause the owner's first setup: a delay, never a takeover, since the code is still needed); anyone who can reach the login (the LAN, a tunnel) can keep it closed for everyone with 100 failures every 15 minutes; and IPv6 clients are keyed per address, not per /64.
- `AuthMiddleware` (`backend/middleware/auth.py`) validates the `edward_token` cookie on every `/api/*` route except `PUBLIC_ROUTES`: `/api/auth/status|login|setup`, the Twilio webhooks (they fail closed on the Twilio signature instead, [integrations.md](integrations.md)), `/api/push/vapid-key` and `/api/push/status`, `/api/widget` and `/api/widget/chat` (token-checked inside), `/api/presence/beacon` and `/api/presence/stream` (token-checked), `/api/alexa` (only its skill id is checked — no Amazon signature verification), `/api/gmail/oauth/callback` (state-checked inside), and `/api/health/email` (the watchdog's verdict, no details); plus `/docs`, `/redoc`, `/openapi.json`. The photo door's routes have their own rule (below). WebSockets never pass through it: the voice socket checks the cookie itself, with or without a password set, and the browser extension's socket takes only a direct connection from this Mac with the Origin of Edward's own extension ([screen-and-browser.md](screen-and-browser.md#edwards-hands-in-the-owners-chrome)). The widget token that `/api/widget*` and the presence routes check is **owner-equivalent**: `POST /api/widget/chat` runs a turn as the owner, so the token belongs only on the owner's own devices, and `POST /api/widget/token/regenerate` replaces a leaked one.
- REST API: `GET /api/auth/status`, `POST /api/auth/setup`, `POST /api/auth/login`, `POST /api/auth/logout`, `POST /api/auth/change-password`.
- The JWT secret: `JWT_SECRET_KEY` when set to a real value; otherwise the persisted `backend/.jwt_secret` (auto-generated on first use; an old dev default is ignored with a warning). Whoever holds it can mint the owner's session. **Edward's shell and editor cannot read it** (2026-10-12): a Seatbelt read-deny on the file, with `.env` and the setup code, mirrored by the editor's read check, which compares the file on disk, not the path's spelling, and no directory above it can be renamed ([computer.md](computer.md#the-rails)); and his shell cannot connect to :8000 or :3000 (nor the WhatsApp bridge, nor either database), so a session signed inside the shell, which redaction never sees, has nowhere local to go. Keep the key in that file (leave `JWT_SECRET_KEY` unset): a value in `.env` is in the backend's environment, which the programs it starts inherit ([trust-boundary.md](trust-boundary.md)). The shell is not a containment boundary, though: code it plants where unsandboxed programs run (a LaunchAgent, a shell startup file) could read the file as the owner ([computer.md](computer.md#what-the-sandbox-is-and-isnt)). It is also one of the secret scan's known secrets, as defence in depth (a Codex session, dormant, can still read it by path): `secret_scan.known_secrets` reads `backend/.jwt_secret` itself (again whenever the file changes) and `auth_service` registers the key it signs with (`secret_scan.register_known_secret`), so tool output shows it as `[redacted: …]` and the egress scan blocks it ([trust-boundary.md](trust-boundary.md)). Test: `tests/test_public_session_key_redaction.py`.
- **The cookie is `Secure`** by default, which assumes HTTPS in front of Edward (a tunnel or a reverse proxy); browsers also accept a Secure cookie from `http://localhost`. For a plain-HTTP LAN setup you trust, `EDWARD_COOKIE_SECURE=off` (`auth_service.cookie_secure`). A LAN kiosk on plain HTTP otherwise needs a browser flag that treats its origin as secure ([hub.md](hub.md)).
- **Sessions renew** (2026-09-21): `AuthMiddleware` re-issues the cookie on any authenticated request once the token has less than half its life left (`auth_service.should_renew_session`); login, setup and renewal all write the cookie through `auth_service.set_session_cookie`. Before this the 30-day cookie was a cliff: on the reference install a `/screen` tab that never logs in by hand went from steady 200s to 85,000 401s a day when its cookie expired (2026-09-20). A tab whose cookie already died still has to log in once. Test: `tests/test_auth_session_renewal.py`.

## The household photo door

(`backend/services/photo_door_auth.py`, `backend/routers/photo_door.py`, `frontend/app/photos/`; 2026-10-11.) A small home-screen app at `/photos` with its own password, for someone else in the household (`EDWARD_HOUSEHOLD`): the hub's screensaver album and its screensaver settings, nothing else.
- **Off unless configured.** `PHOTO_DOOR_PASSWORD_HASH` holds a bcrypt hash of the door's password, read from the environment only (`.env`) — there is no built-in password. Put the hash in `.env` in **single quotes**, so every `$` in `$2b$12$…` stays as written whichever reader parses the file (the backend's python-dotenv, the scripts' `scripts/lib/edward-env.sh`, or a shell that sources it by hand). Make one with the backend's python (bcrypt is in its venv, not in macOS's `python3`): `cd backend && .venv/bin/python -c "import bcrypt, getpass; print(bcrypt.hashpw(getpass.getpass().encode(), bcrypt.gensalt()).decode())"`. Unset or not a bcrypt hash (a warning in the log), the door is off: a login answers 403 with the reason, every other door route answers 404, and `GET /api/photo-door/auth/status` returns `{"authenticated": false, "enabled": false}`.
- **Its own session.** The cookie is `photo_door_token`, a 90-day JWT with `sub: "photo_door"`, renewed past half its life, `Secure` like the owner's. `auth_service.verify_token` accepts only `sub: "user"`, so a door token never opens the owner's app; `AuthMiddleware` lets the door cookie through only on `/api/photo-door/*`, and the owner's own session opens those routes too. `/api/photo-door/auth/status|login|logout` are public; the login shares the owner's rate limit. Settings changes made through the door are recorded as `photo_door`.
- **Its own app.** The page has its own manifest (`public/photo-door-manifest.json`, `start_url` and scope `/photos`), no app shell and no `AuthProvider`, and talks only to `/api/photo-door/*` (album list, upload with HEIC conversion, thumbnails, rotate, delete, screensaver settings), which reach the same files and settings row the hub reads. The service worker never caches `/api/photo-door/*`.
- Tests: `tests/test_photo_door.py`, `__tests__/photoDoor.test.tsx`. Routes: [api.md](api.md).

## The PWA's auth and caching rules

- **PWA auth rules** (2026-09-21): the Workbox runtime rules live in `frontend/pwa-caching.js` (pinned by `__tests__/pwaCaching.test.ts`): `/api/auth/*` is NetworkOnly and app data is never cached — the auth check used to be StaleWhileRevalidate for an hour, so a phone with a dead cookie could be told "authenticated" from cache, render, 401, bounce to `/login`, and loop. `lib/authSession.ts` holds the other half: the login page leaves only on the server's verdict (`authChecked`, not the optimistic localStorage hint), and a 401 anywhere (`authFetch`, the chat stream, the `/screen` pollers) clears the hint and goes to `/login?redirect=<page>` once.
- **An unreachable server is not a verdict** (2026-09-26): only a real `/api/auth/status` answer (`authVerdict`) decides; a 500 while uvicorn restarts or a tunnel's 502 keeps the hint and retries (`authRetryDelayMs`, 1 s doubling to 30 s, and at once when the network or the tab returns; `AuthContext.unreachable`), so the app renders with Edward "Offline" instead of sending a good cookie to `/login`.
- **Redirects stay on the site**: `lib/loginFlow.ts::loginRedirectTarget` accepts only a same-site path — control characters and backslashes are refused (the URL parser read `/\t/evil.com` as `https://evil.com`) and `/`, `/login` fall back to `/today`; the login page never leaves while `needsSetup` (that looped /login ↔ /today).
- **The setup form** (2026-10-12): while there is no password and the server says `setup_code_required` (`lib/loginFlow.ts::asksForSetupCode`), `/login` shows a "Setup code" field with the hint "It's in backend/.setup_code on the Mac Edward runs on." and won't submit until the password and the code are both filled; `api.setupPassword(password, setupCode)` sends `setup_code`, and `authVerdict` and `AuthContext` carry `setupCodeRequired`. A refused setup shows the server's own words (`loginErrorCopy(message, {setup: true})`: a wrong code, "only on the Mac Edward runs on", "already set"), never "That's not it", which reads as a wrong password and is what a phone used to show; after a refused code the code field takes the focus. A failed setup re-checks `/api/auth/status`, so a stale setup form turns into the sign-in form once a password exists. Tests: `__tests__/loginSetupCode.test.tsx`, `loginFlow.test.ts`, `authSession.test.ts`.
- **Sign-out clears what the tab holds** of the owner's (`clearSessionContent`: the Today cache, composer drafts, the cached mind/now answer) and fires `edward:signed-out`; the attachments the composer kept for each thread go too (`lib/draftFiles.ts` empties on that event). Tests: `__tests__/authSession.test.ts`, `authResilience.test.tsx`, `loginFlow.test.ts`.
- **The login page** greets the owner by `EDWARD_OWNER_NAME` ("Welcome back." when it is unset) and carries a hidden username field (`edward`) so password managers save one entry for the site.
- **The service worker and new builds** (2026-09-27): `/build-id` is NetworkOnly. Workbox matches a rule against the whole URL, so `pwa-caching.js`'s `handlerFor` does too — a pattern anchored at the path (`^/build-id`) passed the old test and never matched in the real worker. The hub's photos and the photo door's routes are NetworkOnly and sit above the image rule: Workbox takes the first matching route, and `/api/hub/photos/x.jpg` ends in `.jpg`, so it used to be served from cache for 30 days after it was deleted. Each build's `sw.js` / `workbox-*.js` travels with the build (`<build>/EDWARD_PWA/`), so a staged deploy never writes the live `public/` and a rollback restores its own worker ([ops-health-backups.md](ops-health-backups.md#the-frontend-is-a-production-build)). `public/sw-push.js` (push handling, tracked) carries a copy of `notificationNav`'s helpers; `__tests__/swPush.test.ts` pins that they agree.
