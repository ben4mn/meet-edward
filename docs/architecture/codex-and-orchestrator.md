# Codex: the fallback provider, sessions, workers, the wishlist and evolution

Three different things share the name Codex in this codebase: the **Codex fallback provider** (model calls through OpenAI's Codex backend instead of the Claude API — unofficial and opt-in), **Codex sessions** (`codex exec` runs a coding task in a sandbox) and the **workers** that started them. This file covers the last two and the containment they run under since 2026-09-27, custom MCP servers' environment, and the history of self-evolution: v1 removed on 2026-09-12 and the wishlist that replaced it.

## The Codex fallback provider (unofficial, opt-in)

Edward makes every model call through the Claude API (`EDWARD_LLM_PROVIDER` unset or `anthropic`, the default; [llm-and-quota.md](llm-and-quota.md)). `EDWARD_LLM_PROVIDER=codex` switches the builders to `ChatCodexResponses` (`services/codex_chat_model.py`), which reaches **ChatGPT's private Codex backend** with the Codex CLI's OAuth login (`~/.codex/auth.json`, or `CODEX_AUTH_PATH`) and its client id. That is not a public API: it may break at any time and may conflict with OpenAI's terms. It is kept because the reference install ran on it for months and the code is tested; a new install should not depend on it. `OPENAI_API_KEY` points the same manager at the public OpenAI API instead. With the provider unset, the Codex rate-gate meter is never restored or fetched at startup and `codex_calls` stays empty. The model catalog, the quota meter, the rate gate and the OAuth refresh are in [llm-and-quota.md](llm-and-quota.md).

## Workers and Codex sessions are dormant

**The tools are gone; the services stay (2026-10-11).** The toolset rebuild ([computer.md](computer.md)) deleted `spawn_worker`, `check_worker`, `list_workers`, `cancel_worker`, `wait_for_workers`, `send_to_worker` and `spawn_cc_worker` (on the reference install: one worker call and no Codex session in the month before), and the six custom-MCP self-service tools (no calls). Long work now runs as a background job in Edward's own shell plus a scheduled wake to come back to it; he codes in his own clones under `~/edward-evolve` with the shell and the file editor, and the live checkout is protected by the computer's rails rather than an argv and cwd allowlist. The orchestrator, `cc_manager_service`, `codex_cli_service` and their routes and panels stay, with nothing creating tasks; `codex_paths.protected_roots()` stays because `sandbox_env` reads it. What follows is how they work, for anyone who wires them back in.

## Orchestrator (workers)

(`backend/services/orchestrator_service.py`, `backend/services/orchestrator_models.py`, `backend/routers/orchestrator.py`)
- Spawned lightweight worker agents (mini-Edwards) that ran inside Edward's process via `chat_with_memory()` (turn source `worker`, model calls labelled `turn:worker`).
- Workers had full tool access, memory retrieval and state persistence; the wishlist tools were bound for them too; `forget_about` never was.
- Worker conversations appear in the sidebar with source `orchestrator_worker`; they are Edward's own threads, so extraction from them never yields the owner's standing instructions ([mind.md](mind.md)).
- DB tables: `orchestrator_tasks`, `orchestrator_config`; crashed worker tasks are recovered at startup (the last step of the lifespan).
- REST API: `GET /api/orchestrator/tasks`, `GET /api/orchestrator/tasks/{id}`, `GET /api/orchestrator/tasks/{id}/events`, `POST /api/orchestrator/tasks/{id}/message`, `POST /api/orchestrator/tasks/{id}/cancel`, `GET /api/orchestrator/status`, `GET/PATCH /api/orchestrator/config`. Tasks were created by the tools, never over REST.
- Frontend: `OrchestratorPanel` — Edward tab → Work → **Workers** (slug `orchestrator`; task browser, cancellation, streaming events; `?id=<task>` opens one).

## Codex sessions

(`backend/services/codex_cli_service.py`, `backend/services/cc_manager_service.py`, `backend/services/codex_paths.py`, `backend/services/sandbox_env.py`)
- `spawn_cc_worker(task, cwd?, read_only?, wait?)` → `orchestrator_service.spawn_cc_task` → `cc_manager_service` → `run_codex` ran a coding task through `codex exec`, streamed as `cc_*` events (and inline in the chat stream when `wait=True`: `cc_session_start`, `cc_text`, `cc_tool_use`, `cc_tool_result`, `cc_session_end`; the work rail renders them). `claude_code_service.py` (an older `claude-agent-sdk` runner) was dead code and is gone.
- A concurrency semaphore separate from the internal workers' (prevents starvation); DB table `claude_code_sessions` (the name predates `codex exec`); one `codex_calls` row per `codex exec` turn (`turn_source="codex_exec"`, the only trace of that spend).
- Replies open with a fixed phrase so the journal can read them: "Codex session completed (task …).\n<summary>", "Codex session started. Task ID: …", "Codex session failed (task …): …". A failure is one line that names Codex ("Codex error: <reason>", "Codex failed: <summary>", "Codex session timed out after Ns"); the traceback goes to the log beside the task id, never into the task's error.

### Containment (2026-09-27)

**Why**: `run_codex` defaulted its cwd to the live `backend/` and ran `codex exec --approve-for-me` there — write access to the code production runs from (a session on the reference install did exactly that on 2026-09-07); it inherited the owner's `~/.codex/config.toml` (computer-use and browser plugins, an MCP server, a notify hook) and every secret in the backend's environment; and it was not taint-gated, so a scheduled event, a heartbeat reply or a wake that had read a web page could start a coding session whose task came from that page.

- **Where Codex may run** (`services/codex_paths.py`, stdlib only): a cwd must be a directory strictly inside the scratch root (`EDWARD_CODEX_SCRATCH_ROOT`, default `~/edward-scratch/codex`) or inside a registered linked git worktree on an `evolve/*` or `edward/*` branch under a worktrees root (`EDWARD_CODEX_WORKTREE_ROOTS`, `os.pathsep`-separated, default `~/edward-evolve`, which only Edward's own flow creates; the root itself is not a worktree; the branch is read from git's own files, never by running git), and must neither sit in nor hold a protected root. The owner's worktrees (`EDWARD_HUMAN_WORKTREE_ROOTS`, default `~/edward-worktrees` — where people and their coding agents work on the code that gets deployed) are refused like a protected root even if named as a worktrees root (a pre-deploy review found any directory there used to pass, git or not). The protected roots are the checkout this code runs from, `EDWARD_LIVE_REPO` (default: that same checkout) and `EDWARD_RELEASES_DIR` (default `~/edward-releases`). It is an allowlist because the first version refused only a cwd *inside* a protected root, so `cwd="~"` passed and workspace-write — whose writable root is the whole cwd subtree — handed Codex the live repo; and a denylist can never name everything production runs (the apple-mcp clone, the LaunchAgents, the Homebrew python the venv is built on). Paths are compared after resolving `~`, symlinks and `..`, case-folded for APFS, and by identity (`st_dev`, `st_ino` of the path and each parent) — realpath does not follow APFS firmlinks (`/System/Volumes/Data/Users/…` is `/Users/…`) and APFS ignores Unicode normalization. No cwd means a fresh `~/edward-scratch/codex/<session id>`. Refused at every level — the tool (`Tool error:`), `orchestrator_service.spawn_cc_task` before any task row, and `run_codex` (an error event, nothing spawned). **Codex never runs in the live tree.** Tests: `tests/test_spawn_cc_worker_refuses_live_tree.py`.
- **The argv** (`codex_cli_service._build_codex_cmd`; checked against `codex exec --help` for codex-cli 0.153.2):
  `codex exec --json --ephemeral --ignore-user-config --ignore-rules --skip-git-repo-check -s workspace-write|read-only --config approval_policy="never" [-m <model>] [--config model_instructions_file=<path>] [-C <cwd>] -- <task>`
  - `--ignore-user-config` skips the owner's `config.toml` (auth still comes from `CODEX_HOME`); `--ignore-rules` skips execpolicy `.rules` files, which `--ignore-user-config` does not cover — an "always allow" given in the owner's own Codex would otherwise auto-approve that command prefix here; `--ephemeral` keeps no session files; `--skip-git-repo-check` because a scratch directory is not a repo (0.153.2 refuses "Not inside a trusted directory" otherwise).
  - **Write sessions are `-s workspace-write` with `approval_policy="never"`**, not `--approve-for-me`: that flag routes every request to leave the sandbox (a write outside the worktree, the network) to an automatic reviewer that can approve it. With `never` such a request fails (a smoke run wrote in its scratch dir and got "operation not permitted" writing to `~`). A read-only request (`read_only=True`, threaded through the cc manager and the inline streaming path) is `-s read-only`.
  - **The task is the positional after `--`**: right after `exec`, clap read a task starting with "-" (a markdown bullet list) as an option and died in under a second, a task that is exactly "review", "resume", "fork" or "help" ran that subcommand, and a flag-shaped token was taken as that flag.
  - Instructions go through `model_instructions_file`, the key 0.153.2 reads; the old `experimental_instructions_file` is unknown to it, and codex drops an unknown `-c` key silently.
  - The model is always passed: from 2026-05-18 to 05-26 every session died because `codex exec` without `-m` fell back to a model ChatGPT-account auth no longer accepted.
  - History: codex-cli 0.153 dropped `--full-auto` (2026-09-05) and 0.153.2 refused `--sandbox` beside `--approve-for-me` (2026-09-07) — each killed every session in under a second. Pin the argv in `tests/test_codex_cli_cmd.py` when the CLI changes again.
- **Preflight** (`codex_cli_service.codex_preflight`): before any session, `codex --version` and `codex exec --help` (never a task) are checked against the argv contract — every flag `_build_codex_cmd` can emit, derived from the builder so it cannot drift. A success is cached 300 s, a failure 20 s (`PREFLIGHT_FAILURE_TTL_SECONDS`: a transient failure during `brew upgrade --cask codex` used to refuse sessions for five minutes); one log line per distinct failure, logged again after a recovery. `backend/scripts/codex_probe.py` prints the version, the contract and whether `codex sandbox` (seatbelt) can reach localhost Postgres — on 0.153.2 read-only and workspace-write both block :5433 and :5432 (EPERM), and with `sandbox_workspace_write.network_access=true` both are reachable, production included. So database gates run outside Codex, and **`network_access` must stay off**. Tests: `tests/test_codex_preflight.py`.
- **The environment is an allowlist** (`sandbox_env.sandbox_env()`): `PATH`, `HOME` (Codex finds its auth in `$HOME/.codex`), `CODEX_HOME` when set, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_*`, `TERM`; `DATABASE_URL` and `TEST_DATABASE_URL` = the test database on :5433 (never :5432); `EDWARD_FAKE_EMBEDDINGS=1`, `GRAPHITI_ENABLED=false`, `GRAPHITI_INGEST_ENABLED=false`. Nothing else, never a `.env` — it used to copy all of `os.environ` (Twilio, VAPID, the JWT secret, model keys). Every absolute `PATH` entry in or under a protected root is dropped: the live backend's PATH carries `<checkout>/backend/.venv/bin`, which holds the only `pip` and `python` on PATH, so a `pip install requests` inside a session would have landed in the venv production runs on. A session that needs Edward's dependencies calls that python by its full path. Tests: `tests/test_codex_env_allowlist.py`, `test_db_safety_guard.py`.
- **What the allowlist does not do**: Codex's seatbelt allows full-disk reads in every mode — a read-only `codex sandbox` from a minimal env read the live `.env`, `~/.codex/auth.json` and `backend/.jwt_secret`. So a session's output and error are scanned for secrets before the task row is written (`cc_manager_service.withhold_secrets`, [trust-boundary.md](trust-boundary.md)). Keeping those files unreadable (a restricted-read profile, a separate macOS user) is not done.
- **Taint-gated and journaled**: `spawn_cc_worker` is in `taint_service.GATED_SEND_TOOLS` like `add_mcp_server` (shadow: `taint/would_gate` and it runs; `on`: held for the owner, [trust-boundary.md](trust-boundary.md)); the gate runs before the streaming loop's inline Codex path, so a held spawn never starts. It is a journal commitment, and an unattended turn that starts Codex leaves an `acted` entry the owner sees ([mind.md](mind.md)).

## Custom MCP servers' environment

`custom_mcp_service._build_server_launch_spec` used to build `env = {**os.environ, **env_vars}`: every npx/uvx server Edward installed — code chosen by a package name, restarted on every boot — ran with the live `DATABASE_URL`, Twilio, VAPID, the JWT secret, tunnel API tokens and every model key. Since 2026-09-27 it inherits only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_*`, `TERM` (`custom_mcp_service.inherited_env`), then the server's own `env_vars`, then the npm/uv/corepack/XDG cache defaults. A custom server still runs unsandboxed as the owner's user and can read secrets by path, which is why installing one is taint-gated and journaled and its tools are outward ([trust-boundary.md](trust-boundary.md)). The built-in apple-mcp and WhatsApp servers (`services/mcp_client.py`) pass no env, so the MCP SDK gives them only its default set. Test: `tests/test_custom_mcp_env_allowlist.py`. A custom GitHub server with 26 write tools and its token in plaintext `env_vars` was removed from the reference install on 2026-09-27; a fresh install has no custom servers. More on custom MCP: [integrations.md](integrations.md).

## Edward's wishlist, and evolution

(`backend/services/wishlist_service.py`, `backend/routers/wishlist.py`, `frontend/components/settings/WishlistPanel.tsx`)
- **The self-evolution pipeline is gone** (2026-09-12). Ten days of cycles had produced zero merges; the dream judge, Codex worktrees, gates, review, merge, restart, rollback, proposals and signature cooldowns were all removed, with their tables (`evolution_config`, `evolution_history`, `evolution_proposals`, `dream_signature_cooldowns` — dropped in `init_db`). Edward cannot change his own running code. **Do not rebuild the old self-coding loop.** A successor (Evolution v2) was designed after it: propose → find the code → a locked-down `codex exec` → run the new version or fall back, with extensions before core, the gate outside what the builder can change, immutable releases with automatic rollback, and the owner approving every core deploy until a trust ladder opens. Only its Phase 0 — the containment above — shipped; the rest is not part of this release. Build anything like it that way, never as the v1 loop.
- What replaced it: Edward keeps a wishlist. **Since the toolset (2026-10-11) its tools are not among the 14** (the premise went with the self-coding loop) — they are bound only under `EDWARD_TOOLSET=legacy`; the list, its routes and the owner's panel stay. The tools: `wish_for_feature(title, why, detail?, priority?)`, `list_wishlist(status?)`, `update_wish(id, status?, detail?)`; the "## Your wishlist" prompt section tells him to log what he wishes he could do, a tool he lacks, a recurring failure a code change would fix, or something that would help the owner — and never to promise he will build it. A repeated wish bumps `times_wanted` instead of duplicating (`wishlist_service.normalize_title` / `find_existing` are pure and tested).
- The owner reads and manages it in Settings → Work → Wishlist (status segment, priority, delete, and their own "Add a wish" — a half-written wish holds a new build's reload); recent wishes appear in the Work room activity timeline and as "Wished for: …" rows in the Today digest.
- REST: `GET /api/wishlist?status=`, `POST /api/wishlist`, `PATCH /api/wishlist/{id}`, `DELETE /api/wishlist/{id}`.
- Still here and unrelated to evolution: `self_observations` (`services/observe.py`; fed by tool failures, collapsed by signature), `services/dream/` (memory retrieval: query cache, hot memories, speculative recall — nothing to do with dream synthesis), and memory consolidation, whose flags/connections UI is the "Dreaming" panel in the Memory room (`/settings/dreaming`).
- **The 2026-09-07 incident** (kept for the lesson): an evolution cycle ran pytest with the live `DATABASE_URL` and `conftest.clean_db` truncated the production database; it was restored from the night's backup the same day. `services/sandbox_env.py` points every spawned `codex exec` at the test database on :5433, and conftest never uses a database not named `*_test` (it falls back to `edward_test` on :5433), refuses a `*_test` URL on :5432, and `clean_db` refuses to truncate a non-test database ([testing.md](testing.md)). **Never run the backend test suite with the live DATABASE_URL exported.**
