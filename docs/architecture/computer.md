# Edward's computer: one toolset, two browsers, his own eyes, the web and the owner's calendar

The toolset rebuild of 2026-10-11. The design decision behind it: Edward gets a real computer, with broad access, and the risks that come with it are accepted. The rails that still hold are: no test or harness ever messages a real person or touches the owner's real Chrome; the egress secret scan; never a second Google Chrome; never a test on the production database (:5432); never deleting the owner's memories; and never starting or joining other people's conversations unasked.

## Why

- **The agent the owner talks to had the weakest hands.** Pings arrived as `mention` / `messages` wakes with a small mind toolset: no shell, no browser, no image, no code. Three of 21 pings in the audit window failed for that alone: one could not see the photo it was sent, one had no browser, one was told "desktop control … not available".
- **The big toolset was dead weight.** 58 of 116 chat tools were never called in 30 days and carried 9.3K schema tokens.
- **Real holes sat where nothing looked.** The Python sandbox passed the backend's whole environment, the live `DATABASE_URL` included, to every snippet; apple-mcp's calendar call timed out 201 times in 8.4 days; the page fetcher failed 18 % of the time and refused to run without a Brave key.

## The toolset

Fourteen tools, the same list on every surface (chat, voice, pings, wakes, the pulse, scheduled events), so its prompt-cache entry is shared by every same-model turn. Limits per surface moved from hiding tools to the executor's per-turn policy, and a refused call is an honest `Tool error:`, not a missing tool ([tool-loop.md](tool-loop.md)).

| tool | what it is | module |
|---|---|---|
| bash | a persistent shell per thread in `~/edward-home` (Anthropic `bash_20250124`) | `services/computer/`, `services/toolset/computer_tools.py` |
| str_replace_based_edit_tool | view, create and edit files (Anthropic `text_editor_20250728`) | the same |
| `web_search`, `web_fetch` | Anthropic's server tools per model, local fallbacks | `services/toolset/web.py` |
| `browser` | his own invisible browser (Playwright's headless shell) | `services/toolset/browsers.py`, `services/headless_browser.py` |
| `chrome` | the owner's own Chrome through the Edward extension (off unless `EDWARD_CHROME_HANDS=on`) | `services/toolset/browsers.py`, `services/browser_hands.py` |
| `look` | images, PDFs and screens as pictures | `services/toolset/look.py` |
| messages, send_message, tell_owner, memory, schedule, screen, plan | read iMessage and mail; the one guarded send; reach the owner; memories and documents; reminders, wakes, the owner's calendar and Reminders; the screens and the widget; a visible checklist | the toolset core (`services/toolset/`) |

Every tool raises `ToolFailure` with the real reason on failure; the executor turns it into `Tool error: …` plus `is_error`. Action tools take an `action` plus flat optional arguments, and their work-rail summary is `"{action}: {detail}"`, which `frontend/lib/toolLabels.ts` reads action by action ("Opened example.com in my browser", "Searched memory for “Biscuit's meds”", "Stood down in Family"). Old tool names keep their labels for the receipts already in history. `services/toolset/_compat.py` takes `ToolFailure` and "is the owner the one asking" from the toolset core (`services/toolset/result.py`, `services/toolset/policy.py`), with the turn's source as its fallback.

## His computer: home, shell, files, rails (`services/computer/`)

`services/computer/` gives him a home directory, a persistent sandboxed `bash` per thread, and an in-process file editor: the backend of the `bash` and `str_replace_based_edit_tool` tools in `services/toolset/computer_tools.py`. One rails table (`services/computer/rails.py`) is rendered both into the macOS Seatbelt profile the shell runs under and into the `can_read` / `can_write` checks the in-process editor uses, so the two deny exactly the same things (a parity test keeps them in step).

**Reads are allowed everywhere but Edward's own credentials** (a design decision; the exception since the 2026-10-12 review). The session-signing key (backend/.jwt_secret: whoever holds it can mint the owner's session), the first password's setup code (backend/.setup_code) and `.env` (at the top and in backend/), in the checkout the backend runs from and in `EDWARD_LIVE_REPO` (`rails.SECRET_FILES`, `rails.read_deny_files`), can't be read, replaced, moved or linked by the shell or the editor, however the path is spelled, and `look` and `send_message`'s files refuse them too. Redaction could not be the protection: code run in the shell uses a key without the model ever seeing it, so redaction never gets the chance. With them, the shell may not open TCP to Edward's own ports, 8000 and 3000, or to the WhatsApp bridge's (8080), on any address, so a session signed or borrowed in the shell has nowhere local to go ([trust-boundary.md](trust-boundary.md)), and it reaches neither of Edward's databases. Everything else is readable; command output and file `view`s are still scanned and redacted (`secret_scan.redact_secrets`) before the model sees them, as defence in depth. A side effect: a script in the live repo that loads `.env` fails when he runs it. `EDWARD_COMPUTER_SANDBOX=off` is an emergency switch that runs the shell unsandboxed (and logs `[computer] UNSANDBOXED` on every command).

**This is a guard against accidents and against a talked-into command, not a containment boundary.** The shell runs as the owner's macOS user, and outside the paths below it can write what the owner can, including files that unsandboxed programs later run. What it covers and what it doesn't: [What the sandbox is (and isn't)](#what-the-sandbox-is-and-isnt).

**Identity, not spelling** (review 2026-10-12). macOS volumes usually compare names case-insensitively and `realpath` keeps the case the caller typed, so `<repo>/BACKEND/.JWT_SECRET` used to open the real key while the editor's string comparison let it through (Seatbelt resolves case itself and refused it). Every in-process check now compares what is on disk (`rails.identity`): the `(st_dev, st_ino)` of the path, or of its nearest existing ancestor plus the remaining names, folded the way that volume compares them. A case variant, a symlink and a hard link of a credential are the credential; a case variant of the live repo is the live repo.

### His home: `~/edward-home`

`home.ensure_home()` lays it out at boot (`EDWARD_HOME` overrides the path): `bin/` (on PATH), `skills/`, `projects/`, `downloads/`, `jobs/` (background logs), `tmp/` (TMPDIR), `.venv/` (his Python 3.12 venv, created lazily on the first shell, from Homebrew's python3.12 under `HOMEBREW_PREFIX`), `.npm-global/`, `.out/` (the full output of commands that were cut for the chat) and `.trash/` (the editor's cheap undo). Backend-owned and not writable by him: `~/.edward-computer/` (`profile.sb`, `sessions/*.pid`).

The shell's environment is an **allowlist** (`home.shell_env`): no `.env` secrets, no API keys, and no database: neither `DATABASE_URL`, `TEST_DATABASE_URL` nor libpq's `PG*` settings, which are stripped even when the backend's own environment holds them (review 2026-10-12; until then they pointed his shell at the test cluster on :5433, below). A project that needs Postgres runs its own in `~/edward-home`.

`ensure_home` writes `README.md` and `SKILLS.md` into his home only when nothing (a file, a link, even a dangling one) is there, through `rails.open_checked`: the home is his to change, and the backend, which runs outside the sandbox, never writes through a path he could have pointed elsewhere.

`(allow default)` plus these denies; SBPL takes the **last matching rule**. Verified on macOS 15.7 and in `test_computer_profile_sandbox.py` against scratch paths and throwaway ports: never :5432, :5433, a live path, Chrome or osascript. The credential read-deny and the port denies were verified with the real `sandbox-exec` on macOS 15 (2026-10-12): `cat`, a symlink, relative and `..` paths, a case variant, `cp -c`, `ln` and python all fail to read, `mv` and an overwrite fail, and IPv4 and IPv6 loopback connections are both refused. The ancestor rule was verified the same way: renaming the repo's parent or grandparent, or the scratch root, fails, while creating, renaming and removing a sibling file or directory inside them works; a protected link can't be repointed (`test_a_parent_of_the_repo_cannot_be_renamed_out_from_under_the_rules`, `test_a_case_variant_does_not_get_past_the_sandbox`, `test_a_protected_link_cannot_be_repointed`, `test_the_test_cluster_is_refused_like_production`). `rails.rail_hint` names these rails too: "[rail] the session key, the setup code and .env are the backend's own credentials — your shell and editor can't read them"; for a refused connection (curl says "Failed to connect", not EPERM) "[rail] your shell can't call Edward's own API (ports 8000 and 3000) or the WhatsApp bridge — use your tools"; and for either database "[rail] Edward's databases are off limits to your shell — production (:5432) and the test cluster (:5433) …".

**The protected kegs follow `HOMEBREW_PREFIX`** (`home.homebrew_prefix()`: the variable, else `/opt/homebrew` if it exists, else `/usr/local`). The same prefix puts Homebrew on his shell's PATH and finds his venv's python3.12.

`rails.precheck` is a mistake guard, not the boundary (Seatbelt is): it refuses `brew upgrade` with no formula, `brew upgrade/reinstall/uninstall/rm/unlink/link/pin/unpin` of a protected formula, `rm -rf` of a Homebrew core directory, and everything but `rm`/`du`/`ls`/`df` when the disk is below `EDWARD_SHELL_MIN_FREE_GB`. `rails.rail_hint` adds one line to a command's output naming the rail it hit.

Edward may `pip install` into his own venv, `uv`, `npm`/`npx`, and `brew install` ordinary formulae. A `brew install` whose formula runs a build or post-install hook can fail inside the sandbox (nested `sandbox-exec` returns "Operation not permitted"), so pip, uv and npm are preferred; this is a known limitation, not a hang.

### The shell: `shell.py`

One `/bin/bash --noprofile --norc` per conversation under `sandbox-exec -f profile.sb`, spawned with `start_new_session=True` so the harness owns its process group. Each command runs between sentinel markers (written to fd 9, so an `exec 1>…` redirect can't hide the sentinel) with stdin from `/dev/null` (so a command that reads stdin can't swallow it). `bash -n` syntax-checks the command first, so a stray quote or brace can't hang the session.

- A **non-zero exit is a normal result** (the command ran). A tool error is only a harness outcome: a timeout, a kill for memory or disk, a shell that died, a refused rail, or the sandbox failing to start. The error line leads the text (any partial output follows), so the loop flags it (`status="error"`, the ledger's failure count). `exit` in a command ends the session normally; the result says the next command gets a fresh shell (`tests/test_computer_tool_errors.py`).
- The Settings row (Shell/Bash) reads `computer.status()`: the open sessions, "UNSANDBOXED" under the emergency switch, and an error when `sandbox-exec` is missing.
- Per-command timeout `EDWARD_SHELL_TIMEOUT_S` (180 s). On a timeout the harness kills the session's process group and the shell restarts. Long work is a `nohup … &` job plus a `schedule` wake (background jobs die with an Edward restart).
- A 5 s watchdog kills the group if the session's process tree exceeds `EDWARD_SHELL_MAX_RSS_MB` (2048) of RSS or the disk falls below the floor.
- At most `EDWARD_SHELL_MAX_SESSIONS` (4) sessions; at capacity the least-recently-used **idle** one is closed. A session mid-command is never evicted for another thread (review 2026-10-11: a long build was cut off and read as the command having exited); when every session is busy, the new call is a tool error. A command the harness kills (`kill(reason=…)`) is a tool error, never "the shell exited".
- Output to the model is redacted, then capped at 30,000 characters (head and tail, the full text spilled to `~/edward-home/.out/`), then the exit-line footer and any rail hint.
- `computer.startup()` sweeps the shell process groups a previous run recorded, but only when the group leader is still one of Edward's shells (its command line names the profile, or its environment marker matches), so a reused PID that now belongs to Postgres or Chrome is never killed.

If `sandbox-exec` is missing or the profile won't apply, `bash` and the editor fail closed with a plain `Tool error:`: they never silently run unsandboxed (only the explicit `EDWARD_COMPUTER_SANDBOX=off` does that).

### The editor: `editor.py`

`view` / `create` / `str_replace` (exactly one match) / `insert`, in-process under the same rails: `can_write` for writes, `can_read` for `view`, `str_replace` and `insert` (`~` and relative paths resolve against `~/edward-home`). The backend runs outside the sandbox, so the editor never trusts a path between the check and the write: it reads and writes through one descriptor from `rails.open_checked` (review 2026-10-12), which checks the path, opens its directory by descriptor and checks that directory's canonical path, opens the file relative to it with `O_NOFOLLOW` (a link swapped in after the check is refused, never followed), then checks the opened file's own inode and canonical path (`F_GETPATH`) again before a byte is read or written. A write never truncates before those checks pass, an overwrite keeps the file's mode, and a file a failed check created is removed. Overwritten files are copied to `.trash` first, from that same descriptor and only after the checks (a refused file is never copied: a case-varied `.jwt_secret` once was), always as a new file, never through a link planted in `.trash`, never into a protected root. `view` output is redacted and capped at 30,000 characters. `look` reads local files through `rails.read_checked`, and the shell's spill of a long output (`.out/`) uses the same open.

### What is deliberately not a rail

The profile does not deny `sudo`, `security`, `launchctl`, `crontab` or `tccutil`, and reads are open but for his own credentials (a design decision: few restrictions, and only writes and sends wait for the owner's ask). The manual asks him to leave the host's machinery alone (no sudo, launchctl or crontab) as guidance, and `tests/test_manual_rails_are_enforced.py` keeps the manual from calling anything a rail that the profile or the precheck does not enforce. An audit on 2026-10-11 confirmed the profile reaches the login Keychain, and so anything kept there (a sudo password stored in it, for one, means root). On the reference host that was intended. **If you don't want that on your Mac**, add a deny for `~/Library/Keychains` and the `security` command to the rails table, and keep the manual in step.

### What the sandbox is (and isn't)

The Seatbelt profile is `(allow default)` plus the denies above, applied to a shell that runs **as the owner's macOS user**. It is built to stop accidents and the obvious misuse, and to protect specific things. It is **not a containment boundary**: whatever the table does not deny, the shell may do, with the owner's own permissions.

**What it protects** (the rails table):
- the code Edward runs: the live checkout and the checkout the backend runs from, the releases, his own rails directory, and every directory above them;
- the data and binaries production runs on: Postgres' data directories (production's and the test cluster's), the python@3.12 and postgresql@16 kegs and their `opt/` links;
- his own credentials: the session key, the setup code and `.env`, whatever the spelling;
- the local services that act as the owner: Edward's API (:8000, :3000), the WhatsApp bridge (:8080), and both of Edward's Postgres clusters (:5432, :5433, by TCP and socket);
- the rest of the Mac's apps: no launching or scripting apps, no second Google Chrome, signals only to his own processes; and the shell fails closed when the profile can't apply.

**What it is not.** Reads are open by design, and writes are open everywhere but the protected paths. That includes places from which unsandboxed programs later read configuration or run code: what lands there runs as the owner, outside every rail, at the next login, launch or restart. A prompt injection that reaches the shell (a web page, a message, a file he was pointed at) therefore has a way to run code as you. The rails make that deliberate work rather than one mistaken command; they don't make it impossible. That is one reason friends' pings get no shell by default ([pings.md](pings.md#the-reply-turn)).

#### What the sandbox does not prevent

The 2026-10-12 review's list, for the threat model:
- **Startup files and agents**: shell rc files (`~/.zshrc`, `~/.zprofile`, `~/.bash_profile`), `~/Library/LaunchAgents/*.plist` (Homebrew's Postgres agent included), login items.
- **Homebrew**: the whole prefix outside the two protected kegs, by design (Edward may `brew install`): `bin` and `sbin`, `node` and `npm` (which the frontend and its builds run), `cloudflared`, Homebrew's own code and every other formula. The launchers search the system's own directories first and never `~/.local/bin` or `~/bin` (`scripts/lib/edward-env.sh::edward_service_path`; the backend's start scripts put only the venv's `bin`, inside the write-protected checkout, ahead of them), run `uvicorn` and Next by absolute path, and the LaunchAgents carry `HOMEBREW_PREFIX` so no job runs `brew --prefix`. So a planted `curl` or `sips` is never the one a job runs; a planted `node` still would be.
- **Caches and clones the backend loads code from**: Playwright's headless shell under `~/Library/Caches/ms-playwright` (the backend launches it), the Hugging Face cache the embedding model is loaded from, bun (`~/.bun/bin/bun`) and `~/apple-mcp` (apple-mcp), the npx and uvx caches, and `~/whatsapp-mcp` (the bridge's own LaunchAgent runs its binary).
- **The rest of the owner's credentials**: `~/.codex/auth.json`, SSH keys, browser profiles, and the login Keychain (above).
- **Other processes' start-up environments.** Any process can read the environment another process of the same user started with (`sysctl` `KERN_PROCARGS2`), and a Seatbelt `process-info` deny does not stop it. That is why the start scripts no longer export `.env` (review 2026-10-12): `backend/start.sh` and `start-graph-worker.sh` read only the few settings they need, and the backend loads `.env` itself once it is running. Programs the backend then starts without an environment of their own inherit those values: Playwright's driver and headless shell, the media and EventKit helpers, and short-lived tools such as `sips` and `osascript`; while one runs, `.env`'s keys are readable from the shell. His shell, custom MCP servers and Codex sessions get allowlisted environments.
- **Postgres from outside the sandbox.** Both clusters accept local connections with `trust` (Homebrew's `initdb` default, and `scripts/test-pg-cluster.sh`), so any program running as the owner outside the sandbox can connect as their superuser, whose `COPY … TO PROGRAM` runs commands as the owner. The shell itself is refused both.
- **A file swapped under `send_message`**: its files are checked with `rails.can_read` and the transport copies the path afterwards, so a link swapped in between is followed (`look` and the editor open through `rails.open_checked` and are not affected).
- **The media viewer's own denied names** (`services/media/viewer.py`) compare case-sensitively; `look` checks the rail before it asks the viewer, and the viewer only ever returns media.
- **A frontend started by hand**: `./restart.sh` without the LaunchAgents runs `npm run start` with the terminal's PATH and port; only `frontend/run-launchd.sh` pins both.

**For strong isolation, run Edward as a separate macOS user**, so his shell's writes, and anything that escapes it, land in that account's home and not yours: [ADAPTING.md](../ADAPTING.md#g-edward-under-his-own-macos-user) has the steps and what they cost (his own GUI session, his own copies of Messages and the rest, Postgres with passwords). The reference install never ran that way.

### Flags (the computer)

`EDWARD_HOME`, `EDWARD_COMPUTER_SANDBOX` (on/off), `EDWARD_SHELL_TIMEOUT_S`, `EDWARD_SHELL_MAX_RSS_MB`, `EDWARD_SHELL_MAX_SESSIONS`, `EDWARD_SHELL_MIN_FREE_GB`, `HOMEBREW_PREFIX`. `EDWARD_LIVE_REPO` / `EDWARD_RELEASES_DIR` / `EDWARD_COMPUTER_WORKTREE_ROOTS` locate the protected and the evolve roots; `EDWARD_TEST_PGDATA`, `EDWARD_PG_BIN`, `EDWARD_TEST_PG_BIN` and `EDWARD_PGDATA` add their directories to the write-protected roots. A friend's ping gets none of this computer unless `EDWARD_FRIENDS_FULL_TOOLSET=on` ([pings.md](pings.md#the-reply-turn)).

## Two browsers

### `browser`: his own (`services/headless_browser.py`)

- **Playwright's bundled `chrome-headless-shell`, never Google Chrome.** `find_headless_shell` picks it under `~/Library/Caches/ms-playwright` (or `PLAYWRIGHT_BROWSERS_PATH`; `setup.sh` installs it), and `assert_playwright_executable` refuses anything outside that cache, anything under `/Applications` and anything named Google Chrome before launch; no `channel` is ever passed. A second Google Chrome instance hijacks `open -a` and `tell application "Google Chrome"`, so the single-Chrome rule holds in this layer too. The headless shell is not an app bundle.
- **http and https only.** `check_url` refuses `file:`, `chrome:`, `view-source:`, `devtools:`, `blob:`, `data:`, `javascript:` and `about:` before anything opens: this process may hold Full Disk Access, so a `file://` page could read what nothing else may.
- **Never this Mac's own services.** Every request the page makes passes `_route_guard`: literals and local names (`localhost`, `*.local`, `*.localhost`, …) are refused without DNS; anything else must resolve, and every address it resolves to must be public (private, loopback, link-local, CGNAT, multicast, reserved, and IPv4-mapped forms are refused; a DNS-rebinding name with one inside address is refused). Playwright does not route the hops of a redirect, so after every navigation and every click the final URL is checked again, and a page that landed inside is blanked and never read (`open_url`, `guard_current`). Residual risk: a subresource redirect hop is not routed, and only CORS keeps a page's script from reading it.
- **Bounded.** One working page per conversation (`page_for`), at most three, the least recently used closed first; a popup becomes the conversation's page; the whole browser closes after ten idle minutes and in the lifespan's shutdown (`main.py`). Downloads land in `~/edward-home/downloads` under a sanitized, de-duplicated name; the profile (his own cookies, never the owner's) is `~/edward-home/browser/profile`.
- **The same page actions as Chrome.** `HeadlessTarget` is a `browser_hands.CdpTarget` over a Playwright CDP session, so read, find, click, type, key, scroll and wait are the hands' own code and read the same numbered elements.
- **For link enrichment** (pings and media): `read_url(url, screenshot=False)` reads one page in a throwaway tab and never raises (a refusal is its `error`).

The tool: `browser(action=open|read|find|click|type|key|scroll|back|wait|download|close, …)`, 45 s per action.

### `chrome`: the owner's (`services/browser_hands.py` through the extension)

**Off by default.** Edward's hands in the owner's own Chrome need `EDWARD_CHROME_HANDS=on` and the unpacked extension loaded from `chrome-extension/` (see `chrome-extension/README.md`). While off, the extension socket is refused, nothing launches, raises, relaunches or quits Chrome, and every `chrome` action (and `look("chrome")`) answers "Chrome hands are off — set EDWARD_CHROME_HANDS=on and load chrome-extension/ (see its README)". The `browser` tool and the rest of the toolset are unaffected. Details: [screen-and-browser.md](screen-and-browser.md#edwards-hands-in-the-owners-chrome).

With hands on, one tool covers the actions the fourteen old `browser_*` tools had (`tabs|open|use|read|find|click|type|key|scroll|back|wait|fullscreen|steps|done`), 90 s per action. The hands' page actions take an optional `target` (none is the owner's working tab), and `screenshot_target` takes a picture over CDP `Page.captureScreenshot` **without activating the tab**: a wake must not switch the owner's active tab while they work.

**Chrome's rails** (`browsers.chrome_refusal`, checked before the action runs; the label of a clicked element is read from the page at click time):

- Typing outside a search site (`taint_service.SEARCH_TYPING_HOSTS`) or Edward's own /screen (the hosts of `EDWARD_PUBLIC_BASE_URL`, localhost and this Mac's `.local` name, read per call), pressing Enter there, and `steps` that do either, acts as the owner (a message typed into webmail goes out as them), so it runs only when the owner is the one asking in this turn.
- A click on an element labelled send, post, reply, publish, delete, remove, accept, decline, confirm, submit, unsubscribe, sign out, transfer, share, invite, RSVP, archive, forward, follow or block likewise needs the owner asking (word-bounded: "Sender details" and "Deleted items" pass).
- A payment step ("place order", "buy now", "pay", "checkout", "confirm payment", "add card", …, word-bounded so "Paywall" passes) or typing a number that passes the Luhn check is refused in every turn: the owner does those themselves.

The extension being down is a `Tool error:` that says what still works and how Chrome comes back.

## `look`: the picture itself (`services/toolset/look.py`)

`look(target, question?)` returns content blocks: a short text block, up to six image blocks (JPEG, PNG, GIF or WebP; the long edge ≤ 1600 px, scaled down with `sips` only when larger, never up — `-Z` alone upscales a sticker) and a PDF document block (≤ 15 MB). The model sees what was sent, not a second model's description.

| target | resolved by |
|---|---|
| `attachment:<chat.db rowid>`, `media:<id>`, `file:<id>`, media paths | `services.media.view` ([media.md](media.md)); its `unsupported: …` answer sends look down its own path (Messages' attachment table for `attachment:`, Edward's file storage for `file:` — a PWA upload's `file_id`, so a dehydrated upload can be opened again — and the file itself for a path) |
| an http(s) URL | a guarded fetch (the same SSRF rules on every hop, ≤ 25 MB; a web page is sent to `web_fetch` or the browser) |
| `screen` | this Mac's display (`screencapture`; needs Screen Recording permission for the backend's python, else a clear error) |
| `chrome` | Edward's working tab, over CDP, never activated (hands on only) |
| `browser` | his own page |

In a friend's ping, by default, `look` takes only what was sent in a chat (`attachment:`, `media:`), an http(s) URL and `browser`: never `screen`, `chrome`, `file:` or a path on the Mac ([pings.md](pings.md#the-reply-turn)). A local file is read through `rails.read_checked`, and the read rail is asked before `media.view` is. A turn carries at most 40 images and 15 MB of media (the API rejects bodies over 32 MB); a ping turn's count starts from what its trigger already carried (`pings.hooks.current_ping()["media"]`). Under the Codex provider the Responses converter drops images in tool output, so look answers with `attachment_vision.describe_image`'s words. **No test captures the display or the owner's Chrome**: conftest's `_never_look_or_launch` makes both screenshots raise.

## The web (`services/toolset/web.py`)

Under Claude, `web_search` and `web_fetch` are Anthropic's server tools: the search and the fetch run at Anthropic and come back inside the model's own message. The version depends on the model (`server_tool_spec`):

| model | web_search | web_fetch |
|---|---|---|
| Opus 5.5 / 5 / 4.8 / 4.7 / 4.6, Sonnet 5.5 / 5 / 4.6 (the chat, mind, pulse and voice routes) | the basic `web_search_20250305`, 8 uses | the basic `web_fetch_20250910`, 10 uses, 20K content tokens |
| Haiku 5.5 (the background route) and anything else | the basic `web_search_20250305` | the local fetch |

The search's approximate location is the owner's timezone and `EDWARD_SEARCH_COUNTRY` (a two-letter code, default `US`). **Never the dynamic-filtering `_20260209` pair** (2026-10-12). For a day Opus and Sonnet got them, and every search and fetch Edward made under Claude failed: with his other tools bound, Sonnet 5.5 calls them directly with `{"params": {"query": …}}` and Anthropic answers `invalid_tool_input` (a `web_search_tool_result_error` inside a 200, so nothing raised). On one real request 0 of 9 direct calls were well-formed; with the basic versions 6 of 6. Bound alone the dynamic tools work, through code execution — the wrapping comes with the full toolset. A version a model rejects would 400 every turn, so Haiku keeps the local fetch. `ChatClaude` binds a tool's `metadata["anthropic_tool_resolver"]` per bind, and maps any raw dynamic dict down for Haiku at request time, whoever bound it (`map_server_tools_for_model`). Server web fetch reads only URLs already in the conversation (Anthropic's own exfiltration limit). Searches cost $10 per 1,000 (`llm_pricing` prices `usage.server_tool_use`).

Locally (`EDWARD_SERVER_WEB_TOOLS=off`, Haiku's fetch, or the Codex provider) `web_search` is Brave (`BRAVE_SEARCH_API_KEY`) and `web_fetch` is `brave_search_service.fetch_page`: no Brave key needed for the fetch (it used to refuse without one), 30K characters (was 4K), `Accept-Encoding: gzip, deflate` only (an advertised brotli/zstd stream failed in `decompressobj`), every hop SSRF-guarded through an httpx request hook (redirects included), and every failure raises with what to try next: a PDF says `look`, a page with no readable text says `browser`.

## The owner's calendar (`services/calendar_service.py`)

apple-mcp's calendar call (a bun process driving Calendar over AppleScript) timed out 201 times in 8.4 days. Calendar keeps its data in `~/Library/Group Containers/group.com.apple.calendar/Calendar.sqlitedb`; with Full Disk Access granted to the backend's python (it reads `chat.db` the same way), `calendar_service` reads that file in-process, read-only, bounded at 2 s.

- **The encoding** (checked by schema and aggregate counts only, no event content): times are Core Data seconds since 2001-01-01 UTC; `OccurrenceCache` holds every occurrence, recurring ones expanded, **one row per day it touches**: the first with `occurrence_start_date` NULL and the start in `occurrence_date`, later days with `occurrence_date` at that day's start and the real start in `occurrence_start_date`. So the start is `COALESCE(occurrence_start_date, occurrence_date)`, and an occurrence is unique by (event, start). All-day occurrences run from local midnight to the last second of their last day and are shown on the owner's dates; hidden and cancelled items are left out.
- **Never an empty day for "can't read".** Every failure (no file, a schema change, a permission error, the 2 s bound) raises `CalendarUnavailable`. `mode=ro` sees the WAL; only when it can't open is an `immutable=1` read tried, and that answer is marked stale (it misses today's edits).
- **The display hook.** `display_service._calendar_read` tries the database first, apple-mcp when it can't be read, and a stale database read only when apple-mcp fails too; the cache, single flight and last-good list are unchanged. The field contract holds: `source` stays `"apple-mcp"` whenever Apple Calendar answered (the mind's pack and the stale note check exactly that) and `via` says how (`sqlite` or `mcp`). That one function feeds every calendar reader: the pack, the pulse's signals and `GET /api/display/calendar`.
- **Health.** `GET /api/health/report` has a `calendar` line: which source served last (`sqlite`, `mcp`, `unavailable`) and why not.
- **Flags.** `EDWARD_CALENDAR_SQLITE=off` goes back to apple-mcp only; `EDWARD_CALENDAR_DB` points the reader elsewhere. Conftest turns the reader off, so no test reads a real calendar; `tests/test_calendar_service.py` builds its own database. The schema is private to Apple and may change with a macOS update; the fallback and the health line cover that.
- **`schedule(calendar)`** reads a window that starts at the owner's local midnight and runs 7 days by default. Until 2026-10-11 it started at UTC midnight, which in a US Central zone is 7 pm the evening before, so after 7 pm it skipped the rest of the day. Every line ends with `id=cal-<UUID>-<occurrence>` (the occurrence in Core Data seconds): the id the writes take.

`calendar_service` itself stays read-only. Changes the owner asks for go through the EventKit helper below.

### Reminders and EventKit (2026-10-11)

The design decision the same day: block and restrict little. **Reads are open in every turn on every surface** (chat, voice, the hub, pings — friends' included —, wakes, events); what others wrote in a calendar or a reminder is a taint ledger signal, never a block. **Writes happen when the owner asks**: one predicate, `TurnPolicy.may_change_owners_calendar()` (`services/toolset/policy.py`), which is `owner_asked` today; flip that one line to let Edward act on his own initiative. So the owner's chat, voice, widget, Alexa, their own ping and a task they scheduled may add, move, change or delete an event (inviting people included) and add, check off or delete a reminder. The household hub's voice, friends' pings, every wake, the pulse, Edward's own events and the heartbeat get `Tool error: changing <owner>'s calendar or Reminders is for when they ask — this turn isn't theirs. tell_owner what you'd change.`, and the helper is never called.

- **Reading Reminders** (`services/reminders_service.py`, `schedule(reminders, calendar=<list>, query=)`): Reminders keeps one Core Data store per account in `~/Library/Group Containers/group.com.apple.reminders/Container_v1/Stores/Data-*.sqlite`; the backend's python reads every one in-process, read-only (`mode=ro`, the `immutable=1` fallback marked stale), bounded at 2 s, merged soonest-due first. Checked by `PRAGMA table_info` and aggregate counts only: `ZREMCDREMINDER` (title, notes, completed, marked for deletion, a due date in Core Data seconds, all-day, flagged, priority, the list) joined to `ZREMCDBASELIST.ZNAME`; three identifiers — `ZCKIDENTIFIER` (CloudKit; NULL in an Exchange/CalDAV store), `ZDACALENDARITEMUNIQUEIDENTIFIER` and a 16-byte `ZIDENTIFIER` UUID. An all-day due date floats: its stored instant is midnight UTC, so its UTC date is the owner's date. The required columns are checked before every read; a missing store, a schema change, a bad file or the bound raise `RemindersUnavailable`, never an empty list passed off as the truth. Lines read `- Call the vet · due today 5:00 pm · flagged · [Pets] id=rem-…`, at most 60. A list that matches none of the owner's (a typo, Groceries for Shopping) answers "<owner> has no Reminders list called “Groceries” — their lists: …" (`reminders_service.list_names`), never "No open reminders in Groceries".
- **The helper** (`backend/tools/eventkit/edward_eventkit.swift`, called from Python by `services/eventkit_service.py`): one signed binary over EventKit, the only write path. `edward-eventkit <command>` takes one JSON object on stdin (never argv: `ps` would show an event's title and notes) and answers one JSON line; exit 0 ok, 2 bad input, 3 a failure in its own words (`not_found`, `read_only`, `ambiguous`, `save_failed`), 4 access.
  - Commands: `access` (authorization only, never prompts), `request events|reminders` (manual only), `calendars` / `lists`, `event_add` / `event_update` / `event_delete`, `reminder_add` / `reminder_complete` / `reminder_delete`, `selftest` (JSON, dates, the embedded plist and the attendee probe; it never makes an `EKEventStore`).
  - Access is checked before any store is made; nothing in Edward ever requests it (a dialog nobody answers hangs a turn for two minutes).
  - With no calendar or list named it uses EventKit's defaults; a name matches exactly (case-insensitive), then a unique contains; an ambiguous, unknown or read-only target is an error that lists the writable ones.
  - A timed event carries the owner's zone; an all-day one is floating (`date` / `end_date`, inclusive); `event_update` with a new start alone keeps the event's length, and a date start makes it all day.
  - A write to a repeating event changes that occurrence; `span=future` reaches that one and every repeat after it ("cancel my weekly gym class", "move standup to 10 from now on"), and a reply about one occurrence of a repeating event says so. With no occurrence to go on (an id without its suffix and Calendar's database unreadable), EventKit hands back the series' master, whose "this" is its first occurrence — maybe years back — so the helper answers `ambiguous` instead (`needsOccurrence`, review 2026-10-11).
  - A reminder's timed due date gets an alarm at that time; a date alone is a floating due day.
- **When a write may or may not have happened** (review 2026-10-11): a helper that never started (not installed, wouldn't launch) is `EventKitUnavailable`: nothing changed. One that started and gave no answer (the 20 s timeout, a crash, nothing readable) is `EventKitOutcomeUnknown`, because `save(commit:true)` may already have reached Calendar; the tool says it may or may not have gone through and to read the calendar before trying again. `event_add` / `reminder_add` remember a confirmed add for ten minutes, keyed on the title, time and calendar or list (send_message's dedupe, after a duplicated event on 2026-09-14): the same add again answers "Already added “Dentist” … — not adding it twice"; a retry after an unknown outcome still runs.
- **Ids.** Reads print `cal-<CalendarItem.UUID>-<occurrence>` and `rem-<id>`; before a write, Python re-reads that row (`calendar_service.event_by_id`, `reminders_service.reminder_by_id`) and hands the helper its title and occurrence (or every identifier and the list) as hints. That the database's `UUID` is EventKit's `calendarItemIdentifier`, and which reminder identifier EventKit uses, is **not verified**: the helper tries the identifier, the occurrence of a recurring event, the external identifier, then a unique title around the occurrence. Several matches answer `ambiguous`, never a guess. Try your first write with a throwaway event.
- **Invitees.** EventKit has no public API for attendees. The helper attaches them through the private `EKAttendee` only when the class and its selectors exist (`selftest`'s `attendees_api` reports it), never KVC first (Swift can't catch `NSUnknownKeyException`). After the save it reads the event back through a fresh `EKEventStore` (`persistedAttendees`) and answers `attendees_saved`, `attendees_unverified` (it couldn't read the event back; under write-only access it never can) or `attendees_failed`. The reply never says "Invited": Calendar's server sends the invitation and the helper can't see whether it did, so a saved invitee reads "Added a@b.com as an invitee — Calendar's server sends the invitation and I can't see whether it did; want me to email them the details too?".
- **macOS access (TCC).** The backend's python (a LaunchAgent) spawns the helper, so that python is the responsible process and holds the grant. Measured on the reference host: **Calendar write-only, Reminders never asked**, until a one-time request. So `event_add` to the default calendar works as soon as the helper is built; naming a calendar, moving, changing and deleting need Full Access; Reminders need a first ask, and an app macOS never asked isn't in System Settings' list. **The one-time step, at the Mac**: `bash backend/scripts/eventkit_request_access.sh`. It asks for both through a one-shot launchd job under the backend's python (`<EDWARD_LAUNCHD_PREFIX>.eventkit-request`; run from Terminal, `request` would grant Terminal instead), then you click Allow / Full Access. If no dialog appears (an earlier "Don't Allow"): System Settings → Privacy & Security → Calendars → the python → Full Access, and → Reminders → the python on. The tool's refusal says which of these applies. The grant reaches Edward's shell too (it is the python's child). `GET /api/health/report` → `calendar.eventkit` shows what macOS has granted (cached 10 min) and `calendar.reminders` how Reminders were read last.
- **Building the helper.** Run `bash backend/scripts/build_eventkit.sh` once, like the media helper: the command-line tools' `swiftc` and `codesign` only (no Homebrew), `Info.plist` embedded as `__TEXT,__info_plist` (EventKit refuses a process whose bundle lacks the usage strings), an ad hoc signature as `com.meet-edward.eventkit`, the self-test, then into `~/edward-eventkit/bin/edward-eventkit`; a failed build never replaces a working helper. Until it is built, every write answers that the helper isn't installed; reads still work.
- **Rails and records.** The writes are tier COMMITMENT (`names.COMMITMENT`): the judgement check's dry run records them, and the journal tells them ("Added “Dentist” to your calendar for Mon 9:00am"). The egress scan covers what leaves for iCloud and invitees: `what`, `location`, `notes`, `attendees` (`secret_scan.ACTION_EGRESS["schedule"]`).
- **Flags.** `EDWARD_EVENTKIT` (the helper's path, read per call), `EDWARD_REMINDERS_SQLITE=off`, `EDWARD_REMINDERS_DIR`. Conftest turns the Reminders reader off and points `EDWARD_EVENTKIT` at a file that doesn't exist, and since the helper's default path exists once it is built, `eventkit_service._run` itself refuses unless a test patched it or `subprocess.run` (`_never_reach_eventkit`): no test reads real Reminders or reaches EventKit.

The heartbeat's calendar listener (never enabled, 0 events ever) was deleted the same day; its apple-mcp lookup lives in `display_service` ([heartbeat.md](heartbeat.md)).
