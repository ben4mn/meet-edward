# The heartbeat: listeners, the cycle, the mind path

How inbound messages and mail reach Edward: the listeners, the one cycle that hands each batch to the mind path, what the listeners store, the owner's verdicts, and the digest in the Listening panel. The mind side — the `mention` wake (only while `EDWARD_PINGS=off`), the pack's "Waiting on you", the interjection rules — is in [mind.md](mind.md); since 2026-10-11 inbound is *noticed*, never woken for (`request_wake("messages")` is a shim to the noticer, [noticing.md](noticing.md)), and anyone who asks Edward directly is answered by the ping runner ([pings.md](pings.md)).

**On a fresh install** the heartbeat runs but listens to nothing you have not switched on: `heartbeat_config.imessage_enabled` defaults **off** (reading iMessages needs Full Disk Access and is opt-in — the Listening panel's configuration, Edward tab → Attention → Listening → `?view=config`, or `PATCH /api/heartbeat/config {"imessage_enabled": true}`), and the email and Gmail tracks are off until you turn them on. Pings come from the iMessage listener, so with it off nobody can `@Edward` him from Messages.

## The listeners (`backend/services/heartbeat/`)

- Monitors iMessage, Apple Mail and Gmail; each track has its own switch and polling interval. **There is no calendar listener**: the apple-mcp calendar listener stored nothing in its whole life and reopened apple-mcp sessions dozens of times a day, and was deleted on 2026-10-11 with its Listening track — every calendar reader goes through `display_service.get_calendar`, and `schedule(calendar)` reads it when asked ([computer.md](computer.md)); the `calendar_*` columns stay, so an old PATCH still saves.
- `listener_imessage.py` — polls `~/Library/Messages/chat.db` every 10 s (Apple timestamps = date/1e9 + 978307200); the backend's python needs Full Disk Access ([ops-health-backups.md](ops-health-backups.md)). It describes arriving images in the background at background priority (`attachment_vision.describe_image`), scheduled after the commit with the event's explicit id (until 2026-10-11 it got `None` and no photo was ever described), and notes each description for `attachment:<rowid>` (`services/media/hooks.py::note_description`). Attachments read `[image: IMG_0001.heic attachment:12345]` in text, with the description inside once there is one; each carries `uti`, `transfer_state` and `total_bytes`, and a NULL mime type falls back to the UTI and the extension (a CAF audio message is `audio`, not `file`). A URL balloon's preview reads `[link: "<title>" (<site>) attachment:<rowid>]` from the `LPLinkMetadata` Messages already stored in `payload_data` (`services/media/linkmeta.py`; nothing is fetched, and only while `EDWARD_MEDIA` is on). Only images go to vision. Tapbacks and other associated messages (`associated_message_type != 0`) are not ingested: a tapback on "@edward look" reads 'Loved “@edward look”'. The owner's own rows are labelled with `owner.owner_name()` ("the owner" when `EDWARD_OWNER_NAME` is unset), and their handles are `heartbeat_config.imessage_owner_handles` plus `EDWARD_OWNER_HANDLES` — the env list counts even when the config row is missing.
- **The decoder** (`imessage_decoder.py`): `attributedBody` typedstream length prefixes (`0x81` + uint16, `0x82` + uint32) are **little-endian** (2026-10-11: every real blob on the original install). Read big-endian until then, every body-only message of 128 bytes or more (mentions, inline replies, rich text) fell to a regex fallback that kept only its first line; that fallback now joins lines. `backend/scripts/verify_typedstream.py` prints how this Mac's bodies decode, counts only.
- **Edward's own sends coming back** (2026-10-11): he sends from the owner's Apple ID, so each send returns as an `is_from_me` row, the same shape as the owner typing on their phone. The listener recognises them structurally, first match wins (`listener_imessage._echo_reason`): the chat.db ROWID the transport read back (`services/imessage_sent.py`), an in-flight send to this chat with this text (claimed, so the transport finds its row), an `ok` send-ledger row with the same normalised hash for this chat in the last 120 s (aware UTC), then the signature — on the caption, never the text with attachment placeholders appended. An echo is stored `dismissed` with `raw_data.edward_echo` and is never a ping. Readers mark Edward's lines `by_edward`. Before this, Edward's own echo looked like the owner's ping and he answered himself.
- **Pings** (2026-10-11; `services/pings/detect.py`, pure): `@edward` from anyone in any chat (the owner's own included), the owner in their self-chat, and an inline reply to one of Edward's bubbles (must-answer only from the owner). The listener writes the `pings` row in the same transaction under a SAVEPOINT, whatever `EDWARD_PINGS` says; recorded `open`, the event is `triage_status='ping'` and never enters the cycle, so the owner's own ping never silences a friend in the same batch, and the runner is kicked after the commit. With the flag off (`legacy` rows) or a failed ping insert, the message takes the cycle and the mind's `mention` wake answers it. **Self-chat breaker**: for 60 s after an Edward send into the self-chat whose row was never found, a self-chat line without `@edward` is not a ping (`[pings] breaker`). **Poison batch**: the third failed store of the same batch stores it without ping rows, media items or the describer (`[pings] poison batch up to rowid N`) and the watermark advances. At start the listener hands the transport its loop and loads the echo index from 30 days of ok sends.
- `listener_email.py` — polls Apple Mail's Envelope Index (SQLite; `EDWARD_MAIL_ENVELOPE_INDEX` when your macOS keeps it somewhere other than `~/Library/Mail/V10/MailData/Envelope Index`) for unread inbox mail and stores each as an `email` event. It went dark for months on the original install (a `stored` counter sat after a `return`) and came back with three rules instead of a reseed: mail received more than 24 h ago is skipped while the mark (`heartbeat_config.email_last_rowid`) still moves past it — Mail.app downloads old mail under new ROWIDs after an outage, and the rule always applies, so first sight after one is covered; one poll drains the backlog in pages of 20 (at most 50 pages), saving the mark after each; `listener_email.listener_state()` (last clean poll, last error, what the poll did) feeds the health report's `email` block ([ops-health-backups.md](ops-health-backups.md)). Log: `[Heartbeat] Email listener: stored N, skipped M older than 24 h (mark → R)`. iCloud mail only arrives while Mail.app runs on the host Mac.
- `listener_gmail.py` — polls Gmail's history API for new inbox messages; the same 24 h rule, by `internalDate`. An expired `historyId` (`gmail_service.GmailHistoryExpired`) re-seeds the mark and stores nothing — it used to read as an empty inbox forever. It runs while "watch my inbox" (`gmail_enabled`, GmailPanel) is on and Gmail is connected: `heartbeat_service` at startup, `listener_gmail.ensure_started()` from the connect callback and the `PATCH /api/heartbeat/config` switch; disconnecting stops it. Today's `LISTEN_TRACKS` includes `gmail`.
- **Mail can't trigger Edward** (2026-10-11, an integrations audit): an `@edward` in a subject or snippet kicks no immediate cycle, is never a mention (below), and the noticer reads it like any other event (`noticing_service.is_ping_event`). Anyone can put `@edward` in a subject line; only an iMessage can ask Edward anything.
- The listeners store events and nothing else.

### Adapting this

The iMessage listener assumes Messages on the host Mac is signed into the owner's own Apple ID (so `is_from_me` means the owner, and Edward's sends come back as echoes), and both the iMessage and Mail listeners need Full Disk Access for the backend's python. Those seams are marked `ADAPT:` in `listener_imessage.py`, `listener_email.py`, `services/pings/detect.py` and `services/imessage_sent.py`; [ADAPTING.md](../ADAPTING.md) walks through them.

## One cycle, and the mind path

- `heartbeat_service.py` orchestrates the listeners and the cycle, and injects the briefing into the system prompt.
- `triage_service.py` (about 400 lines since this release) is **one cycle**: take the pending events, drop expired listening windows, strip an SMS compliance footer from a message's text, and hand the batch to the mind path (`triage_service.run_triage_cycle` → `services/heartbeat/mind_path.run_mind_cycle`). Beside it live the helpers the rest of Edward imports from there: the chat stand-down (`record_standdown`, `_get_active_standdown`, `_release_standdown` — the send tools, the mind path and the ping runner use it), `register_listening_window_for_chat` (every iMessage send path calls it), `_count_recent_sends` and `MENTION_PATTERN`.
- **The legacy triage engine is gone.** It was a three-layer engine (zero-cost rules, a background-LLM classifier, then its own reply turns and mailbox auto-actions) with a dozen learners and sub-engines around it, tuned to one person's message traffic. The mind path replaced it on the original install in September 2026 behind `heartbeat_config.mind_enabled`; the old path, its sub-engines, their tests and the email auto-actions were deleted for this release. `mind_enabled` no longer chooses anything — every cycle runs the mind path, `GET /api/heartbeat/status` always reports `mind_enabled: true`, and `PATCH` still stores the column (an install whose stored value is `false` escalates to the mind like any other).
- **The mind path** (`mind_path.run_mind_cycle`): `identity_filter` drops what the owner wrote unless it is an `owner_direct` ping or their own `@edward` (the old filter dropped the owner's `@Edward` in a group as "their own message"); drops inbound in a chat the owner replied to in the batch (where the owner pinging Edward is not the owner replying — before 2026-10-11 the owner's ping silenced their friends' in the same batch); keeps one `@edward` mention per chat, found in the whole message — **only an iMessage is a mention** (`mind_path.MENTION_SOURCES`): an email or Gmail row with `@edward` is kept as an ordinary escalation; treats Edward's own echo (`raw_data.edward_echo`, or a signed from-me message) as his, not the owner's; and leaves a row the ping runner owns to the runner. The rest is marked `escalated` and handed to the noticer through the `messages` shim (60 s coalesce), or, for a mention, an immediate `mention` wake carrying its `mention_ids` (only while `EDWARD_PINGS=off`; with pings on, pings never reach `identity_filter`, which then serves the flag-off and degraded paths). After a wake the escalations are stamped `notified_at` / `notification_batch_id="mind:<ledger id>"`; a failed wake counts `mind_attempts` and the third gives up (`mind:gave-up`, still listed on Today).
- `GET /api/heartbeat/act-queue` is retired: it always answers the empty shape (`retired: true`) for old clients, and the presence stream's `watching` is always 0.
- DB tables: `heartbeat_events`, `triage_results`, `triage_decisions`, `heartbeat_config`, `heartbeat_feedback`, and the old engine's batch-A tables, which nothing writes now ([data-model.md](data-model.md)).
- `heartbeat_config` per-track fields: `imessage_enabled` (default off), `email_enabled`, `email_poll_seconds`, `gmail_enabled`, `gmail_poll_seconds`, the unused `calendar_*` columns; `imessage_owner_handles` (the owner's handles — the never-text-the-owner guard reads them, with `EDWARD_OWNER_HANDLES`); `mind_enabled` (default on; informational).
- REST API: `GET /api/heartbeat/status`, `GET /api/heartbeat/events`, `GET /api/heartbeat/triage`, `PATCH /api/heartbeat/config`, `POST /api/heartbeat/triage/run` (operator: an immediate cycle, after re-opening a failed event), `GET /api/heartbeat/act-queue` (retired, always empty), `GET /api/heartbeat/recent-senders`, `GET /api/heartbeat/jarvis-metrics`, `POST /api/heartbeat/events/{id}/feedback`, `GET /api/heartbeat/feedback`.
- Heartbeat turns are tainted by construction; a heartbeat reply to a third party meets `send_message`'s recipient rule, and the taint gate only when `EDWARD_TAINT_APPROVALS` is `shadow`/`on` (off by default; [trust-boundary.md](trust-boundary.md)); their model calls are labelled `turn:heartbeat`. A heartbeat thread is never replayed into by a scheduled event.
- Frontend: HeartbeatPanel — Edward tab → Attention → **Listening** (slug `heartbeat`): the digest, then `?view=log` (every event, filterable) and `?view=config` (what he listens to, how often, who can't @mention him).

## Escalated messages on Today

Escalated heartbeat messages collapse to **one need per thread** (conversation, else chat identifier), carried by the newest message with the count in the detail — a busy group chat used to put the same name on Today five times. Today skips escalations with `notified_at` set (except `mind:gave-up`). "Done" on a card, `POST /api/today/heartbeat/{event_id}/done {also}`, stamps the card's events `notified_at` with batch `owner:done` — the mark the mind puts on what it considered — so the next wake's "Waiting on you" drops them too. An escalated email reads "<sender> emailed you: <subject>". Details: [app-shell-today-chat.md](app-shell-today-chat.md).

## The Listening digest

- **Heartbeat digest** (`components/settings/HeartbeatDigest.tsx`, pure `heartbeatDigestModel.ts`): decisions first (noted / watching / told you / handled by you; a ping — status `ping` — reads "Asked me") with a one-line reason and human labels; dismissals folded per person; message text hidden by default (`edward:heartbeatShowText`); the owner's own outbound texts are never "decisions". Full log and configuration are one disclosure away.
- **"Right call?"** posts to `POST /api/heartbeat/events/{id}/feedback` → the `heartbeat_feedback` table (`services/heartbeat_feedback_service.py`). The mind reads the verdicts — its pack, and the nightly's "anything new?" check. (From 2026-09-12 a "should have told me / noted" verdict was also copied into a false-dismissal table for the old engine's learners; that copy went with the engine.)
- Owner-facing copy never says "triage" or "heartbeat" — the panel is **Listening**.
