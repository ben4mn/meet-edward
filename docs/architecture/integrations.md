# Integrations: skills, MCP, messaging, mail, tools

The integrations Edward's tools reach: the skills system, the built-in MCP clients (Apple, WhatsApp), custom MCP servers, messaging (iMessage, Twilio SMS and WhatsApp), Brave search, HTML hosting, file storage, persistent databases, contacts, mail and Gmail, Alexa and presence beacons, with the tool lists the model sees. Most of them are optional: each needs its own credentials or macOS permissions, and is off or inert until you set it up.

## Custom MCP servers

(`backend/services/custom_mcp_service.py`)

- **The owner installs them; Edward no longer does** (2026-10-11): the six self-service tools (`search_mcp_servers`, `add_mcp_server`, `list_custom_servers`, `remove_mcp_server`, `update_mcp_server`, `restart_mcp_server`) were deleted with 0 calls in 30 days; Edward runs `npx` / `uvx` in his own shell when he wants an MCP server for himself. Servers the owner installs from the Servers panel still bind their tools.
- Servers run as subprocesses via `npx` (Node.js) or `uvx` (Python); no git clone needed. Each server's tools are prefixed with its name to avoid collisions.
- **Their tools ride the rails as outward calls** (2026-10-11): nothing can tell what a custom tool does (post, pay, delete), so `tool_registry._get_custom_mcp_tools` tags each with `metadata {custom_mcp: <server>, tier: outward, timeout_s: MCP_CALL_TIMEOUT_SECONDS}` (`custom_mcp_service.get_all_custom_tools_by_server`), and a tool bound after the 14 is counted in `toolset.names.CUSTOM_MCP_TOOLS`. One named like a tool already bound is dropped and never counted; one whose tag doesn't hold is not bound at all (untagged, it would run with none of the rails). Then:
  - `names.tier` and `thought_journal.action_tier` call it `outward` (a wake that calls one is journaled; the judgement check's dry run records it and never runs it);
  - `secret_scan.egress_args` scans **every string argument, nested ones too**;
  - what it returns taints the turn (`taint_service.ingest_taint`), and its result is redacted like every local tool's ([trust-boundary.md](trust-boundary.md));
  - a friend's ping is refused it with an honest `Tool error:` (`pings/scope.refusal`: where its call lands can't be checked against the recipient rule), as is any turn whose policy may not reach people — the pulse, free time, the nightly, a plain `self` or `manual` wake, a turn with no policy (`toolset/policy.scope_refusal`; review 2026-10-11: a Slack- or mail-posting server could otherwise post from the pulse). Turns that may reach people keep it: the owner's own turns and pings, a mention, a promise kept in a chat, a speak wake into a thread, events.

  Only tagged tools are affected: a legacy or server-tool name keeps its tier. Test: `tests/test_custom_mcp_rails.py`.
- Hot reload: new tools are available immediately via `refresh_registry()`.
- **Orphan sweep** (2026-09-21): `sweep_orphaned_mcp_servers()` runs at startup, before the MCP clients come up, and terminates `whatsapp-mcp-server` / `apple-mcp` processes whose ancestry does not reach this backend. `launchctl kickstart -k` SIGKILLs uvicorn and re-parents its stdio servers to launchd; eight orphaned WhatsApp chains from a month of restarts were found running. The WhatsApp Go bridge runs as its own process and is never swept. Test: `tests/test_mcp_orphan_sweep.py`.
- **Every MCP call is bounded** (2026-09-24): `MCP_CALL_TIMEOUT_SECONDS` (30) in the caller *and* in `MCPSessionHolder`'s worker around `session.call_tool`. A call that times out fails and the session reopens; a queued call whose caller already gave up is never sent. `mcp_client.call_tool_bounded(tool, args, timeout=)` passes a shorter bound (the calendar list: `display_service.CALENDAR_MCP_TIMEOUT_SECONDS`, 10). Before this, one wedged apple-mcp calendar call could freeze every wake, the pulse and the scheduler, with no ledger row. Test: `tests/test_mcp_call_bounds.py`.
- REST: `GET /api/custom-mcp`, `PATCH /api/custom-mcp/{id}`, `DELETE /api/custom-mcp/{id}`, `POST /api/custom-mcp/{id}/restart`. Frontend: `CustomMCPPanel`, Edward tab → Mind → **Servers** (slug `mcp`). Table: `custom_mcp_servers` (separate from the built-in skills).
- **A server's environment is an allowlist** (2026-09-27): it inherits only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_*`, `TERM` (`custom_mcp_service.inherited_env`), then its own `env_vars`, then the npm/uv/corepack/XDG cache defaults. It used to get the backend's whole environment (the live `DATABASE_URL`, Twilio, VAPID, the JWT secret, tunnel tokens, every model key). It still runs unsandboxed as the owner's user and can read secrets by path, so installing one is a deliberate act. Details: [codex-and-orchestrator.md](codex-and-orchestrator.md#custom-mcp-servers-environment).
- **`env_vars` are stored in plaintext**, and so land in every nightly dump. Never put a write-capable token there without a deliberate decision. (On the reference host a test server was once left installed and enabled with a write-capable GitHub token and 26 write tools in its `env_vars`; it was removed on 2026-09-27 and the token revoked.)

A test greps that no code asks `is_skill_enabled` about them outside the legacy registry. Alexa Outbound is not in the list; it gates only the legacy registry's Alexa tools.
  - Test: `tests/test_skills_status_honest.py`.

## Messaging and the tool lists

**Messaging services** (`backend/services/`)

- `imessage_service.py`: iMessage through AppleScript (macOS): one transport, `send_to_chat`, routed by chat.db, read back, honest on failure (below). **Edward sends as the owner**, from the Apple ID this Mac's Messages is signed into; his sends come back as the owner's own `is_from_me` rows and are told apart by the ROWID the transport reads back (`services/imessage_sent.py`, an `ADAPT:` seam: a separate Apple ID for Edward would need the echo checks reworked). Set `EDWARD_OWNER_HANDLES` to the owner's phone numbers and Apple ID. Sending needs the backend's python to hold Automation permission for Messages.
- **Reading iMessages is opt-in**: the heartbeat's iMessage listener runs only with `heartbeat_config.imessage_enabled` on (off by default; the Listening panel) and needs Full Disk Access for the backend's python to open `~/Library/Messages/chat.db` ([heartbeat.md](heartbeat.md)).
- `twilio_service.py`: SMS and WhatsApp send and receive via Edward's own Twilio number (`TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER`).
- `routers/webhooks.py`: the Twilio inbound webhooks for SMS and WhatsApp (`POST /api/webhook/twilio`, `POST /api/webhook/twilio/whatsapp`; processed in the background, answered through the API rather than TwiML).
  - **They fail closed** (2026-10-11): a request is answered 403 unless its `X-Twilio-Signature` is valid for `TWILIO_AUTH_TOKEN` and one of the URLs Twilio may have signed: the configured `TWILIO_WEBHOOK_URL` / `TWILIO_WHATSAPP_WEBHOOK_URL`, or the URL as received (scheme and host from `X-Forwarded-Proto` / `X-Forwarded-Host` behind a proxy or tunnel, else `Host`) (`twilio_service.check_webhook_signature`). **With no `TWILIO_AUTH_TOKEN`, every inbound webhook is refused.** Before this they were accepted unchecked whenever `TWILIO_WEBHOOK_URL` was unset: anyone who found the URL could start a model turn.
  - **Only the owner gets a turn** (2026-10-12). A Twilio turn reads like any other (bash, memory, messages, the calendar: reads are open, [tool-loop.md](tool-loop.md)) and its final text is texted back to the sender, so answering anyone let a stranger who found Edward's number ask for the owner's data and get it by SMS. After the signature and the rate limit, `webhooks.is_from_owner` compares the sender with the owner's handles (`EDWARD_OWNER_HANDLES` plus heartbeat config's `imessage_owner_handles`) by `pings.hooks.chat_key`, as the iMessage listener does (a phone with or without its country code matches), except that two numbers which both carry a country code must agree on every digit, so `+44…` never passes for `+1…` on its last ten. Anyone else's text is held (`webhooks.hold_inbound`): no turn, no reply, no conversation and no push to the owner; the log line names the sender without the text, and `ledger_events` keeps it (kind `twilio_inbound`, outcome `held`, detail `{from, text (first 400 characters), media}`). No polite reply either: it would confirm the number is live and automated, cost a message each time, and let anyone make Edward's number text whatever number they send from. **Set `EDWARD_OWNER_HANDLES`, or nobody is answered.** `EDWARD_TWILIO_ANSWER_ANYONE=on` restores answering everyone; those turns get a prompt line that the sender is not the owner and that nothing of the owner's is to be shared (a prompt, not a wall). Tests: `tests/test_public_twilio_owner_gate.py`, `tests/test_public_twilio_signature.py`.
  - WhatsApp and SMS from the same phone number share one external contact and conversation (`external_contacts.last_channel` picks the reply channel). The Twilio reply, sent by the router rather than a tool, is the turn's final text: it never carries a tool call written as text (`services/tool_markup.py`; else the honest `webhooks.GARBLED_REPLY`) and goes through `webhooks.scrub_outbound_reply` (the egress secret scan). Twilio webhooks read `NumMedia` / `MediaUrl*` and pass MMS media as attachments.
- `mcp_client.py`: the built-in MCP clients, run as stdio subprocesses, every call bounded (above):
  - **WhatsApp** via the whatsapp-mcp project: its Go bridge runs outside Edward (a LaunchAgent you set up, or by hand) on `127.0.0.1:8080`, logs to `MCP_WHATSAPP_BRIDGE_LOG` (default `/tmp/whatsapp-bridge.log`, where its pairing QR appears) and is paired once by scanning that QR. Then set `MCP_WHATSAPP_ENABLED=true` and `MCP_WHATSAPP_SERVER_DIR` (its `whatsapp-mcp-server` directory).
  - **Apple Services** via apple-mcp (Calendar, Reminders, Notes, Mail, Contacts, Maps, Messages): the jxnl/apple-mcp fork run from a local clone with bun. Off unless `MCP_APPLE_ENABLED=true`; `BUN_PATH` (default `~/.bun/bin/bun`) and `MCP_APPLE_DIR` (default `~/apple-mcp`, which must contain `index.ts`) locate them, read per call, and a missing bun or clone is refused early with a readable error. Calendar, Reminders and Contacts are read from their own databases first ([computer.md](computer.md#the-owners-calendar-servicescalendar_servicepy)); apple-mcp is the fallback. Under the toolset apple-mcp is not bound to the model (its sends bypassed `_send_guard`).
- `attachment_vision.py`: iMessage and MMS attachments → base64 JPEG blocks for a turn (HEIC via `sips`, max edge 1600) and one-paragraph vision descriptions; the listener describes images in the background and folds the text into the event, and a ping turn receives the images themselves ([media.md](media.md)).
- `home_assistant_service.py`: Alexa announcements through Home Assistant (`HOME_ASSISTANT_URL`, `HOME_ASSISTANT_TOKEN`, `HOME_ASSISTANT_ECHO_PREFIX`); `HOME_ASSISTANT_DEFAULT_DEVICE` is the Echo entity a sound or a volume change goes to when no device is named (default `<HOME_ASSISTANT_ECHO_PREFIX>_dot`).

**Send guards** (every send goes through `_send_guard`; the toolset's `send_message` wraps it, and so do `EDWARD_TOOLSET=legacy`'s old send tools):

- identical text to the same recipient within 10 minutes answers "Already sent…", PWA chat sends included since 2026-09-27 (the chat stream lost its turn after the first step, and the guard let a send with no turn through; [tool-loop.md](tool-loop.md#stop-leaving-and-a-send-in-flight-2026-09-27));
- a stood-down chat (`chat_standdowns`) is refused in autonomous turns (chat, voice, widget and Alexa are exempt; a fresh @edward mention releases the stand-down);
- a `mind` or `pulse` turn's send to the owner is refused: the owner is reached by push or a Today note ([mind.md](mind.md));
- **a send the turn is cancelled under is finished and recorded** (2026-09-27, `graph/tools._send_and_note`): the transport and the "Already sent" record run as one shielded unit, so Stop cannot leave a message sent but unrecorded (or a Twilio request half-made);
- the egress secret scan runs before any of them, and the taint gate only when `EDWARD_TAINT_APPROVALS` is `shadow` / `on` (off by default since the toolset; [trust-boundary.md](trust-boundary.md));
- **a ping turn's chat is its own** (2026-10-11): an autonomous turn (mind, pulse, a scheduled event, the heartbeat) cannot send into a chat whose ping turn is running; the transport answers "Edward is answering a ping in this chat right now" ([pings.md](pings.md)).

### The iMessage transport (2026-10-11)

Every iMessage goes through `imessage_service.send_to_chat`; `send_imessage` and `send_imessage_to_chat` keep their signatures and return shapes and wrap it. It never signs; callers do.

- **Routing comes from chat.db, not spelling.** `imessage_service.chat_info` reads the chat's `style` (43 = group), `service_name` and `guid` (any spelling: `chat123`, `any;+;chat123`, a chat.db guid, a phone; with an iMessage and an SMS chat for one handle, the one with the latest message), and the pure `imessage_service.applescript_targets` lists what to try in order: a group goes `any;+;<id>`, then its chat.db guid, then `iMessage;+;<id>`; a 1:1 SMS or RCS chat goes by its guid, then the participant; a 1:1 iMessage chat, a phone or an email by participant; **a name never** (Messages would create an undeliverable chat addressed to it). A `-1728` ("Can't get chat") moves on to the next target; any other error stops. **Why**: group chats can have a 32-hex `chat_identifier`, and the old `startswith("chat")` rule sent replies into them to `participant "<hex>"` and reported them delivered (2026-10-10).
- **The read-back decides.** Before osascript the transport notes chat.db's highest ROWID and `imessage_sent.begin`s the send; after it, chat.db is polled (every 250 ms, up to 5 s) for the first from-me row in that chat with the same normalised text, or the row the listener already claimed. A row found is a **confirmed** send, even after an osascript timeout, which never tries another target (Messages often sends anyway). No row with osascript ok is `confirmed: False`, and the chat is marked unconfirmed for 60 s (the self-chat breaker). No row with osascript failed is **`success: False` with the real error, never delivered**.
- **Ping bookkeeping**, synchronously before returning: a send into the chat of the ping the current turn answers is noted on its context (in flight, then its outcome), and the echo index learns the row (`imessage_sent.resolve` / `abandon`).
- **The ledger** (`imessage_outgoing_sends`) gets successful sends only, with an **aware UTC** `sent_at` (timestamptz: a naive value is read as the host's local time) and the read-back columns: `ok`, `route`, `message_rowid`, `message_guid`, `chat_guid`, `text_norm_hash`, `text_len`, `purpose`, `ping_id`, `turn_source`, `confirmed_at`.
- `imessage_service.recent_from_me_since` reads the newest Edward-signed (or same-text) from-me row in a chat since a time; the ping runner's delivery and recovery use it to see a send the ledger missed.
- **Files** (`imessage_service.send_attachment`, 2026-10-11): routed exactly like a text (the in-flight guard, `chat_info`, `applescript_targets`). A **copy** is staged at `~/Library/Messages/Attachments/Edward/<uuid>/<name>` (`EDWARD_IMESSAGE_OUTBOX` overrides it; staged folders older than 24 h are pruned unless a chat.db attachment row still names one as its file; the original is never moved), and the script is `send POSIX file "<staged>"` to the chat or the participant, bounded at 60 s, never a second target after a timeout.
  - **Only the read-back is success**: chat.db is polled (up to 15 s) for a from-me message after the send, in that chat, joined through `message_attachment_join` to an attachment with that `transfer_name` and `error = 0`, or the row the listener already claimed when it carries that file. "That chat" is chat.db's own spelling (`chat_info`), and any spelling of a handle matches (`_chat_clause`: a phone on its last ten digits, never a group; an email without case), because `send_message(to=<name>)` sends to the number as the address book stores it ("(201) 555-0111") while chat.db holds "+12015550111"; an exact match reported files that went out as failed.
  - Found: the echo index learns the row and the send ledger gets `[attachment] <name>`. osascript ok with no row is a failure ("Messages took the file but no message appeared in the chat"). With chat.db unreadable nothing is sent (an unconfirmable send reads as failed and invites a second try).
  - The send begins in flight with U+FFFC (chat.db's text for a file-only message), and the listener's `_echo_reason` claims a captionless from-me row with attachments against it, so a file row it reaches before the read-back is Edward's, never the owner's. When osascript said ok (or timed out) and no row was found, the chat is still marked unconfirmed for 60 s, as for a text.
  - `send_message` sends the text first, then each file, every one through `_send_and_note` and the 10-minute dedupe (a file keyed on its name and size): a step cut while Messages is sending finishes that file and records it, and a re-ask sends only what didn't go. A file that fails after the text says "the text went out, but …". `send_message`'s 150 s deadline covers the text and a file at their worst.
  - The staging folder is community knowledge (from the BlueBubbles project), not verified on every macOS: the read-back keeps it honest. Make the first live send a supervised one into the owner's self-chat. Test: `tests/test_imessage_attachment.py`.
- **Reading** (`messages`, 2026-10-11): `recent` is one block per chat (the chat with the newest message first, its lines in time order), each headed `[<label>] chat_id=<chat_identifier>` (what `send_message(chat_id=)` and `thread` take). `recent(contact=<name>)` resolves the name through the owner's contacts to the person's phones and emails (`listener_imessage.get_recent_messages_across_chats(handles=)`: a phone on its last 10 digits, an email without case), beside the old loose match that finds a group by its name; a handle passes straight through. `thread` and `participants` make the id canonical first (`graph/tools._canonical_chat`: chat.db's `chat_info`, else the `any;+;` / `iMessage;-;` / `SMS;-;` prefix stripped), because their queries match `chat_identifier` exactly; participants are named through `contacts_service.lookup_handle` (an Apple ID too). Test: `tests/test_messages_output.py`.
- **Tests never reach Messages**: `_run_osascript` is the only way to osascript, and conftest's `_never_reach_messages` refuses a real one and points chat.db at a missing file until a test points it at its own fake (`tests/fixtures/fake_chatdb.py`); it also points the address book at a missing directory and keeps Contacts.app asleep. Tests: `test_imessage_chat_id_routing.py`.

## File storage and persistent databases

**File storage** (`backend/services/file_storage_service.py`, `backend/routers/files.py`)

- Persistent file storage with categories, tags and metadata; hex-prefix sharding on disk (`{id[0:2]}/{id}_{filename}`); upload, download and text-file reading. Table: `files` (filename, stored_path, mime_type, size_bytes, category, tags, source). A 50 MB maximum and an allowlist of MIME types. `FILE_STORAGE_ROOT` (default `./storage`).
- REST: `GET /api/files`, `POST /api/files/upload`, `GET/PATCH/DELETE /api/files/{id}`, `GET /api/files/{id}/download` (the chat links a download rather than opening it). Its tools left the toolset on 2026-10-11; a PWA upload is opened with `look("file:<id>")`.

**Persistent databases** (`backend/services/persistent_db_service.py`, `backend/routers/databases.py`)

- Named PostgreSQL schemas (`edward_db_<name>`) inside the main database, kept for reading: SQL validation with blocked patterns (DROP SCHEMA, GRANT, `pg_*` functions, …), at most 10 databases, a 500-row limit, a 30 s query timeout. Its tools were deleted with the sandboxes.
- REST: `GET /api/databases`, `GET/DELETE /api/databases/{name}`, `GET /api/databases/{name}/tables`, `GET /api/databases/{name}/tables/{table}/columns`.

## Contacts

**Contacts** (`backend/services/contacts_service.py`)

- **The AddressBook SQLite stores are primary** (2026-10-11): every `Sources/<uuid>/AddressBook-v22.abcddb` plus the top-level file, opened read-only (`mode=ro`; it needs the same Full Disk Access as chat.db). `EDWARD_ADDRESSBOOK_DIR` replaces the base directory (conftest points it at a missing one, so no test reads a real address book).
- `contacts_service.lookup_contact` takes a name (every word must appear, without case, in the first, middle, last or nick name or the organisation) and hands a phone or an email to `contacts_service.lookup_handle`: a phone matches on its last 10 digits (a shared last four is not a match), an email without case (`ZADDRESS` or `ZADDRESSNORMALIZED`). `lookup_phone` is `lookup_handle`. Each match is `{name, phones, emails, nickname?, organization?}`. One person in two sources is one match (Contacts.app's own link between the cards, `ZLINKID`; a shared phone or email and names that hold each other; or the same full name with no phone or email that disagrees), and a namesake whose numbers or addresses differ stays a second. **A miss is a success with no matches, never an error.**
- **AppleScript only as the fallback**: Contacts.app (after `open -ga Contacts`) is asked only when no store exists, or every store fails to open or has drifted (`sqlite3.Error`, e.g. `ZABCDRECORD` gone). The Settings row reads "N address books (AddressBook database)" or "the AddressBook database isn't readable (Full Disk Access?)", never through osascript.
- Who asks: `messages(who)` (which prints the nickname and organisation too) and `send_message(to=<name>)`; `messages(recent, contact=<name>)` (the stores only, `applescript=False`: with none readable it keeps the loose match and never wakes Contacts.app inside `messages`' 60 s); the listener naming a sender (`listener_imessage._resolve_contact_name`, cached by handle) and `contact_identity_service`, both through `lookup_handle`, so an Apple-ID email sender gets a name and a friend iMessaging from an Apple ID is not held as unknown ([pings.md](pings.md)); chat participants. The eval runners (`scripts/notice_eval.py`, `scripts/ping_eval.py`) turn `lookup_contact`, `lookup_phone` and `lookup_handle` off: their people are synthetic.
- Legacy tools (`EDWARD_TOOLSET=legacy`): `lookup_contact`, `lookup_phone`. No database tables.
- Tests: `tests/test_contacts_sqlite.py`, `tests/test_listener_contact_name.py`, `tests/test_contacts_lookup_launches_app.py` (the fallback).

**Removed integrations.** Find My (friends' locations, read from a decrypted local cache with a key extracted under disabled SIP) and USPS package tracking (an unmounted work-in-progress router) were removed for the public release; their services, routes and skill rows are gone.

## Gmail, email actions, Alexa, presence beacons

- **Gmail** (`services/gmail_service.py`, `routers/gmail.py`; setup in [gmail-setup.md](../gmail-setup.md)): OAuth connect (`GET /api/gmail/oauth/url`, the public `GET /api/gmail/oauth/callback`), `GET /api/gmail/status`, `POST /api/gmail/disconnect`; Settings → Attention → `gmail`.
  - **The callback is public, so a code counts only with a state the signed-in `oauth/url` minted** (2026-10-11 audit): the callback used to take any `code`, so anyone could swap in their own Gmail with Edward's client id, and the PKCE verifier was thrown away, so no exchange could complete. Now `get_oauth_url` keeps `{state: verifier}` in memory (10 min, single use, at most 16; a restart means pressing Connect again) and sends the S256 challenge; a missing, unknown, expired or reused state answers 400 and stores nothing, and a declined consent spends its state; the code is exchanged with that state's own verifier. The account's address must then equal `GMAIL_ACCOUNT` when set (without case), and a different connected account is never replaced (disconnect first); either refusal stores nothing. Both `state` and `code` are redacted from the access log.
  - Production needs `GMAIL_REDIRECT_URI=https://edward.example.com/api/gmail/oauth/callback` (your public URL), a Web client, and the consent screen published **In production** (Testing expires refresh tokens every 7 days).
- **The owner's email in the toolset** (2026-10-11; `services/toolset/mail.py`, `services/mail_service.py`): Gmail through its own API (`gmail_service`, never apple-mcp), and iCloud (or any Mail.app account) through Mail.app on the host (its Envelope Index, opened `mode=ro`, and the `.emlx` files). The index is at `EDWARD_MAIL_ENVELOPE_INDEX` (default `~/Library/Mail/V10/MailData/Envelope Index`; the V10 folder changes between macOS releases); reading it needs Full Disk Access and Mail.app left running so it stays fresh (an `ADAPT:` seam).
  - `messages(mail_search)` matches the sender's address or name or the subject, every mailbox unless one is named, read and unread alike unless `unread_only` (Gmail's search syntax there; `_icloud_terms` cuts it down for the index), merged newest first with ids `icloud:<ROWID>`, `gmail:<id>` (plus its `gmail:thread:<id>`); a stopped Mail.app or an index more than 24 h behind adds a line, and Gmail not connected or signed out is said plainly.
  - `messages(mail_read)` prints From/To/Date (the owner's zone)/Subject, a reply hint, attachment names and sizes, and the body as text (HTML converted by `mail_service.html_to_text`; 8,000 characters, a thread 4,000 a message and 16,000 in all, newest kept; up to 10 links); an `.emlx` Mail hasn't downloaded reads "Mail.app hasn't downloaded this message's body yet".
  - **No gate on reading** (a design decision, 2026-10-11): every surface and turn may read, friends' pings and the hub included, and a read is a taint signal only ([trust-boundary.md](trust-boundary.md)).
  - **Sending**: `send_message` with a `subject`, or with `chat_id` = a mail id (a reply: To = its Reply-To or From — for the owner's own message, the first of its To/Cc who isn't the owner, and a thread answers its newest message that isn't theirs; `In-Reply-To` / `References` the newest message, Gmail's `threadId`, default subject "Re: …"), is an email from the owner's Gmail: the one guarded send, every guard shared with a text ([tool-loop.md](tool-loop.md#the-one-send-toolsetmessagingpy)). The transport is `gmail_service.send_gmail` (`users.messages.send` with the raw `message/rfc822`; attachments ≤ 20 MB; delivered only with the SENT label, one `format=minimal` get when the answer leaves labels out; when that get fails Gmail has still taken it — "sent but unconfirmed", noted in the dedupe and said as "don't resend; check Sent"). The scopes `gmail.readonly` + `gmail.modify` cover send, `threads.get` and `messages.get` / `list`: no `gmail.send`, no re-consent.
  - The owner's addresses (`mail_service.owner_addresses`: `EDWARD_OWNER_EMAILS`, `GMAIL_ACCOUNT`, the connected account, the addresses they send from in Mail.app, and the email handles among the owner's handles) count as the owner for never-email-the-owner. Disabling the `imessage_applescript` skill removes `messages` and `send_message`, so mail goes with it. Tests: `tests/test_messages_mail.py`, `tests/test_send_message_email.py`.
- **The Gmail listener** starts when "watch my inbox" (`gmail_enabled`) is on and Gmail is connected: at startup, from the connect callback and from the Settings switch (`listener_gmail.ensure_started`); disconnecting stops it ([heartbeat.md](heartbeat.md)). Mail's health (Mail.app, the index, the listeners, Gmail's sign-in) is `/api/health/report` → `email` ([ledgers.md](ledgers.md)).
- **Email management** (`routers/email.py`, `services/email_management_service.py`): sender preferences (keep / delete / junk / unsubscribe), per-sender stats, the actions log and an unsubscribe queue the owner approves or skips (`/api/email/*`). The legacy heartbeat triage used sender preferences to delete, junk or archive mail automatically; those mailbox auto-actions went with it. Mail never triggers Edward: an `@edward` in a subject is not a mention ([heartbeat.md](heartbeat.md)).
- **Alexa** (`routers/alexa.py`; setup in [alexa-setup.md](../alexa-setup.md); Edward's four outbound Alexa tools were deleted on 2026-10-11): `POST /api/alexa` is the custom skill's public webhook, `GET /api/alexa/status`, `POST /api/alexa/test` (a test announcement). Alexa turns are the owner speaking (turn source `alexa`). Settings → Attention → `alexa`.
  - **Security gap: inbound Alexa requests are not signature-verified.** The route checks only that the body carries `ALEXA_SKILL_ID`, and the skill id is not a secret, so anyone who learns it and the URL can run a turn as the owner. The reference host relied on the URL staying private. Leave `ALEXA_SKILL_ID` unset unless you use the skill (the route then answers 503), or add Amazon's request verification (the `SignatureCertChainUrl` certificate chain, the `Signature-256` header over the raw body, and a 150-second timestamp window) before the request is processed.
- **Presence beacons** (`routers/presence.py`): `POST /api/presence/beacon` (public; a script on another Mac sends the widget token in the *body*, never the URL; a signed-in tab uses its cookie), `GET /api/presence/state`, `GET /api/presence/stream`. The widget token is not read-only: `POST /api/widget/chat` runs owner turns with it, so it is owner-equivalent for chat. Put it only on the owner's own Macs (`presence.env` `chmod 600`), and replace a leaked one with `POST /api/widget/token/regenerate`. A beacon refreshes the device's `push_subscriptions.last_seen_at`. The stream sends `state` frames only. This is the owner's device presence; Edward's own state is `GET /api/mind/now`.
- **The memory graph** (`routers/memory_graph.py`; optional, off unless `GRAPHITI_ENABLED`): the backend never touches kuzu directly; every graph operation goes through the graph worker daemon over HTTP. `GRAPHITI_ENABLED=true` queues every new memory into `graph_ingest_queue`; the worker drains the queue only with `GRAPHITI_INGEST_ENABLED=true` (without it the graph stays empty and the queue grows, [memory.md](memory.md)). `POST /api/memory/graph/backfill` enqueues existing memories; `GET /api/memory/graph/backfill/status`, `GET /api/memory/graph/status`.
