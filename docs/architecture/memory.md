# Memory: the store, extraction, decay, consolidation, documents

Everything about what Edward remembers: the memories table and its origin/about/tier fields, extraction and its profiles, who counts as having said something, reinforcement and use credit, the tier ladder, intentions and their horizons, decay and what it holds, consolidation and contradiction flags, reflection and deep retrieval, entity extraction, search tags, the document store, provenance and verified forget.

Most of the "memory integrity" rules below landed on 2026-09-27, after an audit of the original install's store found that a large share of what was filed as the owner's word had been written by Edward's own wakes, scheduled reminders and other people's messages, and that some rows had been retired or rewritten by rules nobody asked for. The rules are there so a cleaned store does not refill.

## The memory store (`backend/services/memory_service.py`)

- Embedding: sentence-transformers (all-MiniLM-L6-v2, 384 dims); `EDWARD_FAKE_EMBEDDINGS=1` makes the test suite run without the model download (a conftest fixture; never set on a live backend).
- Search: hybrid 70 % vector similarity + 30 % BM25 keyword.
- Memory types: `fact`, `preference`, `context`, `instruction`, `intention` (a thing Edward decided to do or watch; `valid_until` is its horizon).
- **`valid_until` retires a row**: retrieval filters on it — the hybrid search, the entity-linked lookup (`retrieve_entity_memories`) and spreading activation (`_spread_connected_memories`); the last two loaded rows by id and brought a retired row back through its entity or a live neighbour's connection until 2026-09-27. Both filter before their limit (`get_entity_memories(live_only=True)`; spreading ranks only live candidates above its confidence floor, the floor before the cap too), so retired or low-confidence rows do not crowd out live ones (tests `tests/test_entity_keyed_retrieval.py`, `test_spreading_activation.py`). Nothing but verified forget, consolidation's dedup merge, the tier backfill (`POST /api/memories/backfill-tiers`), the `forget`-style tools (never the owner's row from a turn that is not theirs — below) and the owner's own delete in the Memory room (`DELETE /api/memories/{id}`) deletes one. Neither merge touches the owner's heard/owner rows or a retired row, and the backfill applies a model's MERGE only to ids it showed the model together (it had neither check and deleted any id the model named — `tests/test_backfill_tiers_keeps_owners_words.py`).
- Extraction runs after each turn through `build_background_llm()` (the background route — Haiku on Claude; [llm-and-quota.md](llm-and-quota.md)), post-turn, with reflection and search tags.
- **One store for what he heard, read, thought and did** (2026-09-18): every row carries `origin` (`heard` = the owner said it, `read` = Edward read it in a message/page/screen, `thought` = Edward concluded or decided it, `did` = an action and its outcome) and `about` (`owner`, `contact`, `self`, `world`). Both are orthogonal to the `tier` ladder (observation → belief → knowledge): a thought reinforced three times is a belief. `retrieve_memories(about=…, origins=…)` filters; `format_memory_line` (in `streaming.py`, shared with the respond node) shows `[origin/about]` when it is not the default heard/owner. Edward writes his own memories from inside a turn (the toolset's `memory(action="remember")`, the legacy `remember(content, memory_type, about, origin, importance, valid_until)`); extraction keeps what the assistant decided as `origin=thought about=self` and caps a thought about the owner at confidence 0.6 (`ASSISTANT_TESTIMONY_RULE`). `backend/scripts/backfill_memory_origin.py --apply` stamps old heartbeat rows `read` and pulse rows `thought/self`. Tests: `tests/test_memory_origin.py`, `test_remember_tool.py`, `test_backfill_memory_origin.py`.
- **Memory tools**: the toolset's `memory` (search, remember, update — `until="now"` retires —, close, why, forget — the owner's own conversation only —, doc_read, doc_write, doc_edit; [tool-loop.md](tool-loop.md)); under `EDWARD_TOOLSET=legacy` the old `remember`, `remember_update` (content, and an optional `valid_until` — a zone-less time is the owner's local time; now or earlier retires the row), `close_intention` ([mind.md](mind.md)), `remember_forget`, `remember_search`, `update_memory_confidence`, `graph_memory_search`. A zone-less `valid_until` is always read as the owner's local time.
- **What the owner said changes only in their own turn — through the tools too** (2026-09-27): the update and forget tools took any id, and both were wake tools while search prints ids — reproduced on the test cluster, a `mind`, `heartbeat` or `scheduled_event` turn rewrote an `owner_confirmed` pin, retired it with a past `valid_until`, and hard-deleted it; the original install's turn log showed 17 mind turns calling the forget tool and 28 calling update in 30 days. From a turn that is not the owner's own (`memory_service.is_owners_own_turn`: a wake, the pulse, a fired event, a heartbeat reply, a worker, a Twilio text) both now answer `Tool error: <owner> told me that themselves, so only they can change it…` (`graph/tools._owners_row_refusal`) for a `heard`/`owner` row, and always for an `owner_confirmed` row whatever its labels, and leave it untouched. The owner's own turn (chat, voice, widget, Alexa, their own pings — or no turn on record, which the chat profile takes as theirs, as extraction does) still can. Intentions stay Edward's to tidy (`close_intention` closes one from a wake either way), and so do his own rows and what he read. Test: `tests/test_memory_tools_keep_owners_rows.py`.

## Extraction profiles, and who said it

`VALID_EXTRACTION_PROFILES = ("chat", "heartbeat", "mind", "scheduled_event")`; an unknown profile falls back to chat with a log line.
- **`mind`** (every wake): a wake's pack is the turn's human message, not the owner speaking. An extracted `heard`, or a missing origin (which used to default to `heard`), becomes `read`, or `thought` when it is about Edward himself; a `user_stated` source becomes `inferred`; `MIND_EXTRACTION_ADDENDUM` says a wake writes no instruction for the owner and names the pack sections not to re-extract (standing instructions, intentions, memories). **Why**: wakes minted "the owner's standing instructions" under their name — one such row, heard/owner from `edward-mind`, was re-extracted and reinforced by every later wake (22 → 30 reinforcements in one morning) — and the pack renders heard/owner instructions as rules that "outrank everything below".
- **`scheduled_event`** (2026-09-27; `scheduler_service.SCHEDULED_EVENT_EXTRACTION_PROFILE`): a fired event's trigger is text Edward wrote to himself. Nothing extracted is stored as `heard`; quoted text is `read`; unlabelled rows are his own `thought`; a missing `about` means himself; an instruction about the owner is dropped; new facts are kept and a repeat does not reinforce. Under the chat profile a reminder's trigger ("For the July 7 notification to the owner … Edward should only send an in-app reminder") was stored as the owner's instruction — that is where two blanket "in-app only, never contact anyone" rules came from. Tests: `tests/test_scheduled_event_extraction_profile.py`, `test_scheduler_extraction_profile.py`.
- **An instruction is the owner's only when the owner's own turn said it** (`coerce_extracted_fields(..., turn_source=)`): heard/owner survives only in a turn in `OWNER_SPEAKS_SOURCES` (chat, voice, widget, Alexa, the owner's self-chat ping `ping_owner`, their own words after a ping `owner_ping`; with no turn known, only the chat profile keeps it); otherwise it becomes `read` (heartbeat, twilio, a friend's ping — `SOMEONE_ELSE_SPEAKS_SOURCES`) or `thought` (anything else). **The household hub's voice is not the owner's word** (`hub_voice`; `HOUSEHOLD_SPEAKS_SOURCES`): what is said at the panel stays `heard` but never `user_stated`, and `owners_own_word` refuses a row whose ref names that turn even though the hub's conversation is a `user` one (`memory_decay_service.NOT_OWNERS_TURN_SOURCES`) — so a guest's line never ranks, or is asked about, as the owner's. Extraction reads the turn source from the row's provenance or the current turn; `remember` passes it too, so remembering in the pulse or a fired event writes nothing as `heard`. Test: `tests/test_instruction_speaker.py`.
- **The owner's words from their pings** (2026-10-11): their own `@Edward …` text in any chat ("stop pushing me about soccer") is the owner speaking, but a group ping's turn is extracted under the heartbeat profile because other people's lines are in it. So after the ping turn the runner calls `memory_service.remember_owners_words(text, conversation_id=…, ping_id=…, chat_identifier=…)`, which extracts **only their text** under the `chat` profile with `turn_source="owner_ping"` — the row is heard/owner, the pack renders it under their standing instructions, and decay never lapses it as someone else's ([pings.md](pings.md)). Test: `tests/test_owners_words.py`.
- **Only the owner's own word rewrites what the owner said** (`_is_owners_own_heard`: the incoming memory is `heard` and `is_owners_word(source_ref, turn_source)`): a heard/owner row changes by UPDATE/MERGE only by what the owner said in a turn in which they speak; from a wake, the pulse, an event, heartbeat, twilio or a worker — and Edward's own `thought` or `read` row from the owner's chat turn (a `remember`, or extraction of his own answer, once put its words and its 30-day lapse on a pin) — the resolver's UPDATE/MERGE becomes KEEP_BOTH (DISCARD still stores nothing — it stops paraphrase pile-ups). **A rule the owner pinned is never rewritten here** (`is_owner_confirmed`: `source_ref` kind `owner_confirmed`), even by them: the resolver sees neither side's lifetime and chose UPDATE for a "Until Friday, don't reply to @edward mentions…" over a pinned rule (0.80 similarity with the real model, both tries), which took Friday's lapse with `owner_confirmed` still on top; the exception is now kept beside the rule and lapses on its own — above 0.92 too, where no resolver runs (the same stand-down scored 0.920 to the pin and had reinforced it while being stored nowhere, until `_lifetimes_apart` stopped exempting the owner's one-offs, below). Test: `tests/test_heard_rows_keep_owners_words.py`.
- **Reinforcement**: a near-duplicate (≥ 0.92) from a `mind`, `pulse` or `scheduled_event` turn only refreshes `last_used_at`, and an UPDATE/MERGE from those turns adds no reinforcement — a wake re-reading its own pack is not independent evidence. Reinforcement never demotes a row's tier. Reinforcing a row with no provenance keeps "unrecorded" as its origin (`provenance_service.merge_source_ref(None, new)` records the new source under `also` for every caller), so a later wake's ref cannot make a row from the owner's chat look like Edward's.
- **Live rows only, and no reopening**: conflict detection compares against live rows (`find_similar_memories(live_only=)`, results carry `valid_until`), so a closed intention can be decided again and the owner restating a lapsed instruction stores a new live heard/owner row (`tests/test_restated_instruction_after_lapse.py`). The one exception is a passive re-lift (`is_passive_relift`: post-turn extraction from a turn where the owner is not speaking): it searches retired rows too, and a retired top match ≥ 0.92 counts as already known — nothing stored, the retired row untouched; in 0.75–0.92 only a KEEP_BOTH stores, and a retired row is never rewritten. Verified forget still finds retired rows. Test: `tests/test_retired_rows_stay_retired.py`.
- **In the owner's own turn only what the owner said is a restatement**: a thought/did/read row lifted from Edward's earlier answers in the 10-message window can neither reopen a closed intention nor revive a retired row.

## Use credit is citation, and dated episodes stop at belief

- **A memory is "used" when the answer drew on it** (2026-09-27): `used_count` / `last_used_at` used to grow for every memory whose tag appeared in the prompt — retrieval under another name — so the rows retrieval favoured entrenched themselves (on the original install the 100 most-retrieved rows took 70 % of all retrievals). Inside a turn `mark_memories_used` only holds the shown ids; after the turn extraction credits a shown memory only when the answer reuses its distinctive words beyond what the owner's own message said — at least 2 words, or a quarter of a long memory up to 4 (`cited_memory_ids`). Not citation words: a fixed list ("owner", "edward", …), every word of the owner's configured names, bare and with a possessive "s" (`memory_service._citation_ignored`, from `EDWARD_OWNER_NAME` / `EDWARD_OWNER_FULL_NAME` / `EDWARD_OWNER_ALIASES` — nearly every memory names the owner), month names, weekday names and years. Outside a turn it credits immediately. `last_accessed` still bumps on retrieval, and `turn_log.memories_used` still counts memories shown in the prompt. The memory report's and the health report's "used" figures mean "cited". Test: `tests/test_memory_citation_credit.py`.
- **A dated episode never reaches knowledge**: a past date with a year, an ISO date, or a date after "on" (`names_past_date`) caps the tier at belief — in `_compute_tier(..., content=)`, in consolidation's hourly promotion pass (step 10), and in `update_memory`, which writes belief when asked to write knowledge on such a row (it does not demote a row already at knowledge). A bare "March 14" (a birthday) and future dates are not episodes, and a date right after birthday / anniversary / born / adopted is a durable fact (`_DURABLE_DATE`). Tests: `tests/test_memory_tier_ladder.py`, `test_dated_episode_write_cap.py`.

## Intentions, instructions and one-off preferences have horizons

- **Intention hygiene** (2026-09-25/26: every horizon-less intention a wake stored sat in "Open intentions" until a Sunday reflection happened to close it): `coerce_extracted_fields(item, profile=)` turns an `origin=did` intention into `context` (what he did is a record, never a plan) and, under the `mind` profile, gives an intention with no usable `valid_until` `now + MIND_INTENTION_DEFAULT_HOURS` (72). The mind extraction prompt says so, and that a decision to leave something alone is a `context` thought, not an intention. Remembering runs the same coercion — profile `mind` when the current turn's source is `mind` or `pulse`, `scheduled_event` in a fired event (`graph/tools._REMEMBER_PROFILES` / `_remember_profile`), else `chat` — and says the lapse out loud ("ok (memory_id: …) — this intention lapses <UTC> unless you give it a valid_until or link it to a wake"). `scheduled_events_service.create_event(memory_id=)` stretches a linked intention past its event (`extended_horizon`: fire + 1 day for a one-shot, 30 days for a recurring one) — a wake five days out used to outlive the intention it promised to hold. `close_intention` retires one and keeps its history ([mind.md](mind.md)). Tests: `tests/test_intention_hygiene.py`, `test_remember_tool.py`, `test_close_intention.py`.
- **A temporary instruction gets a 30-day horizon** (2026-09-27): `store_memory` gives any new `instruction` with `temporal_nature="temporary"` and no `valid_until` `now + TEMPORARY_INSTRUCTION_DEFAULT_DAYS` (30) — the horizon a recurring event's intention already gets, and four Sunday reflections' chance to renew one that still matters. A rule the owner means for good is `timeless` or `evolving` and never gets one; the owner's own temporary instruction is stored without it (decay already exempts it, below). **Sensitive content gets none** (as for a preference below): "Give Biscuit her ear medication at 6 am and 6 pm, per the pet sitter" got 30 days at store time, or on an UPDATE, and slipped past decay's hold — decay now decides: it holds what the owner said or Edward read, and lapses Edward's own one-off on its own horizon. So an UPDATE of sensitive one-off words over a lasting row still writes `temporary`, with no horizon (it had kept `evolving`, and Edward's own "For this week, give Biscuit her ear drops…" became an instruction held for good). Test: `tests/test_instruction_horizon.py`.
- **A temporary preference gets a 30-day horizon, whoever said it** (2026-09-27): about a fifth of the original install's live preferences were one-offs — an order, a weekend, a trip, "that night" — taking 38 % of preference retrievals, and nearly none had a `valid_until`. `store_memory` (through `_default_horizon`, which `default_valid_until(..., content=)` backs) gives a new `preference` with `temporal_nature="temporary"` and no `valid_until` `now + TEMPORARY_PREFERENCE_DEFAULT_DAYS` (30) — unlike an instruction, even in the owner's own words (a one-off is a one-off). A taste mislabelled as one lasts once the owner states it as lasting: inside the window, a `heard`, non-temporary preference from their own turn (`is_owners_word`) that reinforces or merges into the one-off writes its nature and clears the horizon (`_owners_lasting_word`) — a remembered preference is a thought, and a thought is temporary, so "<the owner> loves the spicy deluxe" remembered mid-turn used to lapse with its 30 days whatever the owner said next; after the window their words are stored again. **Sensitive content gets none** (`memory_decay_service.is_sensitive`): a row with a horizon is never looked at by decay again, so pets, health, family and money keep the pass's hold for the owner. Remembering says the lapse out loud ("— a temporary preference; it lapses <UTC> unless you give it a valid_until") — the kept row's: when conflict detection keeps an existing row and its lifetime, it names that row's horizon, or none. The extraction prompt (and the backfill and dedup prompts) calls a preference tied to one occasion, order, meal, trip, weekend, purchase or event, or to "right now" / "lately" / "this week", `temporary`; `timeless` is for a taste held for years ("{OWNER} dislikes bananas" — the prompts name the owner through the `{OWNER}` token, and the extraction examples carry no real phone numbers or people); someone else's preference is `about: contact`; `MIND_EXTRACTION_ADDENDUM` says the same. Rows already stored are untouched. Tests: `tests/test_preference_horizon.py`, `test_memory_extraction_profiles.py`.
- **A preference defaults to `evolving`** (`default_temporal_nature`), not `timeless`: remembering has no `temporal_nature` argument, so every preference stated through it was `user_stated` + `timeless` — the one pair decay holds forever. A thought is still `temporary`: `default_temporal_nature(memory_type, origin=)` returns `temporary` for `origin="thought"` unless the type is `intention` (`evolving`). Test: `tests/test_memory_extraction_defaults.py`.
- **An UPDATE carries a preference's lifetime** (`_update_lifetime`): when conflict resolution answers UPDATE with a preference, the row takes its `temporal_nature` and its horizon (its own `valid_until`, or the default above; none clears an old one via `update_memory(clear_valid_until=True)`) — "Rowan wanted salmon nigiri tonight" written over "Rowan likes salmon nigiri" used to keep the old open-ended life. **Any other type keeps a window it already has** and takes the new words' horizon (and nature) only when it had none — a one-off's `temporary` even when no horizon comes with it (sensitive text, the owner's own word): clearing every unnamed horizon (the first cut) made a 24-hour stand-down, restated with no window, permanent, put a wake's 72-hour intention back in "Open intentions" when a chat turn updated it, and let a caller with no nature (the dataclass default `timeless`) turn a two-week note timeless. **The owner's row takes none of it on anyone else's word**: `_update_lifetime` returns nothing for a heard/owner or `owner_confirmed` row unless the incoming memory is the owner's own heard word in their own turn. MERGE and reinforcement keep the existing lifetime, except the owner's lasting word over a one-off preference (above).
- **A lasting statement and a one-off are not folded together** (`_lifetimes_apart`, 2026-09-27): because a reinforcement or MERGE keeps the existing row's lifetime, a heartbeat-read "<the owner> likes oat milk in their latte" (0.925 with the real model) reinforced "<the owner> wants oat milk in their latte this week" and lapsed with it, and merged the other way "for Saturday's order" landed in an open-ended "likes" row. Except where the owner, in their own turn, states a one-off taste as lasting (`_owners_lasting_word` takes the horizon off), a ≥ 0.92 reinforcement or a MERGE between a lasting row (not `temporary`, no horizon — `timeless` and `evolving` alike) and a one-off (`temporary`, or ending at a horizon) keeps both — the owner's own words included: their one-off exception had reinforced the lasting rule or pin it excepts, and their lasting rule had reinforced Edward's week-long note of it and lapsed with it. Intentions are left to their own hygiene (a wake's 72-hour horizon is plumbing, not what the plan says); an echo still only refreshes `last_used_at`. Tests: `tests/test_memory_temporal_edges.py`, `test_preference_horizon.py`, `test_heard_rows_keep_owners_words.py`.

## Decay (`backend/services/memory_decay_service.py`)

`decay_stale_memories(dry_run=False)` runs after the Sunday nightly ([mind.md](mind.md)) and stamps `valid_until`; it never deletes. It returns `retired` (the count), `retired_ids`, `stamp` (the ISO `valid_until` it wrote, or None) and `by_rule`; the nightly's ledger row's `detail.decay` carries the counts and the `stamp` (not the id list — `mind_service.wake_ledger_detail` keeps the row parseable under the 600-char cap by shortening `tools` first). Replayed read-only against the original install's store, the older rules retired 0 rows; the 2026-09-27 rules would retire 73.
- **Age runs from creation, and use lengthens life at most 2×** (`MAX_USE_MULTIPLIER`): `last_used_at` and `last_accessed` were both stamped by retrieval and nothing recorded a citation, so retrieval used to reset a row's clock and multiply its half-life by 1 + log1p(used) without bound — the more a stale row was retrieved, the harder it was to forget (a reminder note from July had been retrieved 2,759 times).
- **A dated episode or a reminder echo earns nothing from tier or use** (`fixed_in_time`: an explicit date near creation, at least 14 days past, nothing recurring; `is_reminder_echo`, which matches "remind(ed) the owner", the owner's configured names, him, her or them), and the knowledge tier no longer protects it. A date with year 0000 is no date. "prefers" / "likes" keep a row out of the episodes only when it is not `temporary`, so a one-off preference that names its date ("<the owner> prefers a low-interruption weekend on September 26–27, 2026") is an episode, while a lasting taste citing a dated example is not; they always keep a taste about reminders from being a reminder echo.
- **The knowledge tier does not hold a `temporary` row** (2026-09-27: 36 live temporary rows sat on knowledge for good on the original install, among them a preference for an upcoming birthday used 33 times). The tier still multiplies the half-life; sensitive content and instructions keep their own holds.
- **A one-off instruction that is not the owner's own lapses after 30 days** (`INSTRUCTION_HORIZON_DAYS`): a `temporary` instruction lapses unless it is the owner's own word (`owners_own_word`: `source_ref` kind **`owner_confirmed`**, or `heard` in a `user` conversation or one of the owner's turns — `memory_decay_service.OWNERS_TURN_SOURCES`; the pass joins `conversations` to tell). **The horizon covers every instruction by default**; `EDWARD_INSTRUCTION_HORIZON_SINCE` (an ISO date or datetime; unset is 1970-01-01, i.e. every one-off instruction; read at import into `INSTRUCTION_HORIZON_SINCE`) exempts a migrated install's older backlog — set it to your upgrade day if you bring a store from an Edward that predates provenance, so instructions written before anyone could tell whose they were are not retired unasked. Leave it unset on a fresh install. **An instruction the owner keeps should carry `source_ref {"kind":"owner_confirmed"}`**: that pin is what decay, the pack and contradiction handling treat as settled.
- **Sensitive content is never auto-retired** (`is_sensitive`): pets, health, family, money, and someone in distress — the owner's call. The words are generic (vets, medications, doses, diagnoses, ear/eye/nose drops, hospitals, parents, grandparents, rent, loans, a body's pain…; the pattern ends words so "moment", "pillow" and "veteran" are not family, pills and vets, and bare affect words like worried or upset do not count while "her ear hurts" or a migraine does); **the names are the household's own**: `EDWARD_SENSITIVE_NAMES` (comma-separated pets, family, anyone whose mentions should be held, e.g. `Biscuit,Maple,Grandma June`) plus the people in `EDWARD_HOUSEHOLD` other than the owner, matched as whole words (`memory_decay_service.sensitive_names`; a configured "Pep" does not match "Pepper"). The owner's own name is never one: nearly every row names them. The hold applies only to rows with origin `heard` or `read` (the owner's world), never to Edward's own thoughts, actions or intentions (held for every row, it made a fifth of one store's thought/did/intention rows permanent).
- Still protected: stated timeless facts (`user_stated` + `timeless`), intentions a pending or in-flight scheduled event links to (`pending_intention_ids`, read from `event_metadata.memory_id`; `is_protected`), knowledge-tier rows that are neither temporary nor fixed in time, and instructions (except the one-off rule above). Nothing under `MIN_AGE_DAYS` (7).
- `backend/scripts/run_memory_decay.py` (dry run by default; `--apply`, `--limit`) prints counts by rule and, after `--apply`, the stamp and "undo with: --revert-stamp <stamp>". `--revert-stamp` clears exactly the rows one pass retired; `--revert-since` clears every future horizon too (open intentions, instructions with a window) — its help says so. Tests: `tests/test_thought_decay.py`, `test_memory_decay*.py`.
- The contradiction ranking uses the same `owners_own_word` rule, and so does `store_memory`.

## Consolidation (`backend/services/consolidation_service.py`)

- Hourly background loop that clusters related memories via `build_background_llm()`; creates `memory_connections` (links) and `memory_flags` (quality/staleness markers, contradictions); tables `memory_connections`, `memory_flags`, `consolidation_cycles`, `consolidation_config`. It merges by hard delete, so pause it before any bulk cleanup of your own.
- **Enabled by default** (`ConsolidationConfigModel.enabled` defaults to `True` and `init_db` seeds the row that way): read the live row in `GET /api/consolidation/status` (it carries the config), toggle via `PATCH /api/consolidation/config {"enabled": false}`. Failed merges count against `max_llm_calls_per_cycle` (2026-09-24; before that a failing LLM was retried for every pair every cycle). **Test stubs must patch `services.memory_service.build_background_llm` too** — `memory_service` imports it by name, and a stub on the wrong module spent real quota from the suite (~40 calls one day; the conftest network guard now refuses it).
- **On Codex the budget followed the quota** (2026-09-25): a cycle with no explicit budget gets `budget_for_cycle(config, decision)` — the stored `max_llm_calls_per_cycle` (15 when unset) ×3 (`SPARE_QUOTA_BUDGET_FACTOR`) while the rate gate's surplus decision allows spending with ≥ 15 % headroom, for that cycle only; the stored config is never written. On Claude the surplus decision always refuses (pay per token), so the stored budget holds. Test: `tests/test_consolidation_budget.py`.
- The hourly promotion pass (step 10) passes `content` to `_compute_tier`, so it knows a dated episode.
- **Entity narratives and dossiers are written from live memories only** (2026-09-27): after the audit retired hundreds of rows, many sensitive, each cycle would have written them back — step 11 builds "Narrative: <name>" from the rows an entity's mentions link to, and `get_memory_by_id` returns a retired row too. The lookup takes only mentions of live rows, before its limit (`get_entity_memories(live_only=True)`, at most 10 — `NARRATIVE_MAX_MEMORIES`), and a narrative is written from those rows alone, never from the old one, so a rewrite drops what was retired. An entity left with fewer than five live rows gets no narrative: its own system-generated one (exactly `Narrative: <name>` with the `system_generated` and `entity:<name>` tags — never a document the owner titled that way, nor another entity's) is deleted rather than kept with retired text, and it uses none of the cycle's narrative slots. The narrative is the name's, so it goes only when **no entity of that name** has five live rows (names are shared — a pet and a topic called "Biscuit" — and in the unordered hourly query the thin twin deleted the narrative the rich one had just written, wasting its model call each cycle); each entity's live rows are read once a cycle. Documents written before a retirement keep that text until they are rewritten. Test: `tests/test_narratives_from_live_memories.py`.
- **Consolidation never merges the owner's row** (2026-09-27): the merge step (step 8) skips any pair with a heard/owner row (`memory_service._is_owners_row`) on either side, before the merge call — their row against one that is not theirs, and two of their own. A merge rewrites one row with the LLM's text and hard-deletes the other; most of the owner's near-duplicate pairs were separate episodes a merge would lose (the same lawn service in July and a September reschedule), and the `owner_confirmed` pins are heard/owner rows too. The owner restating something reinforces their row at store time, in their own turn. Test: `tests/test_consolidation_merge_keeps_owners_words.py`.
- **Nor two rows of different lifetimes**: the survivor keeps its own `temporal_nature` and `valid_until`, so a one-off ("<the owner> wanted the spicy deluxe for Saturday's order") merged with a lasting taste ("<the owner> likes the spicy deluxe", 0.886 with the real model) made the taste lapse and deleted the lasting row — or made Saturday's order open-ended. Step 8 skips a pair whose `temporal_nature` differs or that has a horizon on one side only (`same_lifetime`), before the merge call. Store-time conflict detection keeps the two apart the same way (`_lifetimes_apart`, above). Test: `tests/test_consolidation_merge_keeps_lifetimes.py`.
- REST API: `PATCH /api/consolidation/config`, `GET /api/consolidation/status`, `GET /api/consolidation/cycles`, `POST /api/consolidation/trigger`, `GET /api/consolidation/connections?with_content=true` (both memories' text), `GET /api/consolidation/flags`, `GET/PATCH /api/consolidation/flags/{id}` (one flag with both texts — a deep link past the newest page is read, never guessed "settled"), `POST /api/consolidation/flags/{id}/resolve {keep}` (keep one, retire the other — the Dreaming panel's call and Today's inline choice). Test: `tests/test_consolidation_resolve_endpoint.py`.

### Contradiction flags

**Why**: on 2026-09-27 the original install had 352 unresolved flags, created at 48–80 a day and resolved at 3–11; 288 were duplicates of an existing pair, and the "Which is right?" questions on Today were mostly about things the owner never said.
- **One open flag per memory pair**: a cycle collects everything the model reports and writes a flag only for a pair with no open flag, dropping a pair reported twice in one cycle in either order. A pair the owner was asked about and left unanswered, or that Edward kept both of (`[kept both]`), is not flagged again for 30 days (`REASK_AFTER_DAYS`) — both rows stay live, and re-flagged every hour the pair would take one of the cycle's five slots.
- **A flag whose side has lapsed or is gone closes itself** (`memory_lapsed`, `moot_reason`) without retiring anything. `resolve_contradictions` re-reads both rows just before each verdict, so a row an earlier flag retired in the same pass makes the next flag on it moot (deciding on rows read up front once retired both sides of a pair flagged twice in swapped order, and let a retired row retire a third).
- **At most five new flags a cycle** (`MAX_NEW_CONTRADICTION_FLAGS_PER_CYCLE`); pairs left out come back later.
- **Ranked by `contradiction_priority`** — a sort key: the owner's own word first (`memory_decay_service.owners_own_word`, the conversation's source looked up once per side via `conversation_sources_for`), then the higher importance plus 0.1 · log1p(total `used_count`); ties go to the oldest pair.
- **No automatic verdict over a row the owner did not speak**: `decide_contradiction` picks no winner by label when either side was written in a turn where the owner was not speaking — wake rows are all `inferred`, so the old rank rule retired newer wake-read facts without asking. **`rank_says_who` also reads the row's thread and the audit's stamp**: a row from a heartbeat, journal/wake (`edward_thought`), scheduled-event or worker thread (`mind_service.NOT_OWNERS_CONVERSATION_SOURCES`), or one an audit moved off `heard` (`audit_moved_off_heard`: an `audit` ref with op `relabel` or `demote` from heard), is never ranked by its label. Replayed on the original install's open flags, the first cycle after re-enabling consolidation would otherwise have retired a corrected pet-care rule in favour of a week-old episode; with the rule every one of them closed `[kept both]`.
- **A label never retires a sensitive or knowledge-tier row**: when rank or reinforcement would retire a row the decay pass holds as sensitive (`memory_decay_service._held_as_sensitive` — pets and their meds, health, family, money, distress, in the owner's world) or one at the knowledge tier, the pair is the owner's call if a side is their own word, else both are kept (`_retirable`). Decay already never retired either; the contradiction pass was the one path left that did.
- **A pin the owner confirmed is settled**: a side with `source_ref` kind `owner_confirmed` is kept as it is against any row: never retired, never `open`, so never a "Which is right?" question. What a pin says changes only when the owner says so in their own turn. Tests for the three rules above: `tests/test_contradiction_settled_rows.py`.
- **The owner is asked only when a side is their own word** (`_owner_stated`, the `owners_own_word` rule, with each row's conversation source read once per pass): otherwise the verdict is `keep_both` — the flag closes with a `[kept both]` marker (`KEPT_BOTH_MARK`; an earlier needs-the-owner marker is removed) and no memory is retired, rewritten or deleted. An open question is marked `NEEDS_OWNER_MARK`, which renders as `[needs <owner name>]` (`[needs the owner]` when `EDWARD_OWNER_NAME` is unset), and the verdict reasons name the owner and say "they". Replayed over ten days of new pairs on the original install, most had a side written while the owner was not speaking (Edward's own did/self and thought/self logs) and none of those was the owner's word: asking meant a question on Today every day about nothing they said. The same holds for a tie between two `user_stated` rows: open for the owner only when a side is their own word, else `keep_both`. With both rules the owner is asked about once or twice in ten days instead of daily. The daily triage applies the same check before any LLM call (`triage_flag` → `kept_both`, which closes the pair's duplicate flags too), and **asks the owner, or spends a model call, only on an `open` verdict**: a pair the label decides is `left_for_consolidation` — untouched, unasked — and a flag naming one memory closes (`missing_resolved`). Closing a flag also drops its `[FLAG: …]` note from retrieval. Tests: `tests/test_consolidation_contradiction_tie_stays_open.py`, `test_contradiction_surplus.py`.
- **One "Which is right?" question at a time** (`contradiction_triage_service.triage_unresolved`, which counts memory pairs, not flags): a pair with a flag already asked waits with it, a stale pair closes all its flags, otherwise only one flag per pair is triaged; a flag with a lapsed side is closed without asking (`lapsed_resolved`); on the note path, while another "Which is right?" note is live and its flag still open, the flag is `deferred` — no LLM call, not marked asked — checked again just before writing. The Sunday nightly runs it by note with at most one question ([mind.md](mind.md)). Today shows same-title notes as one card anyway.
- Questions (push or Today note) link to the Dreaming panel, `/settings/dreaming?flag=<id>` (`&ask=rewrite` for a proposed rewrite, which Today does not offer as "keep one"; `contradiction_triage_service.flag_url`). Tests: `tests/test_contradiction_links.py`, `test_consolidation_contradiction.py`.

## Entity extraction

(`entity_service.py`, off the critical path since 2026-09-05) 90 s (`ENTITY_TIMEOUT_SECONDS`; 30 s was still under the call's p90 and half the calls timed out, each a paid request thrown away), each of the last ten messages clipped to 4,000 chars; on Claude the background route, on Codex `EDWARD_ENTITY_MODEL` at `low` effort. Test: `tests/test_entity_extraction_budget.py`. The memory graph (`graph_ingest_queue`, the Graphiti/kuzu worker) is optional and off by default, and takes two switches: `GRAPHITI_ENABLED=true` makes `graph_memory_service.add_episode_from_memory` queue every new memory (and lets the worker start; `scripts/install-launchagents.sh --with-graph` installs it), and `GRAPHITI_INGEST_ENABLED=true` starts the worker's ingest loop, which drains the queue into the graph (`backend/workers/graph_worker.py`). Without the second the worker only answers `/search` from an empty graph and the queue grows a row per memory with nothing to prune it; the reference install kept ingestion off while it chased Kuzu crashes during ingestion, which is why it is separate. Each ingest takes 80–130 s and a few `background`-route calls (`graphiti_adapters.BackgroundLLMGraphitiClient`, inside the daily spend cap); a row that crashes the worker three times is quarantined as failed. `POST /api/memory/graph/backfill` queues the memories already stored, and `/api/memory/graph/*` reports it.

## Reflection and deep retrieval

**Memory Reflection** (`backend/services/reflection_service.py`)
- Post-turn fire-and-forget enrichment: 3–5 queries via `build_background_llm()` to find related memories, stored in `memory_enrichments`, loaded on the next turn. Skips `edward-mind` / `edward-surfaces`.
- The whole reflection is bounded by the query budget plus 15 s (`reflection_outer_timeout()` = `dream.context.REFLECTION_TIMEOUT_SECONDS` + `REFLECTION_OUTER_MARGIN_SECONDS`, read per call). It was a hard-coded 10 s around a 20 s query budget, so a reflection whose queries took 11–20 s was cancelled after the model had answered. Test: `tests/test_reflection_outer_bound.py`.

**Deep Retrieval** (`backend/services/deep_retrieval_service.py`)
- Pre-turn gated multi-query memory search: 4 parallel queries (original + 3 rewritten via `build_background_llm()`) when the message is short or turn_count ≥ 3; context budget `MAX_MEMORY_CONTEXT_CHARS` = 8000. Voice turns skip it (`fast_context`).
- **Query generation is never cancelled** (2026-09-21): `services/dream/context.generate_search_queries(..., timeout=)` waits `DEEP_RETRIEVAL_TIMEOUT_SECONDS` (5 s) before a turn and `REFLECTION_TIMEOUT_SECONDS` (20 s) after it; a call that outlives its caller keeps running (`_inflight`) and lands in the shared cache for the next caller. Before this a 5 s ceiling cancelled 1,615 calls in a day — each a request paid for nothing, and neither subsystem ever saw a query. Test: `tests/test_dream_query_timeout.py`.
- `services/dream/*` is memory retrieval (query cache, hot memories, speculative recall — the stream's "Dreaming…" progress step), nothing to do with the removed dream synthesis.

## Search tags

`backend/services/search_tag_service.py`: 5–10 keywords (topics, entities, intents) per conversation from the last 5 messages via `build_background_llm()`, stored in `conversations.search_tags` for full-text search; post-turn, fire-and-forget, no tools; skips Edward's mind and surfaces threads.

## Document store (`backend/services/document_service.py`)

- Persistent storage for full documents (recipes, notes, reference guides, pet records, dossiers, narratives, `Edward: state`).
- Embedding: same sentence-transformers model as memories, embeds `title + content[:500]`; hybrid 70 % vector + 30 % BM25.
- Relevant document titles surface in LLM context (title + ID only); state documents (tag `state`) ride the prompt's "Active State" block ([tool-loop.md](tool-loop.md)); the model reads full content with the `memory` tool's `doc_read` (the legacy `read_document`).
- Tools: the toolset's `memory` doc actions; under `EDWARD_TOOLSET=legacy` `save_document`, `read_document`, `edit_document`, `search_documents`, `list_documents`, `delete_document`.
- REST API: `GET/POST /api/documents`, `GET/PATCH/DELETE /api/documents/{id}`.
- Frontend: DocumentBrowser — Edward tab → Memory → Documents (`?id=<doc>` opens one).
- `document_service.get_document_by_title("Edward: state")` is the mind's state document ([mind.md](mind.md)); never delete it — rename or archive only.
