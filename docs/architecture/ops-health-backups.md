# Operations: the host Mac, deploys, health, backups

How to keep a self-hosted Edward running: the host Mac and its LaunchAgents, setup, restarting and deploying (the staged frontend build and its rollback), logs, pinned dependencies, the health watchdog, the memory report, and backups and restores. Most rules here came from an incident on the reference install, which ran one person's Edward for months; the date says which. The short version of the rules is in CLAUDE.md. The PWA's auth and caching rules are in [auth-and-pwa.md](auth-and-pwa.md); tests and the test cluster in [testing.md](testing.md). What is bespoke to the reference install, and how to change it, is in [ADAPTING.md](../ADAPTING.md).

## The host Mac

Edward runs natively on one always-on Mac (a Mac mini makes a good host): it reads iMessage, Calendar, Reminders and Mail through macOS, so the backend never runs in Docker or on Linux.

- **The checkout is wherever you cloned it.** Every script finds the repo from its own location (`scripts/lib/edward-env.sh` sets `EDWARD_REPO`), and the LaunchAgents point at the checkout you ran the installer from. That checkout is live: an edit there takes effect at the next restart, and a frontend build there replaces what every phone loads. Do builds, the harness and experiments in a git worktree, never in the checkout that serves.
- **Settings for the shell scripts** come from `scripts/lib/edward-env.sh`: the process environment first, then the checkout's `.env`, then the script's default. launchd starts the health check, the backup and the frontend with an empty environment, so without this a value you put in `.env` (`EDWARD_LAUNCHD_PREFIX`, `EDWARD_BACKUP_DIR`, `EDWARD_TUNNEL_LABEL` …) would reach the backend (which loads `.env`) and not the scripts around it. `.env` is parsed, never sourced, so a script that needs one label does not execute the rest of the file. `EDWARD_ENV_FILE` points at another file (tests point it at one that does not exist). `HOMEBREW_PREFIX` overrides Homebrew's location (default `brew --prefix`, else `/opt/homebrew` or `/usr/local`); the installer writes it into every LaunchAgent, so no job runs `brew --prefix`, which is Homebrew's own code and writable by Edward's shell.
- **The launchers' PATH puts the system first** (review 2026-10-12): the LaunchAgents, `backend/start.sh`, `backend/start-graph-worker.sh` and `frontend/run-launchd.sh` run outside Edward's sandbox, and his shell can write the user's home and the Homebrew prefix (he may `brew install`), so a program they run by bare name (`curl`, `stat`, `sips`, `osascript`) must be the system's copy. `scripts/lib/edward-env.sh::edward_service_path` is `/usr/bin:/bin:/usr/sbin:/sbin`, then Postgres 16's tools (`edward_pg_bin`), then Homebrew's `bin` and `sbin`, then `/usr/local/bin`; never `~/.local/bin` or `~/bin`. The backend's two start scripts put the venv's own `bin` (inside the write-protected checkout) ahead of it, and run `uvicorn` and pip by absolute path; the frontend's agent runs Next as `node <checkout>/frontend/node_modules/next/dist/bin/next start -p 3000`. A tool installed only in `~/.local/bin` (the `codex` CLI, `uvx` from its standalone installer, the `claude` CLI) is no longer found by the backend: install it with Homebrew, or link it into Homebrew's `bin`. What Homebrew's prefix itself still allows is in [computer.md](computer.md#what-the-sandbox-does-not-prevent).

### First-time setup

`./setup.sh` installs everything and is safe to run again (each step checks what is there):

1. checks for macOS on Apple silicon, the Xcode command-line tools and Homebrew. On an Intel Mac, in a Rosetta (x86_64) shell, or with an x86_64 python@3.12 or backend venv, it stops before anything is installed (2026-10-12): the pinned PyTorch (`backend/constraints.txt`, through sentence-transformers) has no x86_64 macOS wheel, so pip used to fail at step 5 after Homebrew and the database were already set up. Under Rosetta it suggests `arch -arm64 /bin/bash ./setup.sh`; `setup.sh::arch_problem` and `python_arch_problem` decide, tested in `scripts/test_setup.sh` with stubbed `uname`, `sysctl` and `brew`;
2. `brew install python@3.12 postgresql@16 node` and starts Postgres 16;
3. builds pgvector (v0.8.2) from source against Postgres 16 — Homebrew's pgvector bottle no longer ships files for postgresql@16;
4. creates the role and database `edward`/`edward` (password `edward`) with the vector extension;
5. makes the backend's venv (`.venv` in `backend/`) with python3.12, installs `requirements.txt` with the pins in `backend/constraints.txt`, and installs Playwright's headless shell (Edward's own invisible browser);
6. `npm ci` in `frontend/`;
7. creates `.env` from `.env.example` if there is none and asks for your name, your Anthropic API key and your time zone.

Flags: `--with-test-db` (the backend tests' own cluster on :5433, [testing.md](testing.md)), `--launchagents` (install the LaunchAgents at the end), `--no-helpers` (skip the Swift media and EventKit helpers), `--non-interactive` (never prompt; takes `EDWARD_OWNER_NAME`, `ANTHROPIC_API_KEY` and `TIMEZONE` from the environment). Then start Edward one way or the other, never both: `bash scripts/install-launchagents.sh` (at login, kept alive by launchd; `--launchagents` runs it at the end of setup, and setup's closing steps then say launchd is starting him) or `./restart.sh` (by hand, now). Open `http://localhost:3000` **on the host Mac** and choose a password: the first one needs the one-time setup code the backend keeps in backend/.setup_code while no password exists (cat it on the Mac; mode 0600, deleted once a password is set), and is refused from any page but this Mac's localhost ([auth-and-pwa.md](auth-and-pwa.md#backend-auth)). Setup's closing steps (`setup.sh::print_next_steps`, step 2), the installer's closing lines and `restart.sh`'s summary say where the code is, never what it is, in one shared line: "First time? Your setup code is in backend/.setup_code (cat backend/.setup_code)" (`scripts/lib/edward-env.sh::edward_setup_code_note`, which asks `GET /api/auth/status` through `edward_password_state`). Setup and the installer print it unless the backend answers that a password is set, so also while it is stopped or still starting; `restart.sh` prints it when the backend says no password is set, or is still starting and has not answered, and never after the backend failed. The harnesses (`scripts/test_setup.sh`, `scripts/test_install_launchagents.sh`, `scripts/test_restart.sh`) stub curl, so no test asks a live backend.

**macOS permissions** (System Settings → Privacy & Security), only for what you use — setup prints the exact paths:
- **Full Disk Access** for the real path of the python3.12 the venv is built on: reading `chat.db` (iMessage), Mail's Envelope Index and Calendar's database, and backups to a removable drive all go through it.
- **Automation**: macOS asks the first time Edward sends a message or drives Chrome.
- **Calendars and Reminders**: `bash backend/scripts/eventkit_request_access.sh`.

**pgvector**: `brew reinstall postgresql@16` (or an upgrade that replaces the keg) removes the source-built extension; run `./setup.sh` again. The test cluster on :5433 uses the same binaries, so it has pgvector too.

**The FDA python**: grants are path-based. The backup LaunchAgent runs under the real path of the venv's base python3.12 (`EDWARD_FDA_PYTHON` picks another); a `brew upgrade python@3.12` moves the binary, so backups and chat.db reads stop until you grant the new path and run `bash scripts/install-launchagents.sh` again. A plain `brew install` of something that pulls python@3.12 forward has the same effect, which is why the media pipeline avoids ffmpeg ([media.md](media.md)).

### LaunchAgents

`bash scripts/install-launchagents.sh` writes and loads the agents (`--with-graph` adds the graph worker, `--without-backup` leaves the backup out, `--dry-run` prints each plist and changes nothing, `--uninstall` unloads and deletes every agent with the prefix). Labels are `<EDWARD_LAUNCHD_PREFIX>.<service>`, default `com.meet-edward.*`; plists go to `~/Library/LaunchAgents` (`EDWARD_LAUNCHAGENTS_DIR`). Running it again rewrites only what changed: an agent whose plist is the same stays loaded and running. The plists are generated from the checkout's path, never committed.

- **It takes over from a hand-started Edward** (2026-10-12): after unloading the old backend or frontend agent and before loading the new one, it stops the copy this checkout started outside launchd (`./restart.sh` before the agents existed, `start.sh` in a terminal), found as `restart.sh` finds it (`edward_checkout_pids`, minus what the agent itself launched, `edward_not_launched_by`), so launchd's copy can take the port. `--dry-run` only reports them. A port held by a process from another checkout or another app is named, never touched; launchd's copy retries every 10 s until it is free. Its closing lines (`next_steps`) say the first start takes a few minutes, which logs to tail, where the first password's setup code is (until a password is set), the full path of `restart.sh`, and how to uninstall.
- **It has no idea which checkout the loaded agents serve**: the labels belong to your macOS user, not to a checkout, so running it in a second clone or a worktree unloads your running Edward's agents and loads ones that run that clone. `restart.sh` checks before it kickstarts (below); the installer does not. On a Mac that runs Edward, develop with the tests and the UX harness, never the installer ([testing.md](testing.md)).

| Agent | What it runs | Log |
|---|---|---|
| `<prefix>.backend` | `backend/start.sh`, always on (`KeepAlive`, 10 s `ThrottleInterval`) | `/tmp/edward-backend.log` |
| `<prefix>.frontend` | `frontend/run-launchd.sh`, always on; it rotates its own log | `/tmp/edward-frontend.log` |
| `<prefix>.graph-worker` | `backend/start-graph-worker.sh`, only with `--with-graph`; without `GRAPHITI_ENABLED=true` it sleeps 30 s and exits, so launchd backs off. It drains the ingest queue only with `GRAPHITI_INGEST_ENABLED=true` ([memory.md](memory.md)). It runs `init_db` too | `/tmp/edward-graph-worker.log` |
| `<prefix>.healthcheck` | `scripts/health_check.sh` every 5 minutes | `/tmp/edward-healthcheck.log` |
| `<prefix>.healthcheck-deep` | `scripts/health_check.sh --deep` at 08:00 | the same |
| `<prefix>.backup` | the nightly backup at 03:30, through `backend/scripts/run_backup_with_fda.py` | `/tmp/edward-backup.log` |
| `<prefix>.memory-report` | `backend/scripts/memory_health_report.py --push` at 09:05 | `/tmp/edward-memory-report.log` |

A daily job whose time passes while the Mac sleeps runs at the next wake.

**Optional agents are yours to install**:
- **A tunnel** (cloudflared, ngrok …) if Edward should be reachable from outside your network. Name its LaunchAgent label in `EDWARD_TUNNEL_LABEL` and its public origin in `EDWARD_PUBLIC_BASE_URL`, and the health check watches and restarts it. With Cloudflare Tunnel: pin the protocol to http2 if QUIC flaps on your network (it did on the reference install), and know that the tunnel gives up on a request after 100 s (a 524) — which is why long operations answer **202** and run as tracked tasks (`POST /api/mind/wake`, an approved Codex spawn).
- **The WhatsApp bridge** (the whatsapp-mcp project's Go bridge) if you use WhatsApp. `backend/start.sh` no longer starts it; run it under its own LaunchAgent. It logs (and shows its pairing QR) to `MCP_WHATSAPP_BRIDGE_LOG`, default `/tmp/whatsapp-bridge.log` ([integrations.md](integrations.md)).

### Restarting

```bash
launchctl kickstart -k gui/$UID/com.meet-edward.backend    # <prefix>.backend
launchctl kickstart -k gui/$UID/com.meet-edward.frontend   # <prefix>.frontend
./restart.sh [frontend|backend]                            # the same, or by hand without agents
```

- **Prefer `launchctl kickstart -k`**, which restarts launchd's own process atomically. `./restart.sh` does exactly that when the agent is loaded; without agents it stops and starts the processes itself (TERM, then KILL after 5 s), moving the previous log to `.prev` so a crash trace survives.
- **Only its own checkout's agents** (2026-10-12): before it stops or kickstarts anything, `restart.sh` checks that a loaded agent runs this checkout (`edward_agent_serves`: the working directory and program arguments `launchctl print` shows, then those of the plist it was loaded from; exact, so a worktree nested inside the live checkout is not taken for it). An agent that runs another checkout, or one it cannot identify, is refused with exit 78 and a message naming both checkouts and pointing at the tests and the UX harness. A second clone keeps the default prefix, so without this its `restart.sh` kickstarted someone's live Edward. With its own agent loaded, it first stops a copy this checkout started by hand that holds the port (launchd's copy could never bind behind it), and names a holder from outside the checkout instead of touching it.
- **It waits, and says how it went**: it launches the backend first, then the frontend (a long first build never holds the backend up), then polls each one's `/health` or page: up to 120 s for the backend (the embedding model's first download, `init_db` on an empty database) and 240 s for the frontend (a cold `next build`). A process still running at the deadline is "still starting — tail -f /tmp/edward-backend.log" and exit 0; one that died prints its log tail and exits 1. With an agent loaded, a crash loop shows only at the deadline. It is written for macOS's `/bin/bash` 3.2 and is sourceable for tests (`RESTART_LIB_ONLY=1`): `bash scripts/test_restart.sh` stubs `launchctl`, the listeners, curl and the start and stop steps.
- **Why**: the old `restart.sh` killed the listener and then started its own copy, racing launchd's `KeepAlive` respawn (within the 10 s throttle) — one of the two lost the port and left an orphan `next-server` / `uvicorn` chain on no port. It also killed every `next-server` on the machine. It now touches only this checkout's processes: the port's listeners and the `uvicorn` / `next` processes whose working directory is inside the checkout (`edward_pids_under`).
- A kickstart SIGKILLs uvicorn, which re-parents its stdio MCP servers to launchd; the startup orphan sweep kills them on the next boot ([integrations.md](integrations.md)).
- `backend/start.sh` runs with the venv's `bin`, the system's directories, Postgres 16's tools (`edward_pg_bin`: `EDWARD_PG_BIN`, else Homebrew's postgresql@16 keg, which is keg-only, so a fresh install has no `psql` or `pg_config` on PATH) and Homebrew's, in that order (above; `start-graph-worker.sh` likewise). **It no longer sources `.env`** (review 2026-10-12): a value in the environment a process starts with can be read by any other process of the same user, Edward's sandboxed shell included (`KERN_PROCARGS2`), so the API keys stay out of it. It reads only what it decides on (`edward_backend_env`: `EDWARD_BACKEND_HOST`, `DATABASE_URL` for its banner, `TOKENIZERS_PARALLELISM`, `OBJC_DISABLE_INITIALIZE_FORK_SAFETY`; the graph worker also `GRAPHITI_ENABLED`), exports the `~/…` paths `.env` holds already expanded (`edward_export_home_paths`; python-dotenv does not expand `~`), and `main.py` loads the rest itself, the environment winning — before, `.env` overrode what the shell exported. The backend loads only the repo root's `.env`: with only a `.env` in backend/ (an old fallback), `start.sh` warns and the backend runs without its settings, so move it up. It installs dependencies when `requirements.txt` or `backend/constraints.txt` is newer than its marker (`.venv/bin/python -m pip`), and runs `.venv/bin/uvicorn` without `--reload` (reload mode forked a watcher whose orphaned worker kept :8000 while launchd respawned copies that could not bind). `EDWARD_BACKEND_HOST` picks the interface: `0.0.0.0` by default so LAN devices (a household hub, a phone at home) can reach the API, `127.0.0.1` to keep it to this Mac behind the frontend or a tunnel.

### Chrome and the browsers

- **Edward's hands in your Chrome are off by default** (`EDWARD_CHROME_HANDS=on` turns them on). On, Edward uses your own Chrome through the Edward extension (`chrome-extension/`, loaded once via chrome://extensions → Load unpacked), and `screen_window_service` finds or opens the `/screen` tab over AppleScript and sizes it to the desktop — never a fullscreen Space, which a mouse user cannot easily leave. Chrome shows its "is being debugged" bar unless `EDWARD_CHROME_SILENT_DEBUGGER=on`. Off, `/screen` is an ordinary page: open it in any browser by hand. Details: [screen-and-browser.md](screen-and-browser.md).
- **A second Google Chrome instance must never be launched**: it hijacks `open -a` and `tell application "Google Chrome"`. The dedicated headless Chrome and its `/screen` LaunchAgent of earlier builds were removed on 2026-09-07.
- **Edward's own invisible browser** is Playwright's bundled headless shell, which setup installs and `services/headless_browser.py` asserts before launch — never Google Chrome ([computer.md](computer.md)).

### Logs

`/tmp/edward-backend.log`, `/tmp/edward-frontend.log` (the previous run's as `.prev`), `/tmp/edward-graph-worker.log`, `/tmp/edward-healthcheck.log` and `~/.edward-health/health.log` (the watchdog), `/tmp/edward-backup.log`, `/tmp/edward-memory-report.log`, and your tunnel's own log. The health check rotates the backend and frontend logs past 100 MB by copy-and-truncate (launchd holds them open, so a rename would leave the process writing to the orphaned file) and keeps the five newest gzip archives.

**The access log is redacted** (2026-09-27): uvicorn wrote every request line, query string included, to the world-readable backend log, and the Scriptable widget authenticates with `GET /api/widget?token=…` (the presence stream with `?token=` too), so the widget token sat there several times a minute. `backend/services/access_log.py` (`RedactSecretsFilter`, stdlib only) rewrites `token`, `key`, `api_key`, `code`, `state` (an OAuth callback's, 2026-10-11), `password`, `secret` and their `*_token` / `*_key` / `*_secret` / `*_password` relatives to `[redacted]`; `backend/log_config.json` is uvicorn's own config plus that filter on both handlers (access lines carry the same timestamp as every other line); `start.sh` runs `uvicorn main:app --host … --port 8000 --log-config log_config.json` (the flag sits after `--port` so `restart.sh`'s process match still works). Lines written before the filter can be masked in place by `backend/scripts/scrub_log_secrets.py` (it keeps the file's size and inode so launchd keeps appending, and rewrites `.gz` archives); after that, regenerating the widget token is optional. Known gap: `services/log_setup.py` sets `uvicorn.error` not to propagate, so its post-startup errors bypass the filter (nothing sensitive goes there today).

## The frontend is a production build

**Since 2026-09-06**: `frontend/run-launchd.sh` runs `ensure-build.sh` (`next build` only when a source file is newer than `.next/BUILD_ID`; test: `bash frontend/test_ensure_build.sh`) and then `next start`. The reference install ran `next dev` in production before that — 11.5 MB of unminified JS on every cold open of the PWA, and dev chunk names never change, so the service worker's 30-day `CacheFirst` served last week's `settings/all` page against this week's runtime. Hashed production chunks end that. A failed build falls back to `next dev` so the app stays reachable; the log says why. `next build` lints, and a lint **error** fails it — so one unescaped apostrophe in JSX silently puts production back on `next dev` (a 2026-09-26 review found exactly that). `__tests__/buildLint.test.ts` lints `app`, `components`, `lib` with the build's config; tsc and the unit tests do not catch it. The generated `public/sw.js` / `workbox-*.js` are gitignored.

**Build before the swap** (2026-09-27): a deploy used to kickstart the frontend and let `run-launchd.sh` build afterwards, with the old server already gone — about a minute of 502s through the tunnel, longer on a cold build. Now:

```bash
git pull
bash frontend/deploy-build.sh                               # builds into .next-staging; the site stays up
launchctl kickstart -k gui/$UID/com.meet-edward.frontend    # <prefix>.frontend; swaps in seconds
```

- `deploy-build.sh` builds into `.next-staging` while `next start` keeps serving `.next`, takes a lock (`.next-staging.lock`, stale after 60 min), and writes the `EDWARD_STAGED` marker (`build_id=…`) last, so a running or failed build never looks complete. Exit 0 staged, 1 failed or another deploy build running. A failed build leaves no staged build, so a restart builds in place as before (and falls back to `next dev` if that fails).
- On start, `ensure-build.sh::swap_staged_build` swaps in a complete, newer staged build and keeps the replaced one as `.next.prev` (minus its ~250 MB webpack cache); an incomplete staged build is left alone and an older one discarded. With no staged build nothing changes. Only `required-server-files.json` names the staging dir, and `next start` reads nothing from it but an experimental flag, so a build moved to `.next` serves as it is (proven on a spare port: every poll answered 200 during the build, and the swap took 0 s).
- **Each build's service worker travels with it**: next-pwa used to write `public/sw.js` and `workbox-*.js` at the client compile, whatever the distDir — before type checking and lint could still fail the build — and the new worker precached manifests the old server 404s, so its install failed. `next.config.js` now points next-pwa's `dest` at `.next-staging/EDWARD_PWA/` when `NEXT_DIST_DIR` is `.next-staging` (every other build still writes `public`); `deploy-build.sh` also snapshots `public/`'s worker files and puts them back when the build ends; the swap installs `<build>/EDWARD_PWA/` into `public/` and keeps the replaced pair in `.next.prev/EDWARD_PWA/`.
- **tsconfig**: `next build` rewrites `tsconfig.json` when its distDir's types include is missing; the file is tracked and a newer one would trigger an in-place rebuild right after the swap, so `deploy-build.sh` puts it back byte for byte with its old mtime. For the staged build only, tsconfig includes `.next-staging/types` and no other build's types — a staged build that also type-checked the served build's route types failed with TS2307 after a route was deleted (2026-09-27). The permanent tsconfig also lists `.next-staging/types/**/*.ts`.
- **Rollback**: `bash frontend/rollback-build.sh` then `launchctl kickstart -k gui/$UID/<prefix>.frontend`. It swaps `.next` and `.next.prev` (running it again undoes it), puts that build's service worker back in `public/` and touches its `BUILD_ID`, so the restart serves it instead of rebuilding. **Never a bare `mv .next.prev .next`**: the restart rebuilds the bad code in place. It refuses while a deploy build runs or a staged build waits. The rollback holds until the next source change, which rebuilds in place as any change does.
- `frontend/.gitignore` ignores `.next-staging/`, `.next-staging.lock/` and `.next.*/` (covers `.next.prev`, the rollback's temp dir and any hand-made `.next.bad`), so none can be committed from the live checkout.
- **Bundle budget** (2026-09-27): `frontend/scripts/bundle-budget.js` computes first-load JS exactly as `next build` prints it (gzip level 9 over each route's `app-build-manifest.json` files) and `ensure-build.sh` / `deploy-build.sh` run it after a successful build. A route over budget prints a `WARN` line — in `deploy-build.sh`'s own output for a staged deploy (the swap on start never reports), or in `/tmp/edward-frontend.log` when `ensure-build.sh` builds in place under launchd; it never fails a build (a failed build puts production on `next dev`). Budgets: /today 160 kB, /chat 260, /settings 183, /screen 145, /hub 104; /today has had almost no headroom. Test: `__tests__/bundleBudget.test.ts`.
- **Open tabs reload themselves onto a new build**: the served build id is `GET /build-id` (Next, outside `/api`), equal to `.next/BUILD_ID` and `NEXT_PUBLIC_BUILD_ID`; a route serving it reads it per request. Details and the reload holds: [app-shell-today-chat.md](app-shell-today-chat.md#new-builds-reach-open-tabs). A tab opened before this shipped needs one manual reload; after that tabs and kiosks update themselves.
- Kickstarting the frontend without a staged build can still take a couple of minutes (`restart.sh` and the health check wait up to 4 min).

## Running the app

**The backend must run natively on macOS** — AppleScript, the MCP integrations, the macOS databases Edward reads and the scheduler all need it.

### First-time setup
```bash
./setup.sh                  # Homebrew packages, Postgres 16 + pgvector, the venv, npm, .env
./setup.sh --with-test-db   # also the test cluster on :5433
```

### Start / restart
Start at login, kept alive by launchd (once; it takes over from a copy `./restart.sh` started):
```bash
bash scripts/install-launchagents.sh
```
Or by hand, and to restart either way (a kickstart when this checkout's agents are loaded):
```bash
./restart.sh                           # both
./restart.sh frontend                  # only the frontend (port 3000)
./restart.sh backend                   # only the backend (port 8000)
```

### Manual dev mode
```bash
cd frontend && npm run dev         # Port 3000 — never in the checkout that next start serves
cd backend && ./start.sh           # Port 8000 (activates the venv, installs deps)
```
For UX work use the fixture harness from a worktree ([testing.md](testing.md#ux-fixture-harness)).

### Pinned dependencies
`requirements.txt` is unpinned, and a rebuild with langgraph-checkpoint-postgres 3.0.5 + psycopg 3.3.6 cannot read older-format checkpoints (`operator does not exist: text = bytea`). `bash scripts/pin_requirements.sh` writes `backend/constraints.txt` from the venv's `pip freeze`; `start.sh` and setup install with `-c constraints.txt` and reinstall when it changes. **`psycopg-binary` is pinned at `psycopg`'s version** (2026-10-12, in `requirements.txt` and the constraints): psycopg 3 (the LangGraph checkpointer) needs libpq, postgresql@16 is keg-only, so pure-python psycopg found none on a fresh Mac and the backend died at import; the binary wheel bundles its own. `pin_requirements.sh` refuses to write a constraints file without it or with a version that differs from psycopg's (`psycopg_pair_problem`), so a regeneration from an older venv cannot drop it. Tests: `scripts/test_pin_requirements.sh`, `tests/test_public_install_path.py`. The test venv needs `httpx<0.28` (0.28 removed `TestClient(app=)`, which fastapi 0.109 uses); `pytest` and `pytest-asyncio` are in `requirements.txt`.

### Other commands
```bash
cd frontend && npm run lint        # Lint frontend
cd frontend && npm test            # node --test over the frontend tests
bash frontend/deploy-build.sh      # the production build, staged (never npm run build in the live checkout)
```

## Health watchdog

`scripts/health_check.sh` — a dependency-ordered health check with self-repair, scheduled by the two healthcheck agents. Tests: `bash scripts/test_health_check.sh`. `HEALTH_CHECK_LIB_ONLY=1 . scripts/health_check.sh` loads the functions without running the checks; `--dry-run` reports without repairing. Exit 0 healthy / 1 repaired / 2 needs a human; state in `~/.edward-health/` (`health.log`, `status.json`; `EDWARD_HEALTH_STATE`).

**Settings** (the environment, then `.env`): `EDWARD_LAUNCHD_PREFIX` (the labels it restarts), `EDWARD_TUNNEL_LABEL` and `EDWARD_PUBLIC_BASE_URL` (a tunnel, if any), `EDWARD_BACKUP_DIR`, `DATABASE_URL` (the credentials for its queries), `EDWARD_PG_BIN` / `EDWARD_PGDATA` / `EDWARD_PG_LOG` (default Homebrew's postgresql@16 binaries, data directory and log; `EDWARD_PG_BIN` also heads the PATH of `start.sh`, the graph worker and the agents), and the optional deep checks `EDWARD_HEALTH_HUB_KIOSK` / `EDWARD_HEALTH_EMAIL`. When something needs attention it posts a macOS notification and, when `EDWARD_HEALTH_NOTIFY_CMD` names a command, runs it with (title, body) — a hook for a text, a mail or a pager.

- **Checks bottom-up on purpose.** On 2026-08-12 Postgres died in a reboot and left a stale `postmaster.pid` naming a PID that npm inherited minutes later, so Postgres refused to start for nine days while launchd respawned a backend that died on connect every time. `is_stale_postmaster_lock()` detects exactly this (lock PID dead, or alive but not a postgres process) and clears it. Restarting the app can never fix a dead dependency, so the script never tries: with Postgres down it skips the app checks.
- **Shallow** (every 5 min): Postgres (and a query) → backend → frontend → the tunnel (only when `EDWARD_TUNNEL_LABEL` is set: its launchd PID, then the public URL unless that is localhost) → the graph worker (only when its agent is loaded and `GRAPHITI_ENABLED` is on). Repairs via `launchctl kickstart -k`. Then, when the backend answers, **scheduler liveness**: the scheduler stamps `~/.edward-health/scheduler.alive` (`EDWARD_SCHEDULER_ALIVE_PATH`) after every poll and 10 minutes of silence is a problem (reported, not restarted; skipped just after a backend restart). The old check read the log's mtime, which the `/screen` pollers keep fresh while a wedged scheduler fires nothing (2026-09-24).
- **A dry pool or a 5xx burst** (2026-09-27): the shallow check also reads the last 10 minutes of the backend log (`log_window` carries a stamped line's time onto the bare uvicorn access lines below it) and reports any `QueuePool limit` line, or five or more server errors — 5xx access lines plus `Exception in ASGI application`, which uvicorn answers 500 without an access line (`backend_error_verdict`). Reported, never repaired: restarting the app onto a stalled Postgres changes nothing. On 2026-09-26 the backend logged 20 QueuePool tracebacks in ten minutes while the watchdog saw a healthy backend.
- **Deep** (daily 08:00): adds disk free (10 GB floor), backup freshness, Postgres and app log rotation, checkpoint bloat (the three LangGraph tables past 2 GB means the nightly GC stopped), the memory pipeline, proactivity, and the log-silence check as a second scheduler signal. Backup freshness reads the stamp the backup writes (`~/.edward-health/backup.ok`, see Backups) through `backup_verdict`: a backup directory under `/Volumes` that is not mounted → "plug the backup drive back in" first; a readable stamp decides (older than 26 h → "backup stale") and the directory is never listed; only without a stamp does it list `edward-db-*.dump` (48 h). **Why**: the deep check runs as bash under launchd, which has no permission to list a removable volume, so it reported "no database backups" every morning (2026-09-25) while the backups were fine.
- **Proactivity** (2026-10-11, deep): `check_proactivity` reads the last 6 h of the backend log (`proactivity_verdict`). No `[sweep] ok` line for 30 min in a log that covers 30 min is a problem — the `*/5` `proactive_sweep` runs the late-dose check ([hub.md](hub.md)), so a dead sweep means no alert for a late dose. Half or more of at least four `[notice] pass` lines `FAILED` is a problem too; `deferred` (the spend cap) is only counted. Reported, never repaired.
- **The memory pipeline says when its problems predate the restart** (2026-09-27): the 24 h window is split at the last `Started server process`; when every failing measure has had no failure since the restart the line says so ("all before the backend restart at …; since then 0/11, 0/11"), and it stops being a problem after five clean samples since.
- **Mail** (deep, opt-in with `EDWARD_HEALTH_EMAIL`, only when the backend answered): `check_email` curls `GET /api/health/email` and reads it with `email_verdict` — `warn` is a problem carrying every warning; an empty or unparseable answer, or `unknown`, is "not judging". The route is public because the watchdog has no cookie, so it answers only `{"verdict", "summary"}` (the warnings, written without an address or a subject) and keeps it 60 s, hits arriving together sharing one check (`mail_service.cached_public_summary`: anyone who can reach the backend can call it, and a check runs pgrep, opens Mail's index and asks Postgres). The backend does the judging, since the script has no Full Disk Access and never touches Mail's files. Reported, never repaired: nothing restarts Mail.app (make it a Login Item if you rely on it). If a public route is unwanted, the alternative is a stamp file the backend writes (the `scheduler.alive` pattern) read by the same `email_verdict`.
- **The hub kiosk** (deep, opt-in with `EDWARD_HEALTH_HUB_KIOSK`, for a dedicated household kiosk that polls `/api/hub/*` all day): a problem after 6 h with no request the kiosk alone makes (`HUB_KIOSK_REQUEST`: `board`, `canvas`, `who`, `lists`, `settings`, the screensaver's `photos?seed=`). It does not judge when the log covers less than 6 h (after a restart or rotation). A phone's own `/api/hub/*` calls (the Edward tab reads `/api/hub/health`, Today's "Log given" posts `/api/hub/care`) do not count: the first version counted them and said "last polled 0h ago" while the kiosk had been dark for over a day. A /hub page left open in a browser elsewhere still hides a dark kiosk — a silence detector, not a roll call.
- **Restart cooldown**: at most 3 restarts per component per hour, then it escalates instead of feeding a crash loop.

## The memory report

Daily 09:05, `<prefix>.memory-report`: `backend/scripts/memory_health_report.py --push` measures the memory store's 30-day targets (new memories a day < 15, entity-extraction ok-rate ≥ 80 %, consolidation cycles that exhausted their budget = 0, checkpoint tables < 500 MB, disk ≥ 10 GB free, open contradictions) and **records them**: one `ledger_events` row, kind `memory_report` (`source="script"`, `outcome="ok"`, the verdict — "on track" / "needs a look" — as its `reason`, the summary counts in `detail_json`). `GET /api/health/report` → `memory_report` shows the newest row (its time, verdict, counts and how many ran in the window). Without `--push` it only prints. Tests: `tests/test_memory_report_no_push.py`, `tests/test_memory_health_report.py`.

**It no longer pushes** (2026-10-11, the proactivity rebuild). From 2026-09-05 the figures became a due-now scheduled event that Edward wrote up in the day's own thread (`memory-report-YYYY-MM-DD`; before 2026-09-27 it fired in `edward-mind` and dragged the mind thread's history along) and pushed the owner the link — a push a day about the memory store's plumbing, which went unopened. Every reach to the owner now goes through `reach_service`, for what matters to them; whoever runs a health check reads the row. The `--push` flag keeps its name because the LaunchAgent passes it.

**Mail in the report** (2026-10-11): `GET /api/health/report` → `email` is `mail_service.email_block()` — `icloud` (`mail_app_running` from `pgrep -x Mail`, `index_readable`, `newest_received_at` and `index_age_hours` from `MAX(messages.date_received)` in Mail's Envelope Index, opened `mode=ro`; the listener's `listener_state()`), `gmail` (`connected`, `account`, the listener), a `verdict` (`ok` / `warn`), `warnings` and `info`. Warnings: Mail.app not running (iCloud mail stops arriving — on the reference install it was down for four weeks unnoticed); the newest mail in the index more than 24 h old; the index unreadable; an enabled mail listener stopped, failing, or without a clean poll for 30 min (or three of its polls; one started less than that ago is not judged); Gmail's token refresh failing ("sign-in has lapsed"). Gmail not connected, or a listener switched off, is `info`. It never sinks the report (`health_report_service.email_section` → `verdict: "unknown"`). Tests: `tests/test_mail_health.py`.

**Proactivity in the report** (2026-10-11): `GET /api/health/report` → `proactivity` is `noticing_service.proactivity_report(days)` — the mode, the trust line (pings answered vs noticed / spoken / pushed / ignored), the per-day counts, the stalls and a verdict (`off` / `ok` / `stalled` / `failing`). When it fails the section reads `verdict: "unknown"` with the reason and never sinks the report (`health_report_service.proactivity_section`). The surplus queue's `surplus` section went with the queue ([surplus.md](surplus.md)). Test: `tests/test_health_report_proactivity.py`.

## Backups

`backend/scripts/backup_memories.sh` — a nightly `pg_dump` (compressed custom format, verified readable with `pg_restore -l`) plus a best-effort copy of the kuzu graph, via `<prefix>.backup` at 03:30; then `gc_checkpoints.py` prunes superseded LangGraph checkpoints. Run it by hand with `bash backend/scripts/backup_memories.sh`; `backend/scripts/BACKUP.md` is the short guide.

- **Where**: `EDWARD_BACKUP_DIR` (the environment, then `.env`), default `~/edward-backups` — outside the repo; dumps hold everything Edward knows about you and are never committed. 14 dumps plus 3 kuzu copies can reach tens of GB on a long-lived install, so point it at a bigger or removable disk when the internal one cannot spare it. There is no offsite copy unless you make one.
- **Retention**: `EDWARD_BACKUP_KEEP` dumps (14) and `EDWARD_BACKUP_KEEP_KUZU` kuzu copies (3). A kuzu copy is ~5 GB against a few hundred MB of dump and is rebuildable from Postgres; 14 of them filled the disk and took Postgres down on 2026-08-12.
- **Who**: the role is `EDWARD_BACKUP_USER`, else `$PGUSER`, else your macOS user — Homebrew's Postgres superuser, which can also reach the `edward_db_*` persistent-database schemas (owned by that role, not `edward`).
- **Owner-only** (2026-10-12): a dump is the whole database (memories, conversations, widget tokens, push subscriptions, OAuth tokens), and under the default umask it came out 0644 in a 0755 folder any local account could read. The script sets `umask 077` before it writes anything, `chmod 700` on the folder and `600` on `backup.log`, every new dump and kuzu copy, and tightens older ones on the next run. The health stamp is owner-only too. A filesystem without Unix permissions (an exFAT drive) may refuse the chmod: that is a warning, never a reason to skip the backup. Test: `tests/test_public_backup_permissions.py`.

Two guards exist because of two separate incidents, both about backups to a removable drive (a path under `/Volumes`; neither applies to a directory on the internal disk):
- **Not mounted**: the script refuses to run while a `/Volumes/*` backup directory is not a real mount. Without this, `mkdir -p` silently recreates the path on the *internal* disk and fills it with backups that vanish when the real drive is remounted over them. `scripts/health_check.sh` has the matching `backup_volume_missing()` so the message says "plug the drive back in" rather than "no backups found".
- **Mounted but not writable**: macOS gates removable volumes **per process**. A LaunchAgent has no TCC grant even when an interactive shell does, so testing by hand proves nothing about the scheduled job — this is how it broke on 2026-08-23: `/bin/bash` had never been granted Full Disk Access (the grants had gone to the terminal apps, which is why manual runs passed while every 03:30 run failed). Since 2026-09-05 the agent runs `backend/scripts/run_backup_with_fda.py` under the python3.12 that holds Full Disk Access (the same grant the iMessage listener needs for `chat.db`); children inherit the responsible process's TCC identity, so the shell script works unchanged. The grant is path-based (see the FDA python, above). Check `launchctl print gui/$UID/<prefix>.backup | grep "last exit"` and `/tmp/edward-backup.log` first.

**The success stamp** (2026-09-25): after a dump verifies, the script writes `~/.edward-health/backup.ok` (`EDWARD_BACKUP_STAMP`, or `$EDWARD_HEALTH_STATE/backup.ok`; `key=value` lines `verified_at`, `verified_at_iso`, `dump`, `size_bytes`, written to a temp file and renamed). Only a verified dump refreshes it; a stamp that cannot be written is logged and never fails the backup. The deep health check reads it (Health watchdog). **Tests never touch the live system**: `tests/test_backup_script.py` stubs `pg_dump`/`pg_restore`, points the stamp at a scratch dir (`EDWARD_HEALTH_STATE`) and sets `EDWARD_GC_PYTHON` to a path that does not exist — the script's checkpoint GC otherwise defaults to the live venv's python running `gc_checkpoints.py --apply --vacuum` against the live database, which an early version of the fixture let happen. `test_the_health_check_reads_the_stamp_the_backup_writes` pins that the two scripts agree; `scripts/test_health_check.sh` covers `backup_verdict`.

## Restores

`backend/scripts/restore_memories.sh` restores into a **new verification database** (`edward_restore_test`) and prints a row-count comparison by default; only `--force-live` replaces the live database, and it snapshots the current state first (and asks for a typed confirmation).

```bash
bash backend/scripts/restore_memories.sh                    # newest dump -> verify DB
bash backend/scripts/restore_memories.sh <dump-file>        # a specific dump -> verify DB
PGHOST=localhost PGPORT=5433 bash backend/scripts/restore_memories.sh <dump>   # a restore test on the test cluster
bash backend/scripts/restore_memories.sh <dump> --force-live   # REPLACE live (asks first)
```

- It reads where the backup writes (2026-09-27): `EDWARD_BACKUP_DIR`, else `~/edward-backups` — it once looked in a directory the backup had stopped writing a month before. A test pins the two scripts to the same default.
- It refuses an unmounted `/Volumes` path (the `--force-live` snapshot would otherwise land on the internal disk) and says "No dump found in <dir>" instead of exiting silently.
- Every command is plain libpq, so `PGHOST`/`PGPORT` pick the cluster; without them the verify path restores onto the main cluster (:5432). The role is the backup's (`EDWARD_BACKUP_USER`, else `$PGUSER`, else your macOS user — the superuser of both Homebrew clusters).
- Stop the backend and the graph worker before `--force-live`.
- Tests: `tests/test_restore_script.py`.

`run_memory_decay.py --revert-stamp <stamp>` undoes exactly one decay pass; see [memory.md](memory.md).

## Maintenance scripts

All in `backend/scripts/`; each is a dry run unless told otherwise.
- **Cobwebs**: `backend/scripts/prune_cobwebs.py [--dry-run]` removes month-old unengaged cron/thought conversations (with their LangGraph checkpoints, which the delete endpoint leaves behind), finished `scheduled_events` rows, dead tasks, and marks stale self-observations superseded. Never touches the owner's or inbound conversations, heartbeat threads, memories or documents.
- `backend/scripts/gc_checkpoints.py` runs after the nightly backup; `backend/scripts/prune_checkpoint_history.py --dry-run | --apply` keeps each thread's latest checkpoint and VACUUMs ([tool-loop.md](tool-loop.md#checkpoint-history)); `backend/scripts/prune_dead_turns.py <conversation_id> [--apply]` removes the scaffolding of a failed attempt from one thread.
- `backend/scripts/run_memory_decay.py` is a dry run unless `--apply` ([memory.md](memory.md)); `backend/scripts/prune_memory_connections.py` restamps memory-connection strengths and trims the surplus edges.
