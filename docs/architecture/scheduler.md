# Scheduled events and the scheduler

The in-process scheduler that fires reminders, messages, the nightly, wakes, the sweep and the pulse: event rows, cron in the owner's zone, what never blocks the poll, which thread an event runs in, whose event it is, and its extraction profile.

## Scheduled events

(`backend/services/scheduled_events_service.py`, `backend/services/scheduler_service.py`)
- Edward can schedule future actions for himself: reminders, messages, tasks, and wakes.
- Events are rows in the PostgreSQL `scheduled_events` table; an in-process asyncio loop polls every 30 s for due ones.
- An ordinary event runs as a `chat_with_memory()` turn with the full toolset, under the turn policy below.
- One-time and recurring events (cron patterns via `croniter`).
- Atomic pickup: `SELECT ... FOR UPDATE` prevents double-firing; a failed recurring event still advances to its next fire time.
- **The scheduler never blocks on work** (2026-09-24): each due event runs as its own tracked task (`EVENT_TIMEOUT_SECONDS` 600; the pulse and wakes keep their own bounds with a backstop above them), an in-flight event is never dispatched twice, stale-processing recovery runs only while nothing is in flight, a routed event (pulse, `wake_me`, ticks — `event_route`) that raises is failed and never re-run as an ordinary turn, and a failed boot retries with backoff (10 s → 300 s). `get_due_events` stamps `updated_at` in UTC from Python (the server's `now()` writes the session zone into a naive-UTC column). `start_scheduler` warns once when `settings.timezone` differs from the host zone; `GET /api/health/report` → `config {timezone, host_timezone, mismatch}`. Test: `tests/test_scheduler_never_blocks.py`.
- **Cron results and tool times are the owner's zone, never the host's** (2026-09-21): `timezone_utils.local_naive_to_utc` reads a naive datetime in `get_user_tz()`; `_next_cron_utc`, `wake_me` and `schedule` go through it. A naive `dt.astimezone()` means the *process* zone — with `settings.timezone` set to Pacific on a host running in Central time, every cron advance landed two hours early and each recurring row was due again the moment it finished: the `*/15` pulse fired over ten thousand times in a week (about once a minute), the twice-daily mind ticks ran in two-hour storms, and most `wake_me` calls were refused as "in the past". Test: `tests/test_timezone_safe_scheduling.py`. The Locale panel auto-detects the browser zone once while the setting is still the default — check `settings.timezone` before trusting a tick time.
- **Routed events** (`scheduler_service.event_route`, by `event_metadata.type`): the surfaces pulse (`expression_pulse`, cron `*/15`, `PULSE_CRON`; change-only since 2026-10-11 — [screen-and-browser.md](screen-and-browser.md)), the nightly (`wakeup_tick` `nightly`, `0 3 * * *` — `WAKEUP_TICKS`), the day's free time (`wakeup_tick` `free`, `0 13 * * *`, `FREE_CRON`), `wake_me` rows (`mind_wake` → `wake("self")`), the `proactive_sweep` (`*/5`, `SWEEP_CRON`) and the widget refresh (a leftover row runs a pulse). They are Edward's plumbing and never appear on Today (`today_service.PLUMBING_EVENT_TYPES`, pinned against `event_route`) or on the widget's fallback card. Everything else is an ordinary event: a full `chat_with_memory` turn.
- **Proactivity is noticing, not a schedule** (design decision, 2026-10-11; [mind.md](mind.md)). The seeds:
  - **two ticks: the silent 03:00 `nightly`, and the 13:00 `free` run** (the owner's zone, as every cron; free time is one budgeted run a day for Edward's stage and his own projects, no push, no send). The `free` tick route wakes `free` and nothing after it. The tick route wakes `nightly`, then `expression_service.pulse_in_background("nightly", extra=NIGHTLY_PULSE_EXTRA)` sets the morning scene. The wake's turn may run 900 s on a Sunday (decay and the week's reflection), and `event_timeout_for` sizes the backstop for it (`NIGHTLY_MAX_TIMEOUT_SECONDS`);
  - **retired**: the 07:00 `morning`, 18:00 `evening` and Sunday 09:00 `reflect` ticks are in `RETIRED_WAKEUP_KINDS` beside the pre-mind kinds, and the surplus queue's `surplus_tick` is in `RETIRED_CRON_EVENTS` beside `widget_refresh` ([surplus.md](surplus.md)). The boot cancels their live rows idempotently (`Scheduler: retired N pre-mind wake-up tick(s)`, `Scheduler: retired N old cron event(s) (widget_refresh, surplus_tick)`), and a retired row that fires before the boot reached it is cancelled, never run (`event_route` → `retired`, or a retired tick kind — `is_retired_wakeup_seed`). Old kinds keep their reason in `wake_reason_for_tick` so history renders;
  - **`proactive_sweep`** (`*/5`, `SWEEP_TIMEOUT_SECONDS` 120): code only, no model. `_run_proactive_sweep` runs `care_watch.check()` (the late-dose alert — [hub.md](hub.md)) and `noticing_service.sweep()`; one part failing never stops the other, and every pass prints `[sweep] ok care=… due=… outcomes=…` (the watchdog's liveness line; `scheduler_service.last_sweep()` keeps the last pass in process);
  - **the same rows in every mode**: `EDWARD_PROACTIVITY` (`off` | `shadow` | `notice`) is read at call time and never changes the seeds, so flipping it needs no reseed.

  Tests: `tests/test_proactivity_modes.py`, `tests/test_ticks_wake_the_mind.py`, `tests/test_care_watch.py`, `tests/test_rollback_guard.py`.
- **Rolling back the rebuild** (2026-10-11). The scheduler before the proactivity rebuild ran an unknown event type as an ordinary LLM turn and an unknown tick kind as a full-tool `manual` wake. An older Edward started against this database with the rebuild's seeds pending would therefore run the `*/5` `proactive_sweep` as ~288 event turns a day (its description as the prompt, every tool, push included) and the `nightly`/`free` ticks as full-tool wakes — burning the daily spend cap within hours, which then stops every wake and reminder. This release's boot cancels anything retired, but an older checkout knows nothing of these seeds. If you ever run older code against this database, cancel them first — with the old process stopped or right after its boot, in `psql`:

  ```sql
  UPDATE scheduled_events SET status = 'cancelled'
   WHERE status IN ('pending', 'processing')
     AND (event_metadata LIKE '%"type": "proactive_sweep"%'
          OR (event_metadata LIKE '%"type": "wakeup_tick"%'
              AND (event_metadata LIKE '%"kind": "nightly"%' OR event_metadata LIKE '%"kind": "free"%')));
  ```

  Only the rebuild's seeds change (the pulse, a `wake_me`, the owner's reminders and rows with no or broken metadata stay — `tests/test_rollback_guard.py` runs this exact statement); the old boot then re-seeds its own ticks. A recurring row the old process was executing when you cancelled is re-armed `pending` when it completes, so cancel again after its boot. Data is untouched. Turn the flags down before anything else: `EDWARD_PROACTIVITY=off`, `EDWARD_CARE_WATCH=off`, `EDWARD_PUSH_BUDGET=<n>`.
- **A self wake carries its event** (2026-10-11): the `mind_wake` route passes `event_meta` (the row's metadata, with `ping` when a promise was made in a ping) to `wake("self")` (`_accepts` feature-detects the keyword), so a promise is followed through in the chat it was made in ([mind.md](mind.md)). An ordinary event's turn gets `TurnPolicy(source="scheduled_event", owner_asked=…, may_reach_people=…, may_push=…)` (`event_policy`, `event_policy_kwargs`). **Whose it is** is `scheduled_events_service.event_is_owners` (below) — the rule the spend cap uses too (review 2026-10-11: reading only the toolset's `requested_by_owner` stamp fired every reminder the owner made as Edward's own turn — linted, held overnight as a note, refused as a repeat, their own iMessage reminder refused by never-text-the-owner). The owner's event may reach people and push. **Edward's never gets more reach than the turn that made it**: `create_event` stamps `event_metadata.reach = {may_reach_people, may_push}` from a policy its caller set when the owner was not asking (`reach_stamp`), and `event_reach` applies it — so a task the 03:00 nightly scheduled for 07:01 cannot push, and a speak wake held to a note cannot get a push one hop later. An unstamped event keeps both. Test: `tests/test_event_policy.py`.
- **Which thread an event runs in** (`event_thread`): the thread that made it, when that thread still exists and is the owner's or Edward's own (sources `user`, `edward_thought`, `scheduled_event`; a heartbeat thread is never replayed into), else `edward-mind`. `build_event_trigger` carries `fire_count`, `last_fired_at`, `last_result` and the intention behind the event. A `why` given when scheduling is remembered as a linked `intention` memory; cancelling the event retires it. An event should carry its own conversation when it is not a continuation — the daily memory report fired in `edward-mind` until 2026-09-27 because its event had none ([ops-health-backups.md](ops-health-backups.md)).
- **An ordinary event takes its thread before its bound starts** (2026-09-27): `_run_event` finds the unrouted event's thread and takes it (`thread_turns`, [tool-loop.md](tool-loop.md#one-turn-at-a-time-in-a-thread-servicesthread_turnspy-2026-09-27)) before `wait_for`, so the 600 s covers only the event's own turn; `_execute_event` holds the thread once for both attempts and the error note; if the thread cannot be read the event is still marked failed. Two events in one thread take turns.
- **Event turns extract under the `scheduled_event` profile** (2026-09-27, `SCHEDULED_EVENT_EXTRACTION_PROFILE`): both attempts pass it, and `skip_extraction` (`extraction_kwargs_for_event`) still reaches the turn. A reminder's trigger is text Edward wrote to himself; under the chat profile it was stored as the owner's standing instruction — that is how two blanket "in-app only, never contact anyone" rules appeared that the owner never gave ([memory.md](memory.md#extraction-profiles-and-who-said-it)). Test: `tests/test_scheduler_extraction_profile.py`.
- A fired event's model calls are labelled `turn:scheduled_event`; an unattended event turn that starts Codex or installs an MCP server leaves an `acted` journal entry ([mind.md](mind.md)).
- **Whose event it is** (2026-10-11, for the Claude spend cap): `create_event` stamps `event_metadata.created_in` with the source of the turn that made it (`turn_ledger.current_turn()`; a caller's own value is kept). `event_is_owners(event)`: yes for `created_by` `user` (the REST routes) or `owner`; then the toolset's `requested_by_owner` stamp when there is one; then yes for `created_in` one of the owner's own turns (chat, voice, widget, Alexa, their pings — `OWNER_TURN_SOURCES`), no for any other `created_in` (a wake, the pulse, another event, a heartbeat reply); an unstamped event is the owner's unless its thread is one of Edward's own (`mind_service.EDWARD_OWN_THREAD_IDS`). `_execute_event` runs any other ordinary event inside `llm_spend.own_work_scope()`, so the mind's follow-ups stop at the daily cap and never spend the reserve the owner keeps past it ([llm-and-quota.md](llm-and-quota.md#pay-per-token-the-claude-spend-ledger-and-the-daily-cap)).
- `scheduled_events` API items carry `event_type` (null for the owner's plain reminders) and parsed `event_metadata`.
- Tools: the toolset's `schedule` (add a task, a reminder or a wake; list; cancel — [tool-loop.md](tool-loop.md#the-other-tools)); the legacy `schedule_event`, `list_scheduled_events`, `cancel_scheduled_event` and `wake_me(when, why, memory_id?)` under `EDWARD_TOOLSET=legacy`. A turn whose policy may not reach anyone cannot leave a task or reminder behind (`TurnPolicy.may_schedule` / `may_wake_later`).
- REST API: `GET/POST /api/events`, `GET/PATCH/DELETE /api/events/{id}`.
