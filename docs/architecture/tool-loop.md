# The turn: LangGraph, the toolset, the tool loop, the stream

How one LLM turn runs: the LangGraph graph, the toolset (14 tools, the same on every surface) and its `TurnPolicy`, the one tool loop both paths share (`stream_with_memory_events` for chat and voice, `chat_with_memory` for wakes, pings, events, heartbeat and workers), the window, deadlines, the failure contract, the per-turn dollar cap, the reply check, the Claude and Codex streams, the per-turn trace, and — since 2026-09-27 — one turn at a time per thread, a Stop that really stops, and a save that survives the owner leaving. Model routing lives in [llm-and-quota.md](llm-and-quota.md); the SSE events in [api.md](api.md#the-chat-stream-sse). The toolset replaced a per-surface tool registry on 2026-10-11.

## LangGraph flow

```
preprocess → retrieve_memory → respond → extract_memory → END
                  ↓                ↓              ↓
            [pgvector search]  [tool loop]  [LLM extraction]

Tool loop (graph/tool_loop.py, both paths):
  model call ──tool calls?──yes──> run them in order ──> ToolMessages (status ok/error) ──┐
       │                                                                                  │
       no ──> the reply check (once) ──> answer                    stop checks: rounds (60),
       ↑                                                           deadline, dollar cap, 6 failed
       └──────────────────────────────────────────────────────────────rounds ──> one closing call
```

Conversation state is persisted to PostgreSQL through langgraph-checkpoint-postgres (`checkpoints`, `checkpoint_blobs`, `checkpoint_writes`). Memories are retrieved before responding and extracted after; reflection and search tags run post-turn ([memory.md](memory.md)).

## The graph package (`backend/services/graph/`)

- `state.py` — AgentState with messages, memories, node tracking
- `nodes.py` — preprocess, retrieve_memory, respond, extract_memory nodes
- `graph.py` — graph construction and structure export (`GET /api/debug/graph`)
- `streaming.py` — context collection, `compose_system_prompt`, the SSE events (`EventType`, `create_event`), the two entry points and what they do around the loop (memory, the checkpoint save and trim, post-turn work)
- `tool_loop.py` — the loop both paths run (`run_tool_loop`) and the executor (`execute_call`; `execute_tool_call` / `execute_tool_call_with_events` are re-exported from `streaming.py`)
- `turn_window.py`, `tool_policy.py`, `tool_deadlines.py`, `history_window.py` — the pure decisions below
- `turn_trace.py` — the compact per-turn trace (reasoning, tools, memory hits) kept on the answer so a reloaded chat still shows the work
- `tools.py` — the older tool bodies the toolset wraps (memory, documents, messaging, scheduled events, screen, widget, browser, plan state) and, for `EDWARD_TOOLSET=legacy`, the old tools themselves

`services/thread_turns.py` (one turn per thread) sits beside it.

## The toolset (`backend/services/toolset/`, 2026-10-11)

**Why**: the agent the owner talks to had the weakest hands — a ping ran as a mind wake with a short wake tool list, no shell, no browser, no image (three of the first 21 pings failed for that alone); 58 of the 116 chat tools were never called in 30 days and cost 9.3K schema tokens a call; the per-surface lists defeated the shared prompt cache. Now:

- **14 tools in one order on every surface** (`names.TOOL_ORDER`): `bash`, `str_replace_based_edit_tool`, `web_search`, `web_fetch`, `browser`, `chrome`, `look`, `messages`, `send_message`, `tell_owner`, `memory`, `schedule`, `screen`, `plan`. `build_toolset(skill_states)` drops only what a skill toggle turns off (`shell_interpreter` → bash and the editor, `brave_search` → the web tools, `imessage_applescript` → `messages` and `send_message`); `ios_widget` and `push_notifications` are refused inside `screen` and `tell_owner`. The computer tools come from the toolset's computer_tools module; the web tools, the two browsers and `look` from its web, browsers and look modules — stand-ins otherwise (`services/toolset/fallbacks.py`). Custom MCP tools the owner installs are appended, each tagged `custom_mcp` and treated as outward on every rail ([integrations.md](integrations.md#custom-mcp-servers)).
- **The registry** (`services/tool_registry.py`): `get_available_tools()` ignores the message (no keyword gating — a keyword gate once left a turn without the tool it needed), `get_worker_tools()` is the same toolset, `get_tool_descriptions()` is the static `TOOL_MANUAL` (`toolset/manual.py`, ~1K tokens: make a plan, act, look at the real result, fix or re-plan; take another route when stuck; never give up silently; the rails). Tools plus manual are ≤ 22,000 characters (`tests/test_toolset_budget.py`). Skill state is cached 30 s; toggles call `refresh_registry()`.
- **Every tool fails the same way** (`toolset/result.py`): it raises `ToolFailure` (or returns `ToolResult(is_error=True)`); the executor turns that, any other exception (with its type and message) and an error-shaped string into `Tool error: …` with `ToolMessage.status="error"` — the Claude adapter sends `is_error`, the turn ledger counts it. Until then only `Tool error:`-prefixed results counted, against ~115 other failure shapes.
- **Action tools** (`browser`, `chrome`, `messages`, `memory`, `schedule`, `screen`) take `action` plus flat optional arguments; their work-rail chip is `"{action}: {detail}"` (`streaming._summarize_toolset_args`). Each tool's `metadata` carries `timeout_s`, `action_arg`, `parallel_safe` and, for native and server tools, `anthropic_tool`.
- **Retired names still work**: a call to `send_imessage`, `leave_note`, `send_push_notification`, `wake_me`, `schedule_event`, `stand_down`, `remember_search`, `compose_screen` … that an older prompt teaches is answered by the new tool with its arguments translated (`names.alias_call`).
- **`EDWARD_TOOLSET=legacy`** (read per call) restores the old registry — the families still in `graph/tools.py`, gated by skills, honouring `allowed_tools` / `excluded_tools` — minus the apple-mcp and WhatsApp MCP tools (their sends bypassed the send guard) and minus keyword gating. The loop stays new. No legacy tool reads the turn's policy, so a household hub turn (`hub_voice`) there goes without every send and the tools a friend's legacy ping goes without — the legacy `execute_shell` is bash as the backend's user, unsandboxed (`graph/tools.hub_legacy_refusal`, in the executor's boundary step); it reaches the owner through `leave_note` / `send_push_notification`, which go through `reach_service` (origin `hub`).

## `TurnPolicy` — what a turn may do (`toolset/policy.py`)

The executor and the tools enforce limits from the turn's policy instead of a shorter tool list; a refusal is an honest `Tool error`, never a missing tool.

- **Fields**: `source`; `owner_asked` (the owner is the one asking in this turn); `may_reach_people` (`send_message` at all, and any custom MCP tool — it may reach people through its own service, so a turn that reaches nobody gets an honest `Tool error:` from `policy.scope_refusal`; so does `hub_voice` — for someone who isn't the owner, a custom tool is the owner's call); `may_push` (`tell_owner(urgent=True)`); `reply_to` (the chats this turn was asked in); `max_turn_usd`; `deadline_s`; `third_party` (a friend's ping — it narrows nothing here: what a friend's ping may not do is `pings/scope.py`'s, asked at the tool boundary for every call — by default the owner's machine (the shell and the editor, the owner's Chrome, the screens, `look` at the owner's display, Chrome or files), plus a custom MCP tool and any send to someone who asked Edward nothing; `EDWARD_FRIENDS_FULL_TOOLSET=on` gives friends the full toolset, the reference host's design decision of 2026-10-11, [pings.md](pings.md#the-reply-turn); the field lets the runner and the boundary know); `final_text_is_reply` (the caller posts the final text: default for `ping`/`ping_owner`); `dry_run_outward` (the judgement check: sends, `tell_owner`, Chrome typing, screen changes and every custom MCP call are recorded, never done — `tool_loop.dry_run_calls(conversation_id)` hands the records back); `may_schedule` / `may_wake_later` (`schedule(add)` of a task or reminder / of a self-wake: an event fires later as its own turn with a fired event's or a wake's reach, so a turn that may not reach anyone must not leave one behind); `max_output_tokens`; `any_reply` (a legacy `required_tools`). One method, not a field: `may_change_owners_calendar()` — `schedule`'s writes to the owner's calendar and Reminders happen when the owner asks (`owner_asked` today; one line to flip for Edward's own initiative; reads are open in every turn — [computer.md](computer.md)).
- **Defaults** (`default_policy`, used when a caller passes none): the owner's sources (`chat`, `voice`, `widget`, `alexa`, `ping_owner`) may do everything; the household hub's live voice (`hub_voice` — someone in the owner's home, not necessarily the owner) may reach people, push and schedule a task, but `owner_asked` is false (the recipient rule, never-text-the-owner, stand-downs and the Chrome typing rule hold) and it may not wake Edward later; a fired event is the owner's unless the scheduler runs it as Edward's own work (`llm_spend.in_own_work`, set from `scheduled_events_service.event_is_owners` — [scheduler.md](scheduler.md)); **everything else is fail-closed** — no reach, no push — so a wake that forgot its policy fails visibly, never silently sends. A caller still passing `allowed_tools` / `required_tools` gets them translated (`legacy_policy`: a send tool → may reach people, `send_push_notification` → may push, `schedule_event` → may schedule, `schedule_event` or `wake_me` → may wake later, a required send → the reply check).
- `chat_with_memory(…, policy=, deadline_s=)` and `stream_with_memory_events(…, policy=, deadline_s=)` take it; it is current (`current_policy()`) for the whole turn and around every tool call.
- **Chrome** (`policy.chrome_action_allowed`; Chrome hands are off unless `EDWARD_CHROME_HANDS=on` — [screen-and-browser.md](screen-and-browser.md)): payment steps (a word-bounded "place order / pay / checkout / add card …" label, or a Luhn card number) are refused in every turn; typing outside a search site or Edward's own `/screen` (`policy.own_screen_hosts`, from `host_config.own_hosts()` and `EDWARD_PUBLIC_BASE_URL`), and clicking a control that acts as the owner (Send, Post, Delete, Unsubscribe …), only when the owner asked in this turn. In `steps`, a click, a key or back may navigate, so typing or Enter after one is judged on an unknown page and, outside the owner's turn, refused until it runs as its own call (a review on 2026-10-11 found a forum passing as the search site the steps had opened).

## The one send (`toolset/messaging.py`)

`send_message(message, chat_id | to, files?, subject?)` is the only way to text or email anyone; `send_imessage`, `send_sms`, `send_whatsapp` and the MCP sends are gone from the toolset. **An email** (`toolset/mail.py`) is a call with a `subject`, or with `chat_id` = a mail id from `mail_search` (a reply in its thread); without either, `to` = an address is still iMessage to an Apple ID. Both share every guard below and differ only at the transport: an email's recipient is an address, or a name with one person and one address (a reply: its Reply-To or From, or whom the owner wrote to when it is their own); the owner's handles include their email addresses (`graph/tools._owner_all_handles`: `heartbeat_config.imessage_owner_handles`, `EDWARD_OWNER_HANDLES` and `mail_service.owner_addresses`, read by both this check and the executor's); the dedupe keys on `mail:<address>`; the transport is `gmail_service.send_gmail`, delivered only with Gmail's SENT label; no iMessage listening window; the egress scan covers `subject`.

In order:
1. exactly one of `chat_id` / `to`;
2. **never text the owner from a turn they are not part of** (keyed on the policy — by name before the lookup, `graph/tools.names_owner` with the configured names plus "me", "myself", "owner", "the owner"; by their own handles after it; a text into the chat this turn was asked in, or into their self-chat where their own ping is waiting, goes through — an email to them never does; they are reached with `tell_owner`);
3. `to` must resolve to exactly one person (several → the list with handles);
4. `may_reach_people`; stand-downs (lifted when the owner asked);
5. **the recipient rule** — the owner asked, the chat is in `reply_to`, the chat addressed Edward in 24 h (`policy.addressed_recently`: the pings table, else the heartbeat's own `@edward` and self-chat rows — only those rows are loaded, so a busy day in other chats can't push a mention out of the 500-row limit), or a live conversation (his last send there answered by someone other than the owner within 2 h, `policy.in_conversation`) — anyone else is the owner's call;
6. the 10-minute dedupe;
7. files (never Edward's own credentials, refused through the computer's `rails.can_read` ([computer.md](computer.md#the-rails)); in his own turns only from `~/edward-home`; a text file carrying a secret is refused; `imessage_service.send_attachment`);
8. the egress scan at the boundary;
9. then the transport, shielded (`graph/tools._send_and_note`), whose failure raises.

The send-review critic and the taint approval hold are not on this path.

## The other tools

`messages` (recent, thread, participants, who, stand_down, mail_search, mail_read — the owner's iCloud and Gmail mail, read in every turn without a gate, [integrations.md](integrations.md)), `tell_owner` (`reach_service.tell_owner`: a note on Today, or with `urgent` a push — [push-and-notes.md](push-and-notes.md)), `memory` (search, remember, update — `until="now"` retires —, close, why, forget — the owner's own conversation only —, doc_read, doc_write, doc_edit; nothing is hard-deleted from Edward's own turns, and the owner's rows change only in their turn, confidence included), `schedule` (add a task, a reminder or a wake — refused when the policy says `may_schedule` / `may_wake_later` is off; list; cancel; read the owner's calendar (`calendar`) and Reminders (`reminders`); change them when the owner asks — `event_add`, `event_update`, `event_delete`, `reminder_add`, `reminder_complete`, `reminder_delete`, behind `TurnPolicy.may_change_owners_calendar()` ([computer.md](computer.md))), `screen` (the stage, the house screen, the widget; the owner's hold is a `Tool error`), `plan` (the whole checklist each call; the diff becomes the existing plan events; not a gate). ## The tool loop (`graph/tool_loop.py`)

**One loop.** `run_tool_loop(LoopContext)` serves both paths: the streaming path forwards its events as SSE, the non-streaming path drains them; both get the same accounting, traces and endings.

- **Executing one call** (`execute_call`): an unknown tool or arguments the adapter marked `{"__invalid_json__": raw}` are answered, never run; **the identical-failure stop** — the same name and arguments that failed twice are refused (`tool_policy.FailureTracker`; success never counts); the boundary (`_boundary_check`: the never-text-the-owner check for old send names and the hub's legacy refusal, then the ping scope while a friend's ping is current (`pings.scope.refusal`: no send to someone who asked nothing, no task left behind), then `taint_service.check_tool_call` — the egress secret scan in every mode, and the taint gate only if `EDWARD_TAINT_APPROVALS` is `shadow`/`on`; it is off by default); then the turn's `policy.scope_refusal` (the policy in hand, else `current_policy()` — fail-closed: a custom MCP tool in a turn that may not reach people); the run, under the tool's `metadata.timeout_s` clamped to the turn's deadline minus a 45 s closing reserve (`tool_deadlines.clamp_to_turn`), with the turn's policy current; then the failure contract and **the redaction** (`redact_result`: `secret_scan.redact_secrets` over a text result and the text blocks of a block result, never an image or document block — so no local tool's output carries a key to the model, the rail, the trace or the checkpoint; a redaction that breaks withholds the result as a `Tool error:`), the taint and journal notes, the work-rail events (`code` / `execution_output` / `execution_result` for `bash`, search progress, plan events), `ToolMessage.status`, the turn ledger and the ping's `pings.hooks.note_tool`.
- **Rounds**: calls in one response run in the order given (the loop binds with parallel tool use on under Claude: fewer rounds); after **3** rounds in which every result failed the loop appends one step-back note, after **6** it stops. The ceiling is `EDWARD_MAX_TOOL_ROUNDS` (60) or the caller's `max_tool_iterations`; a plan no longer raises it.
- **The per-turn dollar cap**: the loop sums each response's `estimated_cost_usd` (the Claude adapter's); past `TurnPolicy.turn_cap_usd()` — `EDWARD_TURN_MAX_USD` (3.00) when the owner asked, `EDWARD_AUTONOMOUS_TURN_MAX_USD` (1.00) otherwise — it stops with a closing call ("say where you got to and what is left"; the owner's turns may offer to continue). The cap is soft: it is read before each round, so the round already running and the closing call land on top of it. A turn that must stay under a ceiling also sets `TurnPolicy.max_output_tokens`, which the loop applies to every call's `max_tokens` (the closing call and the cut-tool-call retry's base included; `tool_loop.cap_output_tokens` never raises a route's own) — the daily free run does ([mind.md](mind.md)). The daily cap is the adapter's (`llm_spend.LLMSpendCapReached` propagates).
- **Deadlines**: 300 s per model call (`LLMCallTimeout` → an honest ending, no closing call); a streaming turn stops calling tools when 45 s of its 600 s (`tool_deadlines.STREAM_TURN_MAX_SECONDS`, or a shorter `deadline_s`) remain; a non-streaming caller passes `deadline_s` (a wake's timeout minus 30 s) and the loop stops gracefully with a closing call instead of being cancelled mid-tool by its caller's `wait_for`. A cancelled or failed non-streaming turn still saves its trigger and finished calls plus `[interrupted after N tool calls]`.
- **Stops the model gives**: tools in a `refusal` response never run; a `max_tokens` cut that dropped a tool call (or left nothing) is asked once more with `max_tokens` doubled — even after a streamed preamble (a `progress` `generating`/`retrying` event first; the preamble used to become the finished answer and nothing ran), and a second cut tool call ends with the honest ending; `_stream_llm_with_events` carries `incomplete_reason`; `pause_turn` is the adapter's to resume.
- **The reply check** (replaces the required-tool nudge and forced `tool_choice`, which Opus and Sonnet 5.5 reject with a 400): when the policy has `reply_to` (or a legacy `required_tools` names a send) and the model ends without a successful send into that chat or a stand-down for it, the loop says so **once** — `[SYSTEM] You were asked in <chat> and haven't replied there …` — and never forces. A ping turn's final text is its reply (the ping runner posts it) — never a tool call written in it: in a benchmark run with no tools bound, 44 of 47 replies wrote `send_message` as XML in their text, so every final-text-is-reply path (the ping outcome rules and delivery, the Twilio reply) posts `services/tool_markup.py::clean_reply`'s remainder, or an honest "my answer came out garbled" line when nothing is left. A `tell_owner` answers only the owner's own turn (`owner_asked`, or their own ping): in a friend's ping or a mention wake a note to the owner left the person who asked with nothing. The durable guarantee is the ping record ([pings.md](pings.md)).
- **Endings**: an answer is the answer. An owner-facing turn whose tools ran and that ended silent gets one closing call; one with no tools and no text gets the honest ending ("I stopped before finishing: …"). An autonomous turn that ends empty left it alone. Every closing call keeps the system prompt byte-identical and puts its instruction in a trailing message (a rewritten prompt cost the cache and the turn's thinking). The ping's `pings.hooks.note_stop` hears how the turn ended (`answered`, `deadline`, `turn_budget` — the per-turn dollar cap, which is never the day's spend cap — or `honest_ending`); a model failure propagates (the chat router voices it, a wake's retry reads it).
- **Removed** (each fired 0 times in 8.4 days of logs, or was a GPT-era quirk): the generic "you MUST use your tools" nudge and its keyword gate, forced `tool_choice`, the GPT-empty "summarize" nudge, the plan nudge and plan-raised limit, the repeat guard and reuse cache (identical commands legitimately re-run), the unproductive-turn breaker, the per-surface allowlists, the in-loop Codex 401 branch of the stream (the adapter refreshes itself; a Claude key does not refresh).
- **Scaffolding never persists**: the step-back note, the reply check and the closing instructions are `[SYSTEM]` messages `history_window.strip_scaffolding` removes before every checkpoint; old ones are removed from threads on load.
- **Scaffolding is never the owner speaking**: each loop note is marked (`history_window.scaffolding_note`, `additional_kwargs["edward_scaffolding"]`). `claude_chat_model.to_anthropic_messages` finds the owner's last message ignoring marked notes, so the turn's raw blocks (thinking, `server_tool_use`, `web_search_tool_result`) still replay after a note, the note rides as text in the tool-result turn, and the tail breakpoint and per-turn context stay put (a closing call after a web search was once written blind and missed the cache).
- **Images**: a `look` result (or a ping's photo) reaches the model as image and document blocks; the checkpoint keeps a line naming the ref instead (`history_window.strip_media_blocks`: in place, `attachments[].dehydrated`, `media.hooks.describe_ref`; a PWA upload's `file_id` label becomes `file:<id>`, which `look` opens from file storage, and a person's photo or PDF with no ref at all is kept whole — uploads were once lost after their first turn), and the window counts an image as ~1.6K tokens, not its base64.
- **Server tools** (Anthropic web search and fetch under Claude): their blocks ride the response's `claude_content`; the loop shows them on the work rail and in the trace (`server_tool_uses`), records an `egress`/`detected` row if their input carried a secret, never executes them and never counts them as rounds. Their results can't be redacted: the model reads them at Anthropic inside the same response, before the loop sees them.

**The window**: `max_history_chars` bounds only the history before the turn's trigger; the turn itself gets `CURRENT_TURN_MAX_CHARS` (120K) and, over it, its oldest tool results are elided — **except under Claude**, where an edit to an earlier result breaks the thinking blocks' prefix binding and the cache, so the turn goes whole and the dollar cap bounds it. Each tool result is capped at 30K (`TOOL_RESULT_MAX_CHARS`; only the text of an image result). Tool-call arguments count toward the window; the turn-end checkpoint trim pins the trigger.

**Binding** (`tool_loop.bind_for_turn`): never a forced choice. Under Claude a tool with `metadata["anthropic_tool_resolver"]` — the toolset's `bash`, editor and web tools — goes as itself and `ChatClaude` resolves its Anthropic-defined form per bind, for its model and the flags (`bash_20250124` / `text_editor_20250728` unless `EDWARD_NATIVE_COMPUTER_TOOLS=off`; the web tools per model (`toolset/web.py::server_tool_spec`: the dynamic-filtering search and fetch on Opus and Sonnet, the basic search and a local `web_fetch` on the small model), both local under `EDWARD_SERVER_WEB_TOOLS=off`; `tests/test_toolset_binding.py`); a tool with only a static `metadata["anthropic_tool"]` is bound as that dict unless its flag is `off`; with `parallel_tool_calls=True`; the closing call keeps the tools with `tool_choice="none"` (`closing_llm`). Codex binds the tools as functions and its closing call binds none.

- **The Codex stream** (the fallback provider): reasoning items (with `encrypted_content`, never the id) ride `AIMessage.additional_kwargs["reasoning_items"]` and are replayed before that message's function calls within the current turn only; `strip_reasoning_items` drops older turns' items before checkpointing. `response.failed` / `error` / an early close raise `CodexStreamError(code, message, retryable)` (transient ones retry once); an HTTP 5xx is a retryable `CodexStreamError("http_<status>")` (`test_codex_http_errors.py`). `usage_metadata` carries `cache_read` and `reasoning`. Each request logs one `[codex-cache]` fingerprint line ([llm-and-quota.md](llm-and-quota.md#the-prompt-cache-on-codex)).
- **The Claude stream** (the default provider; [llm-and-quota.md](llm-and-quota.md#claude-the-default-provider)): `ChatClaude` speaks the same contract — text deltas, `reasoning_delta`, `tool_args_delta`, tool calls once on the final chunk. Its raw blocks ride `additional_kwargs["claude_content"]` (carried by `_stream_llm_with_events`, which also keeps the final chunk's `stop_reason` and `estimated_cost_usd`) and are replayed verbatim within the turn; `_checkpoint_messages` runs `strip_claude_thinking`.
- **Prompt order**: `compose_system_prompt(…, tool_manual=, v2=)` puts the static parts first — `base`, the tool manual (`TOOL_MANUAL` under v2, which carries what the assumption-awareness, tool-usage and credential directives said, so they are left out), the state-document directive in the `memory` actions' words when there are state documents — then, after Claude's `STATIC_DYNAMIC_SPLIT`, the per-turn blocks. The "Active State" block (`state_document_entries`) clips each state document to 1,500 chars within a 6,000-char budget. The default persona (`SettingsModel.system_prompt`, `DEFAULT_SYSTEM_PROMPT`) is generic and names the owner through the `{OWNER}` token. Tests: `tests/test_prompt_cache_order.py`, `test_state_docs_in_prompt.py`, `test_engine_unplug.py`.
- **The turn's trace outlives the stream** (`graph/turn_trace.py`): both paths fill a `TraceBuilder` — the reasoning summary, each tool (name, `args_summary`, ok/error, ms, a result preview), server tools too, and `memory_hits` — and store it at `AIMessage.additional_kwargs["trace"]` on the answer they checkpoint (a ping's conversation shows its work); `routers/conversations.serialize_checkpoint_message` returns it as `message.trace`. Never stored: a message body (a send shows its recipient), text typed in a browser (`chrome`/`browser` `type` and `steps`), and any string the egress secret scanner flags. Test: `tests/test_turn_trace.py`.
- Tests: `tests/test_tool_loop.py` (drives both paths through `tests/fixtures/tool_loop.py`), `test_tool_policy.py`, `test_turn_window.py`, `test_tool_deadlines.py`, `test_strip_media_blocks.py`, `test_tool_iteration_cap.py`, `test_tests_never_send.py`, `test_llm_routing_knobs.py`, `test_codex_reasoning_replay.py`, `test_claude_chat_model.py`.

**No test sends a real message**: `tests/conftest.py` refuses any subprocess whose program is `osascript` or `shortcuts` in every test (`_never_run_osascript`), since the approval hold is no longer between a test and the owner's Messages.

## One turn at a time in a thread (`services/thread_turns.py`, 2026-09-27)

**Why**: `mind_service.thread_lock` kept two wakes from interleaving in `edward-mind`, but nothing else took it. Chat and voice streams, a scheduled event firing in the owner's own thread ("text me at 5") or falling back to `edward-mind`, a heartbeat turn in a contact's thread — all ran unlocked. A turn reads the checkpoint at its start and writes it at its end, so two overlapping turns in one thread (a wake and the memory report in `edward-mind` one morning, or the owner on two devices) each wrote their own copy and the last write won.

- `chat_with_memory` and `stream_with_memory_events` hold the per-thread lock (`thread_turns.acquire`, which takes `mind_service.thread_lock(conversation_id)`) around the whole turn, before the `turn_log` row starts. A second turn in the thread waits; different threads run side by side. Keep the name and signature of `thread_lock(conversation_id)`.
- **A turn never waits on itself**: turns with source `mind` or `pulse` (`CALLER_SERIALIZED_SOURCES`) never take the lock — the wake already holds it when it calls `chat_with_memory`, and a test pins that every `wake(` call passes one of those sources. A turn started from inside a turn on its own thread (same task or a child task) sees a context-variable marker and runs without waiting; the streaming path sets it per step, never across a `yield`, so it cannot leak into the consumer. `approvals_service.append_thread_note` holds the lock but runs no turn and is spawned as its own task. Known limit: a fire-and-forget task created inside a turn that starts its own turn on the same thread skips the lock rather than risk waiting on its parent (none exist).
- The streaming path lets go as `done` passes (the voice socket breaks on `done` and leaves the close to the loop's finalizer).
- **A stream nobody closes**: a stream the owner stopped used to be abandoned in a reference cycle and hold its thread until the cyclic GC ran (over a minute in a quiet process). A waiting turn nudges the young GC generations once a second (`GC_NUDGE_SECONDS`), and a wait longer than `ACQUIRE_BACKSTOP_SECONDS` (20 min, longer than every holder's own bound) proceeds without the lock with a WARNING.
- The scheduler takes an ordinary event's thread **before** its 600 s bound starts, so the bound covers only the event's own turn, and holds it once for both attempts and the error note ([scheduler.md](scheduler.md)).
- Tests: `tests/test_thread_serialization.py`.

## Stop, leaving, and a send in flight (2026-09-27)

- **One context for the whole streamed turn**: `routers/chat._yield_with_heartbeats` runs each step in its own task (so a heartbeat timeout never cancels it), and every one of those tasks runs in one context — a copy of the caller's taken as the stream starts (`loop.create_task(…, context=…)`). Until 2026-09-27 each task copied the caller's context afresh, so the turn record `turn_ledger.begin_turn` sets in the first step was gone from the second step on and in the post-turn work: a PWA chat turn had no turn for the send guard, the used-memory credit, `note_memories`, the post-turn extraction's `turn_id` (`turn_log.memories_extracted`), the spend ledger's `turn:chat` label, or the provenance of `remember` and the extraction. **So the ten-minute "Already sent…" check applies to sends from the PWA chat too** — the owner asking twice for the same text to the same person inside ten minutes gets "Already sent" the second time. The key is the number, not the channel, so a resend of the same text by SMS after an iMessage that did not arrive is refused too. A PWA chat turn that reads untrusted content (a web search, a browser read) is tainted like voice and every other turn, and feeds the thread's 7-day history taint ([trust-boundary.md](trust-boundary.md)). The turn's context never leaks into the caller's. Test: `tests/test_chat_turn_context.py`.
- **Stop closes the stream**: `routers/chat._yield_with_heartbeats` shields each step only for the 10 s heartbeat timeout and, when the client goes away, cancels the step in flight with `CLIENT_GONE` ("chat client disconnected"); `_wrap_chat_stream` re-raises at once on `GeneratorExit` or that cancel — no explainer model call on Stop, no "async generator ignored GeneratorExit". Before this a resend after Stop waited for the stopped step (an LLM call can run 300 s) or a GC.
- **Leaving right after the answer keeps it**: the last step (checkpoint write, trim, post-turn work) runs as a task behind `asyncio.shield`; on a cancel it waits for that task to land before re-raising, so the owner's next turn cannot load the thread mid-write. It used to be cancelled by a tap, an app switch or a dropped network while Stop was still on screen, and the message and the answer were gone on reload. Still open: leaving on the very last content chunk cancels the step before the save. Test: `tests/test_chat_stream_close.py`.
- **A send the turn is cancelled under is finished and recorded**: `graph/tools._send_and_note` runs the transport and the "Already sent" record as one shielded unit — in the toolset's `send_message` and in the legacy send tools — so a send that has started is finished, not cut off by Stop. Test: `tests/test_send_survives_cancel.py`.
- A consumer that breaks right after `done` (the voice socket) records `completed`, not `stopped` ([ledgers.md](ledgers.md)).

## Every turn is labelled for the spend ledger

A turn with no job scope labels its own chat model's calls `turn:<source>` (`streaming.turn_purpose`, stamped in `streaming._build_llm`; `turn:background` with no source); an outer `mind:*`, `ping:*` or `pulse` scope always wins, and enrichment calls inside a turn keep their own caller label. Details: [llm-and-quota.md](llm-and-quota.md#the-codex-spend-ledger--who-spends-the-codex-week).

## Checkpoint history

`_trim_checkpoint_history` had never landed until 2026-09-14 — `aupdate_state` without `as_node` raises "Ambiguous update, specify as_node" and `_safe_update_state` only logs it — so every thread kept its whole history on disk (the pulse thread grew to 2,042 messages, a 37 MB messages blob per checkpoint). Fixed with `as_node="extract_memory"`; the trim runs on every turn of both loops and honours a per-call `max_history_chars`. What was already written stays: langgraph-checkpoint-postgres keeps every earlier checkpoint, blob version and pending write. `backend/scripts/prune_checkpoint_history.py --dry-run | --apply` keeps each thread's latest checkpoint and deletes the rest, then VACUUMs. Test: `tests/test_checkpoint_trim.py`.

**Images and PDFs leave saved history** (2026-10-11): `_checkpoint_messages` strips them once, through `history_window.strip_media_blocks`, which calls `media.dehydrate.strip_media_blocks` — it replaces each image/PDF block in a HumanMessage or ToolMessage, in place and on copies only, with a line carrying its ref, its description and the call that shows it again — a photo is paid for in its own turn, not re-sent on every later one ([media.md](media.md#saved-history)). Test: `tests/test_media_dehydrate.py`.
